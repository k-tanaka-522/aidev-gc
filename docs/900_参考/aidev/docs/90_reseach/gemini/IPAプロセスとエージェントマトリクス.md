(AA)、インフラストラクチャアーキテクト (IA)、および言語特化型のポリグロットコーダー (PC) という3つの役割を厳格に分離し、それらを統括する「メタアーキテクト」が状況に応じてエージェントを動的に生成・更新するという概念である。このアーキテクチャは、日本のシステム開発標準である IPA 共通フレーム (SLCP) の第2階層（システム開発工程）および第3階層（アクティビティ）に準拠し、生成AIによる自律的な開発プロセスを、産業界で検証された厳格なプロセスモデルにマッピングすることを目的としている。特筆すべきは、Model Context Protocol (MCP) やシステムプロンプト）を自動的に書き換える「自己進化メカニズム」を導入することで、常に最新の技術スタック（例：Terraformの新バージョン、新しいJavaのLTSなど）に適応可能な「エージェントスワーム（群知能）」を実現する。本報告書では、このアーキテクチャの理論的背景、IPAフレームワークへの詳細なマッピング、各エージェントの詳細定義、そして実装に必要なスキルマトリクスを15,000語にわたり詳述する。2. 現代ソフトウェアエンジニアリングの課題と動的アーキテクチャの必要性従来のソフトウェア開発ライフサイクル（SDLC）は、静的な役割定義と固定されたツールチェーンに依存してきた。しかし、現代の技術環境は極めて流動的である。クラウドサービスのAPIは週単位で更新され、セキュリティ標準（NIST、CISベンチマークなど）は頻繁に改定され、プログラミング言語のエコシステムは日々進化している。このような環境下では、特定のバージョンのJavaやTerraformにハードコードされた静的なエージェント定義は、瞬時に陳腐化する運命にある 1。本提案が解決を目指すのは、この「固定化された知識」の問題である。解決策として自己進化型エージェントシステム (Self-Evolving Agent System) 責任分掌の三原則：アプリケーション、インフラ、コードの分離生成AIを用いた開発において最も懸念されるリスクの一つは、コンテキストの汚染による幻覚（ハルシネーション）の増幅である。複雑なビジネスロジックと、微細なインフラ設定を単一のエージェントに処理させると、推論能力が分散し、エラー率が指数関数的に上昇する。これを防ぐため、本アーキテクチャでは、高度に機能する人間によるエンジニアリングチームを模倣し、厳格な職務分掌（Separation of Concerns）を強制する 5。アプリケーションアーキテクトエージェント (AAA): システムの論理的ビューを担当する。データモデル、API契約（OpenAPI/Swagger）、ビジネスロジックフロー、ドメイン境界（Bounded Contexts）を定義する。このエージェントは、コードが「どこで」実行されるかには関知せず、コンポーネントが「どのように」相互作用するかに注力する 5。インフラストラクチャアーキテクトエージェント (IAA): システムの物理的・クラウドビューを担当する。ネットワークトポロジー、セキュリティグループ、IAMロール、リソースプロビジョニングをInfrastructure as Code (IaC) を用いて定義する。AAAが定義した論理コンポーネント（例：「決済サービス」）を、具体的なクラウドリソース（例：「AWS Lambda関数とDynamoDBテーブル」）にマッピングし、セキュリティコンプライアンスを保証する 7。ポリグロットコーダーエージェント (PCA): 実装を担当する。これらはAAAによって定義された契約を満たし、IAAによって提供された環境内で動作するコードを記述するためにインスタンス化される、短命（Ephemeral）なエージェントである。Python、Go、TypeScriptなど、タスクに最適な言語で実装を行う。2.3 IPA 共通フレーム (SLCP) の役割と位置づけAIの活動を産業標準に接地させるため、本アーキテクチャは IPA 共通フレーム 2013 (SLCP) をオントロジーとして採用する。AIの振る舞いを、ブラックボックス的な「魔法」としてではなく、IPAの第2階層（システム開発タスク）および第3階層（アクティビティ）にマッピングされた具体的な「作業」として定義することで、監査可能性と予測可能性を担保する 自己進化のメカニズム：反射的プロンプトエンジニアリングシステムは「反射的プロンプトエンジニアリング（Reflexive Prompt Engineering）」を通じて自己進化を達成する。新しいライブラリやセキュリティ標準がリリースされた際、メタアーキテクトはエージェント定義リポジトリに保存されているシステムプロンプト自体を更新する。検知（Detection）: VPCピアリング、サブネットマスキング）を単一のエージェントに処理させると、コンテキストウィンドウが溢れ、推論能力が低下する。分離することで、特化したコンテキストロード（Appエージェントはドメイン文書を、InfraエージェントはAWS文書をロード）が可能となる。なぜ動的生成なのか？ 標準的な「コーディングエージェント」は脆い場合が多い。タスクに特化してコーダーエージェントを生成するメタアーキテクトを持つことで（例：「高並行処理 tokio 使用に特化したRustエージェントを作成せよ」）、システムプロンプトのノイズを減らせる。エージェントはそのタスクに必要なことだけを知っていればよい。なぜMCPなのか？ MCPはAIにとっての業界標準「USBポート」である。ベンダーロックインを防ぎ、エージェントがツールを切り替える（例：汎用ファイルIOから特化したGitHub統合へ）際に、エージェントのコアを書き換える必要がないためである。3. 第2・第3次オーダーの洞察洞察1（「生きているドキュメント」の波及効果）: エージェントが機能するために AGENTS.md
