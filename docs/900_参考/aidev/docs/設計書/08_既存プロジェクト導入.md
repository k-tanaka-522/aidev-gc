# 既存プロジェクトへの導入

## 1. 概要

### 1.1 課題

既存プロジェクト（すでにコード・ドキュメントがある）にaidevを導入したい場合、「今どこにいるか」がわからない。

### 1.2 解決策

`/init` 時に既存資産を分析し、現在地を推定する。

### 1.3 設計方針

```
1. 破壊的変更をしない（既存コードを壊さない）
2. 段階的に導入（一度に全部やらない）
3. 足りないものを特定（何が必要かを明確に）
```

---

## 2. 導入フロー

### 2.1 全体フロー

```
ユーザー: /init
    │
    ▼
PM: .claude-state/ 確認 → 存在しない
    │
    ▼
PM: 既存資産の確認
    │
    ├─ src/ が存在する → 実装済みコードあり
    ├─ docs/ が存在する → ドキュメントあり
    ├─ tests/ が存在する → テストあり
    └─ infra/ が存在する → インフラ定義あり
    │
    ▼
PM: 「既存のプロジェクトですね。
     状況を確認させてください。」
    │
    ▼
PM: サブエージェントに分析委譲
    │
    ├─ Architect: 設計書・アーキテクチャ分析
    ├─ Coder: コード分析
    └─ QA: テストカバレッジ分析
    │
    ▼
PM: 分析結果を統合
    │
    ▼
PM: ユーザーに報告
    │
    ▼
ユーザーが選択 → その作業から開始
```

### 2.2 分析委譲の詳細

#### Architect への委譲

```markdown
Task: 既存プロジェクトの設計分析

対象:
- docs/ 配下のドキュメント
- 設計図（あれば）
- ADR（あれば）

分析観点:
1. どのような設計書があるか
2. アーキテクチャは明文化されているか
3. 技術選定の根拠は記録されているか

期待する成果物:
- 設計書の有無と内容サマリ
- 不足している設計書のリスト
```

#### Coder への委譲

```markdown
Task: 既存プロジェクトのコード分析

対象:
- src/ 配下のコード
- package.json, requirements.txt 等

分析観点:
1. 使用言語・フレームワーク
2. ディレクトリ構成
3. 実装の進捗（概算）
4. コード品質の印象

期待する成果物:
- 技術スタックのサマリ
- 実装状況のサマリ
```

#### QA への委譲

```markdown
Task: 既存プロジェクトのテスト分析

対象:
- tests/ 配下のテストコード
- CI設定（あれば）

分析観点:
1. テストの種類（unit, e2e, etc.）
2. カバレッジ（概算）
3. CI/CDの有無

期待する成果物:
- テスト状況のサマリ
- 不足しているテストのリスト
```

## 3. 分析結果の報告

### 3.1 報告フォーマット

```markdown
📂 既存プロジェクトを分析しました

## 現在の状況

### 設計書
- 基本設計書: あり（docs/03_設計/）
- API設計: あり（OpenAPI形式）
- DB設計: なし ⚠️
- ADR: なし ⚠️

### コード
- 言語: TypeScript
- フレームワーク: NestJS (backend), React (frontend)
- 進捗: バックエンド 70%、フロントエンド 30%（推定）

### テスト
- 単体テスト: あり（カバレッジ約60%）
- E2Eテスト: なし ⚠️
- CI/CD: GitHub Actions（ビルドのみ）

## 推奨アクション

1. **最優先**: DB設計書の作成
   - 現状コードからスキーマを逆生成可能
   - 設計の明文化が必要

2. **次に重要**: E2Eテストの追加
   - 品質担保のため
   - 主要フローのテストから開始

3. **推奨**: ADRの整備
   - 過去の決定を掘り起こして記録

どこから始めますか？
```

### 3.2 ユーザーの選択肢

1. 推奨順に進める
2. 特定の作業を指定
3. 他の作業を提案

## 5. 分析観点一覧

### 5.1 チェック項目

| 対象 | 確認項目 | 担当 |
|------|---------|------|
| docs/ | 何のドキュメントがあるか | PM → Architect |
| src/ | 言語、フレームワーク、構成 | Coder |
| tests/ | テスト種類、カバレッジ | QA |
| infra/ | IaCの有無、内容 | SRE |
| 設計 | ADRの有無、図の有無 | Architect |
| CI/CD | パイプラインの有無 | SRE |

### 5.2 推定ロジック

#### フェーズの推定

| 状況 | 推定フェーズ |
|------|------------|
| docs/のみ | 設計 |
| docs/ + src/の一部 | 実装（初期） |
| src/がある程度完成 | 実装（中盤〜後半） |
| tests/も充実 | テスト |
| infra/も完成 | 運用準備 |

---

## 6. 注意事項

### 6.1 やらないこと

- 既存コードの大幅な変更
- 既存ディレクトリ構成の変更
- 既存の命名規則の強制変更

### 6.2 やること

- 足りないものを特定
- 段階的に追加
- 既存に合わせて調整

### 6.3 ユーザーへの確認

分析結果に不確かな部分がある場合は、必ずユーザーに確認する：

```
分析結果について確認させてください。

Q: バックエンドの実装進捗は70%程度と推定しましたが、
   実際の感覚と合っていますか？

Q: DBはPostgreSQLで間違いないですか？
```
