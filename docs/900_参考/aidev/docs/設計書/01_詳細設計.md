# 詳細設計 - 導入ステップ

## 1. 概要

### 1.1 目的

本書では、aidev v4へのアップグレードを段階的に導入するための手順を定義する。
既存システムへの影響を最小化しながら、安全に機能を追加していく。

### 1.2 導入方針

```
1. 影響が小さいものから順に導入
2. 各ステップで動作確認を行う
3. 問題があれば次のステップに進まない
```

### 1.3 変更しない箇所

以下は既存の動作を維持し、変更しない：

| ディレクトリ | 内容 | 理由 |
|-------------|------|------|
| `.claude/docs/10_facilitation/` | ファシリテーションガイド | 既に完成度が高い |
| `.claude/docs/40_standards/` | 技術標準 | サブエージェントが参照 |
| `.claude/docs/30_templates/` | テンプレート | 成果物作成に使用 |
| `.claude/docs/00_core-principles.md` | 基本原則 | 全員の共通認識 |
| `.claude/agents/` | 基本構造 | 内容の微修正のみ |

## 2. Step 1: 状態管理の整備

### 2.1 目的

**解決する課題**: セッション切れで忘れる問題

セッションが切れても、次のセッションで「前回どこまでやったか」を把握できるようにする。

### 2.2 作業内容

#### 2.2.1 context.md の追加

`.claude-state/context.md` を新規作成。人間が読めるセッション引継ぎ用サマリ。

```markdown
# セッションコンテキスト

## 現在の状況
- フェーズ: 設計
- 直前の作業: API設計書のレビュー

## 次にやること
- C4モデルの作成
- ADRの記録
```

#### 2.2.2 decisions.json の構造拡張

「なぜその決定をしたか」を必須化。

**Before**:
```json
{
  "auth-method": "JWT"
}
```

**After**:
```json
{
  "auth-method": {
    "decision": "JWT",
    "reason": "ステートレスでスケールしやすい",
    "alternatives": ["Session", "OAuth2"],
    "decidedAt": "2025-01-11",
    "decidedBy": "Architect"
  }
}
```

#### 2.2.3 tasks.json の status 拡張

より細かい状態管理のため、statusを拡張。

| status | 意味 | 説明 |
|--------|------|------|
| `pending` | 未着手 | まだ作業を開始していない |
| `in-progress` | 作業中 | 現在作業中 |
| `review` | レビュー待ち | 作業完了、ユーザー確認待ち |
| `revision` | 修正中 | フィードバックを受けて修正中 |
| `done` | 完了 | 承認済み |
| `failed` | 失敗 | 何らかの理由で失敗 |

### 2.3 既存への影響

**なし** - 新規ファイルの追加と既存ファイルの構造拡張のみ。

### 2.4 確認方法

- [ ] `/init` で状態が復元されることを確認
- [ ] セッション切れ後、続きができることを確認

## 3. Step 2: スキル基盤の構築

### 3.1 目的

**解決する課題**: コンテキストが溢れる問題

必要な専門知識を必要な時だけロードする仕組みを構築する。

### 3.2 作業内容

#### 3.2.1 ディレクトリ構造

```
.claude/skills/
├── CATALOG.md           # スキル一覧（検索用インデックス）
├── meta/
│   └── skill-creator/   # スキル作成用
├── languages/
│   ├── typescript/
│   └── python/
├── architecture/
│   ├── c4-modeling/
│   └── adr/
├── devops/
│   └── (後から追加)
└── testing/
    └── (後から追加)
```

#### 3.2.2 CATALOG.md の役割

PMが `/init` 時にプロジェクトの技術スタックを確認し、必要なスキルを特定するためのインデックス。

```markdown
| カテゴリ | スキルID | 用途 | 使用Agent |
|---------|---------|------|----------|
| languages | typescript | TypeScript実装 | Coder |
| architecture | c4-modeling | C4アーキテクチャ図 | Architect |
```

#### 3.2.3 初期スキル（優先度順）

1. `meta/skill-creator/` - 新しいスキルを作成するためのスキル
2. `languages/typescript/` - TypeScript実装のベストプラクティス
3. `languages/python/` - Python実装のベストプラクティス
4. `architecture/c4-modeling/` - C4アーキテクチャ図作成
5. `architecture/adr/` - Architecture Decision Records

### 3.3 既存への影響

**なし** - 新規ディレクトリとファイルの追加のみ。

### 3.4 確認方法

- [ ] サブエージェントがスキルを参照できることを確認

## 4. Step 3: コマンド拡張

### 4.1 目的

**解決する課題**: 既存プロジェクトに導入しにくい問題

`/init` で状態を復元し、既存プロジェクトの分析ができるようにする。

### 4.2 作業内容

#### 4.2.1 init.md の修正

追加する処理：

1. **状態ファイル読み込み**
   - `.claude-state/` が存在すれば読み込む
   - `context.md` から前回の状況を把握

2. **既存プロジェクト検知・分析**
   - `src/`, `docs/`, `tests/`, `infra/` の存在を確認
   - 存在すればサブエージェントに分析を委譲

3. **activeSkills 設定**
   - 技術スタックに応じてスキルを特定
   - `project-state.json` に記録

#### 4.2.2 next.md の修正

追加する処理：

1. **タスク完了時の状態更新**
   - サブエージェントが `tasks.json` を更新する手順を明記
   - `decisions.json` への記録タイミングを明記

### 4.3 既存への影響

**小** - 既存コマンドの拡張。後方互換性あり。

### 4.4 確認方法

- [ ] `/init` で「前回の続き」が表示されることを確認
- [ ] 既存プロジェクトで `/init` したとき分析が動くことを確認

---

## 5. Step 4: サブエージェント更新

### 5.1 目的

**解決する課題**: セッション切れで忘れる問題（状態更新の徹底）

サブエージェントが作業完了時に状態を更新するルールを追加する。

### 5.2 作業内容

各 `AGENT.md` に「状態更新ルール」セクションを追加：

```markdown
## 状態更新ルール

**YOU MUST**: 作業完了時に以下を更新

### 1. tasks.json を更新
- status: "done" or "review"
- output: 成果物のパス
- completedAt: 日時

### 2. decisions.json に重要な決定を記録
- decision: 何を決めたか
- reason: なぜそう決めたか
- alternatives: 検討した代替案

### 3. PMに結果を報告
- 成果物のパス
- 完了したこと
- 次に必要なこと
```

### 5.3 対象

- `.claude/agents/consultant/AGENT.md`
- `.claude/agents/app-architect/AGENT.md`
- `.claude/agents/infra-architect/AGENT.md`
- `.claude/agents/coder/AGENT.md`
- `.claude/agents/qa/AGENT.md`
- `.claude/agents/sre/AGENT.md`

### 5.4 既存への影響

**小** - 既存 AGENT.md への追記のみ。

### 5.5 確認方法

- [ ] サブエージェントが `tasks.json` を更新することを確認

---

## 6. Step 5: PM軽量化

### 6.1 目的

**解決する課題**: PMが役割を逸脱する問題

PMの責務を明確化し、役割逸脱を防ぐ。

### 6.2 作業内容

#### 6.2.1 CLAUDE.md の簡素化

```markdown
# あなたはPM（軽量）です

## 役割
- ユーザー対話（唯一の窓口）
- ファシリテーション
- サブエージェントへの委譲
- 進捗管理

## 禁止事項
- コードを書かない → Coder に委譲
- 設計書を書かない → Architect に委譲
- 技術判断しない → Architect に相談

## 参照ドキュメント
- .claude/docs/10_facilitation/（ファシリテーションガイド）
- .claude-state/（状態ファイル）
- .claude/docs/40_standards/ → **参照しない**
```

#### 6.2.2 参照ドキュメントの制限

PMが参照するドキュメントを制限し、コンテキスト肥大化を防ぐ。

| 参照する | 参照しない |
|---------|-----------|
| `10_facilitation/` | `40_standards/` |
| `.claude-state/` | `30_templates/` |
| `00_core-principles.md` | 実装コード |

### 6.3 既存への影響

**中** - CLAUDE.md の大幅な変更。

### 6.4 注意事項

- **これは最後にやる**
- Step 1〜4 が動作確認できてから
- 慎重にテストしながら進める
- 問題があればロールバックできるようにする

### 6.5 確認方法

- [ ] PMがコードを書かないことを確認
- [ ] PMが設計書を直接書かないことを確認
- [ ] サブエージェントへの委譲が適切に行われることを確認

---

## 7. 導入スケジュール

```
Step 1: 状態管理の整備      ← 影響なし、まずこれ
    ↓
Step 2: スキル基盤の構築    ← 影響なし
    ↓
Step 3: コマンド拡張        ← 影響小、動作確認しながら
    ↓
Step 4: サブエージェント更新 ← 影響小
    ↓
Step 5: PM軽量化            ← 影響中、最後に慎重に
```

**重要**: 各Step完了後、必ず動作確認を行う。問題があれば次のStepに進まない。
