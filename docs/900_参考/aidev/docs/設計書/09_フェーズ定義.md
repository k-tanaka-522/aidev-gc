# フェーズ定義

## 1. 概要

### 1.1 設計方針

```
詳細タスクは事前定義しない
AIが判断して進める
```

フェーズは「大枠」のみ定義し、具体的なタスクはプロジェクトに応じてAIが判断する。

### 1.2 なぜ大枠のみか

| 問題 | 詳細定義の場合 | 大枠定義の場合 |
|------|--------------|--------------|
| プロジェクトごとの違い | 合わない | 柔軟に対応 |
| 例外への対応 | 困難 | AI判断で対応 |
| メンテナンス | 大変 | 最小限 |

---

## 2. フェーズ一覧

| フェーズ | 目的 | 主な成果物 | 主担当 | 完了条件 |
|---------|------|----------|--------|---------|
| 企画 | 何を作るか決める | 企画書 | Consultant | ユーザー承認 |
| 要件定義 | 何が必要か整理 | 要件定義書 | PM + Consultant | ユーザー承認 |
| 設計 | どう作るか決める | 設計書、ADR | Architect | ユーザー承認 |
| **実装計画** | **タスク分解** | **実装計画書** | **App-Architect** | **ユーザー承認** |
| 実装 | 作る | コード、単体テスト | Coder | テストパス（TDD必須） |
| テスト | 品質確認 | テスト結果 | QA | 品質基準クリア |
| 運用準備 | 本番準備 | インフラ、Runbook | SRE | デプロイ完了 |

## 3. 各フェーズ詳細

### 3.1 企画フェーズ

**目的**: 何を作るか、なぜ作るかを明確にする

**主な活動**:
- ビジョン定義
- 課題分析
- 解決策の検討
- ROI評価

**成果物**:
- 企画書

**主担当**: Consultant

**完了条件**: ユーザーが企画書を承認

### 3.2 要件定義フェーズ

**目的**: 何が必要かを整理する

**主な活動**:
- 機能要件の洗い出し
- 非機能要件の定義
- ユーザーストーリー作成
- 優先順位付け

**成果物**:
- 要件定義書
- ユーザーストーリー

**主担当**: PM（Consultantと協力）

**完了条件**: ユーザーが要件定義書を承認

### 3.3 設計フェーズ

**目的**: どう作るかを決める

**主な活動**:
- アーキテクチャ設計
- API設計
- DB設計
- 技術選定
- ADR作成

**成果物**:
- 設計書（アーキテクチャ、API、DB）
- ADR（設計決定記録）

**主担当**: Architect（App-Architect, Infra-Architect）

**完了条件**: ユーザーが設計書を承認

### 3.3.5 実装計画フェーズ【新規】

**目的**: 設計書を「実行可能なタスクリスト」に変換する

**主な活動**:
- 設計書の分析
- 2-5分で完了するタスクへの分解
- 各タスクにファイルパス、コード例、検証ステップを記載
- TDD サイクル（RED→GREEN→REFACTOR→COMMIT）の明記

**成果物**:
- 実装計画書（`docs/05_実装計画/YYYY-MM-DD-feature.md`）

**主担当**: App-Architect（writing-plans スキル使用）

**完了条件**: ユーザーが実装計画書を承認

**重要**: このフェーズを経ることで、Coder は Fresh Context で作業でき、コンテキスト汚染を防ぐ。

### 3.4 実装フェーズ

**目的**: 作る

**主な活動**:
- **TDD サイクル**（必須）
  - RED: 失敗するテストを書く
  - GREEN: テストを通す最小限のコードを書く
  - REFACTOR: リファクタリング
  - COMMIT: コミット
- コードレビュー（2段階）
  - Stage 1: 仕様準拠確認
  - Stage 2: コード品質確認

**成果物**:
- ソースコード
- 単体テスト

**主担当**: Coder（タスク単位で Fresh Context 起動）

**完了条件**: 全テストがパス

**禁止事項**: テストを書く前に本番コードを書いたら、そのコードは削除する

### 3.5 テストフェーズ

**目的**: 品質を確認する

**主な活動**:
- E2Eテスト設計・実行
- 性能テスト
- セキュリティテスト
- バグ修正

**成果物**:
- テストコード
- テスト結果レポート

**主担当**: QA

**完了条件**: 品質基準をクリア

### 3.6 運用準備フェーズ

**目的**: 本番環境を準備する

**主な活動**:
- IaC作成
- CI/CD構築
- 監視設計
- Runbook作成

**成果物**:
- インフラコード
- CI/CDパイプライン
- 監視設定
- 運用手順書

**主担当**: SRE

**完了条件**: 本番デプロイ完了

## 4. フェーズ移行

### 4.1 移行の流れ

```
1. 現フェーズの完了条件を満たす
    ↓
2. PM: ユーザーに確認
    ↓
3. ユーザー: 承認
    ↓
4. PM: project-state.json の phase を更新
    ↓
5. PM: 次フェーズ開始を報告
```

### 4.2 移行条件

| 現フェーズ | 次フェーズ | 移行条件 |
|-----------|-----------|---------|
| 企画 | 要件定義 | 企画書承認 |
| 要件定義 | 設計 | 要件定義書承認 |
| 設計 | **実装計画** | 設計書承認 |
| **実装計画** | **実装** | **実装計画書承認** |
| 実装 | テスト | 全テストパス（TDD完了） |
| テスト | 運用準備 | 品質基準クリア |
| 運用準備 | 完了 | デプロイ完了 |

---

## 5. フェーズの柔軟性

### 5.1 厳密な順序ではない

```
フェーズは厳密な順序ではない：
・必要に応じて前のフェーズに戻る
・並行して進めることもある
・AIが状況を見て判断する
```

### 5.2 戻りの例

| 状況 | 戻り先 |
|------|--------|
| 設計中に要件不足が発覚 | 要件定義 |
| 実装中に設計の矛盾発見 | 設計 |
| テストで重大なバグ | 実装 |
| 本番で仕様漏れ発覚 | 要件定義 |

### 5.3 並行の例

| 並行パターン | 説明 |
|-------------|------|
| アプリ設計 + インフラ設計 | 設計フェーズ内で並行 |
| 実装 + テスト設計 | テスト設計を先行 |
| 実装 + CI/CD構築 | インフラ準備を先行 |

## 6. project-state.json での管理

### 6.1 フェーズの記録

```json
{
  "name": "ECサイト構築",
  "phase": "設計",
  "phaseHistory": [
    {
      "phase": "企画",
      "startedAt": "2025-01-10",
      "completedAt": "2025-01-11"
    },
    {
      "phase": "要件定義",
      "startedAt": "2025-01-11",
      "completedAt": "2025-01-13"
    },
    {
      "phase": "設計",
      "startedAt": "2025-01-13"
    }
  ]
}
```

### 6.2 フェーズ戻りの記録

```json
{
  "phaseHistory": [
    { "phase": "企画", "..." },
    { "phase": "要件定義", "..." },
    { "phase": "設計", "..." },
    { "phase": "実装", "startedAt": "2025-01-15" },
    {
      "phase": "設計",
      "startedAt": "2025-01-17",
      "reason": "API設計の見直しが必要"
    }
  ]
}
```
