# 状態管理設計

## 1. 概要

### 1.1 目的

```
セッションが切れても忘れない
次のセッションで続きができる
```

### 1.2 なぜ状態管理が必要か

| 問題 | 原因 | 解決策 |
|------|------|--------|
| 前回の作業を忘れる | セッション内のみの記憶 | ファイルに永続化 |
| なぜその決定をしたか不明 | 決定の理由を記録していない | reason必須化 |
| 進捗がわからない | タスク状態が曖昧 | status詳細化 |

### 1.3 設計方針

```
1. JSON: 機械可読（AIが処理しやすい）
2. Markdown: 人間可読（人が確認しやすい）
3. 両方使い分け: 目的に応じて
```

## 3. 各ファイル詳細

### 3.1 project-state.json

プロジェクト全体の情報を管理。

```json
{
  "name": "ECサイト構築",
  "description": "小規模EC事業者向けのオンラインショップ",
  "phase": "設計",
  "startedAt": "2025-01-10",
  "techStack": {
    "frontend": "TypeScript, React",
    "backend": "TypeScript, NestJS",
    "database": "PostgreSQL",
    "infra": "AWS"
  },
  "activeSkills": [
    "typescript",
    "react",
    "nestjs",
    "openapi",
    "cloudformation"
  ]
}
```

| フィールド | 型 | 説明 |
|-----------|-----|------|
| name | string | プロジェクト名 |
| description | string | プロジェクト概要 |
| phase | string | 現在のフェーズ |
| startedAt | string | 開始日（ISO8601） |
| techStack | object | 技術スタック |
| activeSkills | array | アクティブなスキル |

### 3.2 tasks.json

タスクの進捗を管理。

```json
{
  "_schema": {
    "description": "タスク進捗管理",
    "status_values": ["pending", "in-progress", "review", "revision", "done", "failed"]
  },
  "requirement-definition": {
    "status": "done",
    "output": "docs/02_要件定義書.md",
    "completedAt": "2025-01-12T10:00:00Z",
    "agent": "Consultant"
  },
  "c4-modeling": {
    "status": "in-progress",
    "agent": "Architect",
    "startedAt": "2025-01-13T09:00:00Z"
  },
  "backend-impl": {
    "status": "pending"
  }
}
```

#### status の値

| status | 意味 | 説明 |
|--------|------|------|
| `pending` | 未着手 | まだ作業を開始していない |
| `in-progress` | 作業中 | 現在作業中 |
| `review` | レビュー待ち | 作業完了、ユーザー確認待ち |
| `revision` | 修正中 | フィードバックを受けて修正中 |
| `done` | 完了 | 承認済み |
| `failed` | 失敗 | 何らかの理由で失敗 |

### 3.3 decisions.json

重要な決定とその理由を記録。

```json
{
  "_schema": {
    "description": "決定記録（なぜを残す）",
    "required_fields": ["decision", "reason"]
  },
  "auth-method": {
    "decision": "JWT",
    "reason": "ステートレスでスケールしやすい",
    "alternatives": ["Session", "OAuth2"],
    "decidedAt": "2025-01-11",
    "decidedBy": "Architect"
  },
  "database": {
    "decision": "PostgreSQL",
    "reason": "複雑なクエリ対応、JSONB対応",
    "alternatives": ["MySQL", "MongoDB"],
    "decidedAt": "2025-01-11",
    "decidedBy": "Architect"
  }
}
```

| フィールド | 型 | 必須 | 説明 |
|-----------|-----|:---:|------|
| decision | string | ✅ | 何を決めたか |
| reason | string | ✅ | なぜそう決めたか |
| alternatives | array | - | 検討した代替案 |
| decidedAt | string | - | 決定日 |
| decidedBy | string | - | 決定者 |

### 3.4 context.md

人間が読めるセッション引継ぎ用サマリ。

```markdown
# セッションコンテキスト

セッション跨ぎで引き継ぐための状況サマリ（人間可読形式）。

---

## 現在の状況

**最終更新**: 2025-01-13
**現在フェーズ**: 設計

### 直前の作業内容

- API設計書のレビュー完了
- 認証方式をJWTに決定

### 次にやるべきこと

1. C4モデルの作成
2. ADRの記録（認証方式）

---

## 決定済み事項

1. 認証方式: JWT（理由: ステートレス）
2. DB: PostgreSQL（理由: 複雑なクエリ対応）

---

## 未解決の課題

- CI/CD戦略の決定が必要
```

## 4. 更新タイミング

### 4.1 誰がいつ更新するか

| ファイル | 更新タイミング | 更新者 |
|----------|--------------|--------|
| project-state.json | /init時、フェーズ移行時 | PM |
| tasks.json | タスク状態変化時 | サブエージェント |
| decisions.json | 重要な決定時 | Architect, PM |
| context.md | セッション終了時、区切り時 | PM |

### 4.2 タスク状態の遷移

```
pending → in-progress → review → done
                 ↓
             revision → review → done
                 ↓
              failed
```

## 5. Git管理

### 5.1 管理方針

```
.claude-state/          ❌ Git管理外
```

### 5.2 理由

- セッション固有の状態
- 個人の作業状況
- 頻繁に変更される

### 5.3 .gitignore 設定

```gitignore
# aidev状態ファイル
.claude-state/
```

## 6. 使用パターン

### 6.1 セッション開始時

```
1. PM: /init 実行
2. PM: .claude-state/ 存在確認
3. PM: 存在すれば読み込み
   - context.md から状況把握
   - tasks.json から次タスク特定
4. PM: ユーザーに状況報告
```

### 6.2 作業完了時

```
1. サブエージェント: 作業完了
2. サブエージェント: tasks.json 更新
   - status: "done" or "review"
   - output: 成果物パス
3. サブエージェント: 必要なら decisions.json 更新
4. サブエージェント: PMに報告
5. PM: 必要なら context.md 更新
```

### 6.3 セッション終了時

```
1. PM: context.md を更新
   - 現在の状況
   - 次にやること
   - 未解決の課題
```
