# aiDev ユーザーストーリー

## 概要

aiDev は様々な立場のユーザーが、開発プロセスの異なるフェーズから利用できる。
本ドキュメントでは、ターゲットユーザーと利用シナリオを整理する。

---

## ターゲットユーザー一覧

| ターゲット | 開始フェーズ | 主な価値 |
|-----------|-------------|----------|
| 事業会社（内製化） | 企画 | SIerに頼らず内製できる |
| SIer | RFP〜 | 工数削減、品質標準化 |
| 開発パートナー | 設計書あり | 設計準拠の高品質な製造 |
| スタートアップ | アイデア | 素早くMVP、コスト削減 |
| フリーランス / 個人開発者 | 案件 | 1人でもチーム品質 |
| 社内IT部門 | 既存コード | 可視化・改修 |
| 教育 / 研修 | 学習 | 開発プロセスの習得 |

---

## 1. 事業会社（内製化）

### ペルソナ
- 企画担当、事業責任者
- 技術的な知識は限定的
- 自社でシステムを作りたい

### シナリオ
```
1. 「社内の申請管理システムを作りたい」
2. aiDev: 「どんな業務で使いますか？」
3. 「経費申請です」
4. aiDev: 「承認フローはありますか？」
5. 「上司→経理の2段階です」
6. ...（一問一答で情報収集）
7. aiDev: 「企画書を作成しました。確認してください」
8. 「OK」
9. aiDev: 「要件定義に進みます」
10. ...
```

### aiDev の役割
- **フルファシリテーション**（何も知らない前提）
- 一問一答で導く
- 専門用語を使わず説明

### 価値
- SIerに依頼せず内製できる
- コスト削減
- 自社でコントロールできる

---

## 2. SIer（受託開発）

### ペルソナ
- 営業、PM、アーキテクト、開発チーム
- 開発プロセスは理解している
- 効率化・標準化したい

### シナリオ
```
営業 → aiDev → RFP対応、提案書作成
PM → aiDev → 要件定義、進捗管理
アーキテクト → aiDev → 設計書作成
開発チーム → aiDev → 実装・テスト
インフラ → aiDev → 構築・デプロイ
```

### aiDev の役割
- **プロセス効率化**（ある程度わかっている前提）
- ドキュメント自動生成
- 品質チェック

### 価値
- 工数削減
- 品質標準化
- 納品レベルのドキュメント

---

## 3. 開発パートナー / 協力会社

### ペルソナ
- 元請から設計書を受領して開発
- 設計は固まっている
- 製造に集中したい

### シナリオ
```
1. 元請から基本設計書・詳細設計書を受領
2. aiDev に設計書を読み込ませる
3. aiDev: 「設計書を確認しました。実装を開始しますか？」
4. 「はい」
5. aiDev → Coder: 設計書に従って実装
6. aiDev → QA: テスト実施
7. 成果物を元請に納品
```

### aiDev の役割
- **設計→実装の変換**（製造特化）
- 設計書準拠チェック
- 品質確保

### 価値
- 設計書に忠実な実装
- 品質向上
- 手戻り削減

---

## 4. スタートアップ

### ペルソナ
- 創業者（非エンジニア or エンジニア1人）
- 少人数で素早く作りたい
- 外部に頼む予算がない

### シナリオ
```
1. 「〇〇のサービスを作りたい」
2. aiDev: ビジネス背景をヒアリング
3. aiDev: 「MVPとして最小限の機能は何ですか？」
4. ...
5. aiDev → 企画〜MVP実装まで一気通貫
```

### aiDev の役割
- **一気通貫サポート**
- MVP に必要な機能の絞り込み
- スピード重視

### 価値
- コスト削減
- スピード
- 自分でコントロール

---

## 5. フリーランス / 個人開発者

### ペルソナ
- 1人で複数ロールをこなす
- PM / 設計 / 実装 / テストを全部やる
- 品質を落としたくない

### シナリオ
```
1. 案件を受注
2. aiDev → 要件整理
3. aiDev → 設計
4. aiDev → 実装（レビューも aiDev）
5. aiDev → テスト
6. 納品
```

### aiDev の役割
- **ロール補完**
- 1人では見落としがちな観点を補う
- レビュアーとして機能

### 価値
- 1人でも「チーム開発」の品質
- 抜け漏れ防止
- 効率化

---

## 6. 社内IT部門

### ペルソナ
- 既存システムの保守・運用担当
- システムがブラックボックス化している
- ドキュメントがない

### シナリオ
```
1. 既存システムのコードを aiDev に読み込ませる
2. aiDev: 「コードを解析しました。ドキュメント化しますか？」
3. 「はい」
4. aiDev → リバースエンジニアリング → 設計書生成
5. 改修・機能追加
```

### aiDev の役割
- **可視化・ドキュメント化**
- 既存コードの解析
- 改修支援

### 価値
- ブラックボックス解消
- 属人化解消
- 改修リスク低減

---

## 7. 教育 / 研修

### ペルソナ
- 新人エンジニア、学生
- 開発プロセスを学びたい
- 実践しながら覚えたい

### シナリオ
```
1. 「Webアプリを作りながら開発プロセスを学びたい」
2. aiDev: 企画フェーズから開始
3. aiDev: 「なぜ要件定義が必要か」を説明しながら進行
4. ...各フェーズでベストプラクティスを解説
5. 完成時には開発プロセス全体を体験
```

### aiDev の役割
- **学習支援**
- なぜこうするか説明
- ベストプラクティスの解説

### 価値
- 体系的な開発プロセスの習得
- 実践的な学習
- メンター代わり

## シナリオごとの aiDev 設定

| ターゲット | 開始コマンド | 特記事項 |
|-----------|-------------|----------|
| 事業会社 | `/init` | フルファシリテーション |
| SIer | `/init` または `/status` | フェーズスキップ可能 |
| 開発パートナー | 設計書読み込み | 設計フェーズから開始 |
| スタートアップ | `/init` | MVP重視 |
| フリーランス | `/init` | 1人複数ロール |
| 社内IT | 既存コード読み込み | リバースエンジニアリング |
| 教育 | `/init` | 説明モード有効 |

---

## 8. 継続開発（既存システムの改修）

### ペルソナ
- 既存システムを運用中のチーム
- 機能追加・バグ修正が発生

### 変更規模の分類

| レベル | 内容 | 例 | aiDev の対応 |
|--------|------|-----|-------------|
| **Patch** | バグ修正 | 動かない、表示がおかしい | 影響確認 → 修正 → テスト |
| **Minor** | 機能追加・改善 | 〇〇機能追加、UI改善 | 設計書更新 → 実装 |
| **Major** | 要件レベルの変更 | リビジョン、大幅リニューアル | 要件定義から見直し |

### aiDev の役割
- 変更規模の判断（Patch / Minor / Major）
- 影響範囲の確認
- 適切なプロセスの提案

### 価値
- 場当たり的な対応を防ぐ
- 設計書との整合性維持
- 技術的負債の蓄積を抑制
