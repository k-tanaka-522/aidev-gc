# 実装計画書チェックリスト

実装計画書（Phase 2.5 成果物）の品質確認用チェックリスト。

---

## 概要

実装計画書は設計書を「実行可能なタスクリスト」に変換したもの。
このチェックリストで品質を確認してから Coder に委譲する。

---

## 必須チェック項目

### 1. 基本構造

- [ ] 目的が1文で明記されている
- [ ] アーキテクチャ概要が2-3文で説明されている
- [ ] 技術スタックが列挙されている
- [ ] タスク一覧がある

### 2. タスク粒度

- [ ] 各タスクは2-5分で完了する粒度か
- [ ] 30分以上かかるタスクがないか
- [ ] 1タスク = 1コミットの粒度になっているか

**NG例**:
```markdown
### Task 1: ユーザー認証機能の実装
ログイン、ログアウト、パスワードリセットを実装
```

**OK例**:
```markdown
### Task 1: ユーザーモデルの作成
### Task 2: パスワードハッシュ関数の実装
### Task 3: ログインエンドポイントの実装
...
```

### 3. 具体性

- [ ] ファイルパスが正確に記載されている
- [ ] 変更対象ファイルに行番号がある（既存ファイルの場合）
- [ ] テストファイルパスが記載されている
- [ ] 具体的なコード例がある

**NG例**:
```markdown
適切なバリデーションを追加してください
```

**OK例**:
```markdown
**Step 3: バリデーション追加**
```typescript
function validateEmail(email: string): boolean {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
}
```
```

### 4. TDD サイクル

- [ ] 各タスクに Step 1-5 が明記されている
  - [ ] Step 1: 失敗するテストを書く
  - [ ] Step 2: テスト失敗を確認
  - [ ] Step 3: 最小限の実装
  - [ ] Step 4: テスト成功を確認
  - [ ] Step 5: コミット
- [ ] テストコードの例がある
- [ ] 実行コマンドが記載されている
- [ ] 期待する結果（FAIL/PASS）が記載されている

### 5. 設計準拠

- [ ] 設計書への参照がある
- [ ] 設計書にない機能を追加していないか（YAGNI）
- [ ] 設計書の仕様と矛盾していないか
- [ ] API 設計との整合性が取れているか
- [ ] データモデル設計との整合性が取れているか

### 6. 依存関係

- [ ] タスクの順序が依存関係を考慮しているか
- [ ] 前のタスクの成果物を後のタスクが参照する構造か
- [ ] 並列実行可能なタスクが明示されているか（あれば）

---

## 推奨チェック項目

### エッジケース

- [ ] 境界値テストのタスクがあるか
- [ ] エラーハンドリングのタスクがあるか
- [ ] null/undefined ケースのタスクがあるか

### テスト網羅性

- [ ] 正常系テストがあるか
- [ ] 異常系テストがあるか
- [ ] バリデーションテストがあるか

---

## PM の確認プロセス

```
1. App-Architect から実装計画書を受け取る
2. このチェックリストで確認
3. 不足があれば App-Architect に差し戻し
4. チェック完了後、Coder に委譲
```

### 差し戻し例

```markdown
実装計画書に以下の問題があります：

- [ ] Task 3 の粒度が大きすぎる（30分以上かかりそう）
  → 3-4タスクに分割してください
- [ ] Task 5 に具体的なコード例がない
  → テストコードと実装コードの例を追加してください
- [ ] 設計書にないバリデーション機能が含まれている（YAGNI違反）
  → 削除してください
```

---

## チェック完了時のアクション

チェック完了後、PM は以下を行う：

1. `.claude-state/tasks.json` にタスクを登録
2. 各タスクを個別に Coder に委譲（Fresh Context）
3. タスク完了ごとに進捗を更新
