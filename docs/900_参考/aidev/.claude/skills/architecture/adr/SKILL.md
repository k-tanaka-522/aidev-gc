# adr

Architecture Decision Records（アーキテクチャ決定記録）。

## 用途

重要な技術的意思決定を記録し、「なぜそう決めたか」を残す。

## 使用Agent

- Architect (AppArchitect, InfraArchitect)

## 知識・手法

### ADRテンプレート

```markdown
# ADR-{番号}: {タイトル}

## ステータス

提案 / 承認 / 却下 / 廃止

## コンテキスト

{意思決定が必要になった背景・状況}

## 決定

{何を決めたか}

## 理由

{なぜその決定をしたか}

## 検討した代替案

### 代替案1: {名前}
- メリット: ...
- デメリット: ...
- 不採用理由: ...

### 代替案2: {名前}
- メリット: ...
- デメリット: ...
- 不採用理由: ...

## 影響

{この決定による影響・トレードオフ}

## 参照

- {関連するADR、ドキュメント、外部リンク}
```

### ADR例

```markdown
# ADR-001: 認証方式の選択

## ステータス

承認

## コンテキスト

ECサイトのユーザー認証方式を決定する必要がある。
将来的にマイクロサービス化を検討している。

## 決定

JWTによるステートレス認証を採用する。

## 理由

1. ステートレスでスケールしやすい
2. マイクロサービス間で認証情報を共有しやすい
3. セッションストアが不要

## 検討した代替案

### 代替案1: Cookieセッション
- メリット: 実装がシンプル、サーバー側で無効化可能
- デメリット: セッションストアが必要、スケール時に課題
- 不採用理由: 将来のマイクロサービス化で課題

### 代替案2: OAuth2 + OIDC
- メリット: 外部IdP連携可能、標準準拠
- デメリット: 初期実装コストが高い
- 不採用理由: 現時点では過剰

## 影響

- トークンの有効期限管理が必要
- リフレッシュトークンの実装が必要
- トークン漏洩時の対応手順が必要
```

## ファイル配置

```
└── 03_アプリケーション設計/
    └── 90_ADR/
        ├── README.md
        ├── ADR-001_認証方式.md
        ├── ADR-002_データベース選択.md
        └── ...
```

## 命名規則

- `ADR-{連番3桁}_{短い説明}.md`
- 例: `ADR-001_認証方式.md`

## decisions.json との連携

ADRで決定した内容は `.claude-state/decisions.json` にも記録:

```json
{
  "auth-method": {
    "decision": "JWT",
    "reason": "ステートレスでスケールしやすい",
    "alternatives": ["Session", "OAuth2"],
    "decidedAt": "2025-01-11",
    "decidedBy": "Architect",
    "adr": "docs/03_アプリケーション設計/90_ADR/ADR-001_認証方式.md"
  }
}
```
