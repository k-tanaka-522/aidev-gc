# コードレビュースキル（2段階レビュー）

## 概要

アプリケーションコード（`src/`）の2段階レビューを実施。

**重要**: Stage 1（Spec Compliance）が通らないと Stage 2（Code Quality）に進まない。

---

## 2段階レビューの流れ

```
実装完了
  ↓
Stage 1: Spec Compliance Review（仕様準拠確認）
  - 実装計画書の仕様を満たしているか
  - 足りない機能はないか
  - 余計な機能はないか（YAGNI）
  ↓
  NG → 修正 → Stage 1 再レビュー
  ↓
  OK
  ↓
Stage 2: Code Quality Review（コード品質確認）
  - コードの可読性
  - テストの網羅性
  - 技術標準への準拠
  ↓
  NG → 修正 → Stage 2 再レビュー
  ↓
  OK → タスク完了
```

---

## Stage 1: Spec Compliance Review

### レビュー観点

| 観点 | チェック内容 |
|------|-------------|
| **仕様準拠** | 実装計画書のタスク要件を満たしているか |
| **機能不足** | 必要な機能が欠けていないか |
| **機能過剰** | 実装計画書にない機能を追加していないか（YAGNI違反） |
| **API整合** | APIの入出力が設計と一致しているか |
| **データモデル** | データモデルが設計と一致しているか |

### 出力形式

```markdown
## Stage 1: Spec Compliance Review

### 基本情報
- 対象: {ファイルパス}
- 実装計画書: {実装計画書パス}
- タスク: Task {N}

### チェック結果

| 観点 | 状態 | 詳細 |
|------|------|------|
| 仕様準拠 | ✅/❌ | {詳細} |
| 機能不足 | ✅/❌ | {詳細} |
| 機能過剰 | ✅/❌ | {詳細} |
| API整合 | ✅/❌ | {詳細} |
| データモデル | ✅/❌ | {詳細} |

### 結果
- **PASS**: Stage 2 に進む
- **FAIL**: 修正が必要

### 修正が必要な点（FAILの場合）
- 問題: {具体的な問題}
- 期待: {実装計画書の記載内容}
- 実際: {実装内容}
```

---

## Stage 2: Code Quality Review

**前提**: Stage 1 が PASS していること

### レビュー観点

| 観点 | チェック内容 |
|------|-------------|
| **TDD準拠** | テスト→実装の順序で書かれているか |
| **テスト網羅性** | エッジケースがテストされているか |
| **可読性** | コードが読みやすいか |
| **技術標準** | 技術標準に準拠しているか |
| **セキュリティ** | セキュリティ上の問題がないか |

### 出力形式

```markdown
## Stage 2: Code Quality Review

### 基本情報
- 対象: {ファイルパス}
- Stage 1: PASS（{日時}）

### チェック結果

| 観点 | 状態 | 詳細 |
|------|------|------|
| TDD準拠 | ✅/❌ | {詳細} |
| テスト網羅性 | ✅/❌ | {詳細} |
| 可読性 | ✅/❌ | {詳細} |
| 技術標準 | ✅/❌ | {詳細} |
| セキュリティ | ✅/❌ | {詳細} |

### 結果
- **APPROVED**: タスク完了
- **APPROVED_WITH_COMMENTS**: 軽微な指摘あり、修正推奨
- **REJECTED**: 修正が必要

### 良い点
- {良い点}

### 改善が必要な点（REJECTED/APPROVED_WITH_COMMENTSの場合）
- 箇所: {ファイル:行番号}
- 問題: {具体的な問題}
- 提案: {改善案}
```

---

## レビュアー

| Stage | レビュアー | 責務 |
|-------|-----------|------|
| Stage 1 | QA または App-Architect | 仕様準拠確認 |
| Stage 2 | QA | コード品質確認 |

---

## 重要なルール

1. **Stage 1 が通らないと Stage 2 に進まない**
   - 「仕様通りだが品質が低い」より「仕様と違う」方が問題
   - 仕様準拠を先に確認することで、無駄な品質改善を防ぐ

2. **FAIL の場合は必ず再レビュー**
   - 修正後、同じ Stage から再レビュー
   - 「今回は見逃す」はNG

3. **YAGNI を厳格に適用**
   - 実装計画書にない機能は削除させる
   - 「ついでに」の改善もNG
