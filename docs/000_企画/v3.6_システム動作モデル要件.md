## 2. ルーティング設計

### 2.1 3入力モデル

オーケストレーターのルーティングは以下3つの入力を複合的に判断する。

```
ルーティング = f( ユーザー発言, 現在フェーズ, 曖昧さ解消 )
```

**なぜ3入力が必要か：**
同じ「見積を直して」という発言でも、Phase 1なら概算修正、Phase 3なら詳細見積の修正を意味する。発言だけでは正しくルーティングできない。

### 2.2 ルーティングの2モード

**Mode 1: ユーザー意図ルーティング**
ユーザーの発話を起点に最初のエージェントを選ぶ。（現行のキーワードルーティングを継承）

**Mode 2: ワークフロー遷移ルーティング**
エージェント完了後、オーケストレーターが会話履歴から状態を読み取り、次のステップを自動決定する。ユーザー発話を待たない。

```
[ユーザー]「要件定義して」
    ↓ Mode 1
[orchestrator] → @infra-requirements 起動
    ↓ 完了を受け取る
[orchestrator] → QA_LOG に積まれた不明点を確認
    ↓ 不明点あり
[orchestrator] → 「QAが X 件あります。次の定例で確認してください」と通知
    ↓ Mode 2（自動）
[orchestrator] → 次タスクへ継続
```

### 2.3 曖昧さ解消（オーケストレーター自身が実施）

発言の意図が現在フェーズと合致しない場合、1〜2問で確認する。

```
ユーザー「見積直して」（Phase 3 設計中）
  → 「概算見積の修正ですか？詳細見積の修正ですか？」
  → 回答後にルーティング
```

確認は最小限（1〜2問）。深いヒアリングは hearing-agent が担当。

### 2.4 フェーズ × 発言 の解釈マトリクス（主要パターン）

| 発言 | Phase 1 | Phase 2 | Phase 3〜4 |
|------|---------|---------|-----------|
| 「見積直して」 | 概算見積修正 | 詳細見積修正 | コスト再試算 |
| 「設計して」 | 提案アーキ概要 | 要件定義書参照して設計 | 詳細設計書作成 |
| 「確認して」 | QA票を提示 | QA票を提示 | QA票を提示 |
| 「進捗は？」 | WBSステータス | WBSステータス | WBSステータス |

### 2.5 CLAUDE.md に追加するワークフロー遷移ルール

```markdown
### ワークフロー遷移ルール（Mode 2）

エージェントから結果を受け取ったとき、以下のルールで次のステップを自動判断する。
ユーザーの次の発話を待たない。

| 完了したエージェント | 条件 | 次のアクション |
|-------------------|------|--------------|
| tailoring | qa_items あり | @hearing-agent を起動 |
| tailoring | qa_items なし | @infra-estimation を起動 |
| hearing-agent | 常に | 呼び出し元フェーズの次エージェントへ |
| 各設計エージェント | qa_items あり | @hearing-agent を起動後、次エージェントへ継続 |
| 各設計エージェント | next_action=review | ユーザーに「定例確認を推奨」と通知 |
| infra-qa | フェーズゲート判定完了 | @review-agent（モードB）を起動 |
| review-agent（承認） | 常に | project_state.yaml を更新、次フェーズへ |
| review-agent（差し戻し） | 常に | 指摘エージェントを再起動 |

### セッション開始時の必須手順

セッション開始時は必ず以下を実行してから応答する：
1. `outputs/80_PM/01_スケジュール/project_state.yaml` を読む
2. `outputs/80_PM/02_課題QA管理/QA_LOG.md` のオープン件数を確認
3. `outputs/80_PM/02_課題QA管理/ISSUE_LOG.md` の期限超過を確認
4. ユーザーに現状サマリを提示する
```

## 3. インタラクションモデル

### 3.1 基本原則：作業を止めない

エージェントは不明点があっても**作業を止めない**。仮定を置いて進め、不明点はQA_LOGに積む。

```
❌ 旧設計: 不明点 → ユーザーに即質問 → 回答待ちで停止
✅ 新設計: 不明点 → QA_LOGに積む + 仮定で継続 → 定例でまとめて確認
```

### 3.2 ヒューマンインタラクションのタイミング

人間が介入するタイミングは以下の3種類に限定する：

| タイミング | 種別 | 内容 | 主体 |
|----------|------|------|------|
| **定例会議** | 定期 | QA票・課題票の一括確認・決定 | PM + クライアント |
| **フェーズゲート** | マイルストーン | 成果物の正式承認・次フェーズGo/No-Go | クライアント管理職 |
| **緊急確認** | 臨時 | ブロッカー発生時のみ（作業が完全に止まる場合） | PM |

### 3.3 定例会議フロー

```
定例前（オーケストレーターが自動準備）:
  - QA_LOG のオープン件数・優先度を整理
  - ISSUE_LOG のオープン件数・期限超過を確認
  - 議題リストを生成

定例中（ユーザーが「定例確認して」と指示）:
  - @review-agent（モードA）が QA票・課題票を優先度順に提示
  - ユーザーが一問一答で回答
  - @review-agent が QA_LOG / ISSUE_LOG をリアルタイム更新

定例後（オーケストレーターが自動処理）:
  - 議事録を生成（決定事項・アクションアイテム）
  - 回答済みQAに対応するエージェントを再起動
  - ASSUMPTION_LOG の「作業仮定」を「確定前提」に昇格
```

### 3.4 フェーズゲートフロー（正式承認）

```
フェーズ完了条件が満たされたとき:
  1. @infra-qa がフェーズゲート判定を実施
  2. @review-agent（モードB）が成果物サマリ + 判定結果を提示
  3. ユーザーが「承認」または「差し戻し」を入力
     - 承認: project_state.yaml 更新 + 議事録生成 + 次フェーズへ
     - 差し戻し: 指摘をISSUE_LOGに追加 + 対象エージェントを再起動
  4. 議事録を生成（承認記録・承認者・日時）
```

# hearing-agent

## 役割

呼び出し元エージェントから不明点リストを受け取り、
QA_LOG.md と ASSUMPTION_LOG.md に記録する。
作業は止めない。ユーザーへの質問は行わない。

## 起動タイミング

- tailoring 完了後（案件プロファイルの不明点収集）
- 各設計エージェント完了後（設計上の不明点収集）
- オーケストレーターが qa_items を検出したとき（自動起動）

## 処理手順

1. 入力（qa_items）を受け取る
2. QA_LOG.md を読む
3. 各 qa_item を以下の形式で QA_LOG.md に追記する：
   - 質問内容、対象エージェント、作業継続用の仮定、優先度、ステータス=未回答
4. ASSUMPTION_LOG.md の「作業仮定」セクションに追記する
5. 完了サマリを返す（QA追加件数、優先度[高]件数）

## 出力

「QA X 件を積みました。優先度[高]が Y 件、[中]が Z 件あります。
次の定例会議での確認を推奨します。」

## 制約

- ユーザーへの質問は行わない
- 回答を待たない
- QA_LOG への追記が完了した時点で処理終了
```

### 4.2 review-agent AGENT.md

```markdown
---
name: review-agent
description: 定例会議の進行（モードA）とフェーズゲートの承認取得（モードB）を担当する。
  QA票・課題票の一括確認、議事録生成、ASSUMPTION_LOG更新を行う。
---

# review-agent

## 役割

定例会議の司会進行と、フェーズゲートでの正式承認取得を担当する。

## モードA: 定例確認モード

**起動条件:** ユーザーが「定例確認して」「QA確認して」と指示したとき

**処理手順:**
1. QA_LOG.md を読み、オープン項目を優先度順に整理する
2. ISSUE_LOG.md を読み、期限超過・高優先度を確認する
3. 議題リストを提示する（件数・概要）
4. QA票を1件ずつ提示し、ユーザーの回答を受け取る
5. 回答を QA_LOG.md に記録（ステータス=回答済）
6. ASSUMPTION_LOG.md を更新（作業仮定→確定前提）
7. 議事録を生成して `outputs/80_PM/03_議事録/YYYYMMDD_定例_議事録.md` に保存
8. 影響を受けるエージェントリストを出力する

**出力（オーケストレーターへ）:**
```yaml
status: completed
decisions_made: N
affected_agents:
  - infra-network  # Q-003の回答によりNW設計を更新
  - infra-security # Q-007の回答によりIAM設計を更新
minutes_file: outputs/80_PM/03_議事録/20260415_定例_議事録.md
```

## モードB: フェーズゲートモード

**起動条件:** infra-qa がフェーズゲート判定を完了したとき（オーケストレーターが自動起動）

**処理手順:**
1. infra-qa の判定結果を受け取る
2. 成果物一覧・品質スコア・未解決QA数をサマリとして提示する
3. ユーザーに承認/差し戻しを求める
4. 承認の場合:
   - `outputs/80_PM/01_スケジュール/project_state.yaml` を更新
   - 議事録を生成（承認記録・日時）
5. 差し戻しの場合:
   - 指摘内容を ISSUE_LOG.md に追加
   - 対象エージェントリストを出力

## レビュー主体の識別

| フェーズ1（コンサル単独） | フェーズ2（PM×クライアント並走） |
|------------------------|-------------------------------|
| ユーザーが全レビューを兼任 | 定例=クライアントIT担当が確認、フェーズゲート=管理職が承認 |
```

## 6. エージェント間インターフェース定義

### 6.1 標準出力フォーマット

各エージェントはメッセージの末尾に以下のYAMLブロックを含める：

```yaml
# AGENT_OUTPUT
status: completed | partial | blocked
output_files:
  - path: outputs/xxx/xxx.md
next_action: hearing | review | continue | escalate
qa_items:
  - question: "質問内容"
    assumption: "作業継続用の仮定"
    priority: high | medium | low
issue_items:
  - content: "課題内容"
    type: risk | blocker | change_request
    priority: high | medium | low
```

### 6.2 オーケストレーターの処理

```
AGENT_OUTPUT を受け取る
  ↓
qa_items があれば → @hearing-agent を起動（QA_LOG追記）
issue_items があれば → ISSUE_LOG に直接追記
  ↓
next_action を判断:
  hearing  → hearing-agent 完了後に次エージェントへ
  review   → ユーザーに「定例確認を推奨」と通知
  continue → 次エージェントを自動起動（Mode 2）
  escalate → ユーザーに緊急確認を求める
```

| レビュー種別 | 主体 | タイミング | 記録 |

## 8. gc-document-generation-standards スキル（更新）

### 8.1 基本方針

エージェントはMDで内容を生成する。形式変換はスキルが担当。エージェントは変換を意識しない。

### 8.2 成果物フォーマット定義

| 成果物 | 一次生成 | 納品形式 | 変換方法 |
|-------|---------|---------|---------|
| 見積書（内部用） | .md | .md | 変換不要 |
| 見積書（顧客提出用） | .md | .xlsx | Python（openpyxl） |
| WBS | .md | .xlsx | Python（openpyxl） |
| 課題管理票 | .md | .xlsx | Python（openpyxl） |
| 提案書 | .md | .pdf / .pptx | pandoc（pdf）/ Python（python-pptx） |
| 報告書（フェーズゲート） | .md | .pptx | Python（python-pptx） |
| 進捗報告 | .md | .pptx | Python（python-pptx） |
| 各種設計書（内部用） | .md | .md | 変換不要 |
| 各種設計書（納品物） | .md | .pdf / .docx | pandoc |
| 運用手順書 | .md | .docx | pandoc |
| 議事録 | .md | .md | 変換不要 |
| IaCコード | .tf/.yaml | そのまま | 変換不要 |

### 8.3 変換実行タイミング

- **フェーズゲート承認時**: 納品物対象の成果物を一括変換
- **手動指示時**: ユーザーが「提案書をPDFにして」と指示したとき

### 8.4 変換スクリプト（実装時に作成）

```
scripts/
  generate_xlsx.py   # WBS・見積書・課題管理票 → xlsx（openpyxl）
  generate_pptx.py   # 提案書・報告書・進捗報告 → pptx（python-pptx）
  generate_pdf.sh    # MD → PDF（pandoc使用）
  generate_docx.sh   # MD → docx（pandoc使用）
```

### 8.5 スキルの呼び出し方

```
オーケストレーター → フェーズゲート承認を検知
  ↓
「納品物変換を実行しますか？」とユーザーに確認
  ↓
承認 → scripts/ の変換スクリプトを順次実行
  ↓
変換済みファイルのパスを一覧表示
```
