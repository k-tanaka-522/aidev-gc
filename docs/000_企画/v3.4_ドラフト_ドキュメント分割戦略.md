# 設計書 v3.4 追加セクション（ドラフト）
# ドキュメント分割戦略 — 実装フェーズのコンテキスト最適化

**ステータス:** ドラフト
**目的:** v3.2 本体 + v3.3 ドラフト群を、Claude Code が実装時に効率よく消費できる構造に分割する
**解決する問題:** 2,000行超の単一ファイルでは、後半のスキル生成時に前半の仕様を忘却する

---

## 1. 問題分析

### 1-1. 現状のファイル構成

| ファイル | 行数 | 内容 |
|---------|------|------|
| v3.2 本体 | 1,054 | 全体設計（22エージェント + 33スキル + 97アウトプット + オーケストレーション） |
| v3.3 見積プロセス | ~300 | Step 1-4 + 3スキル追加 |
| v3.3 成果物/IaC | ~400 | メタデータ + 5W1H + Terraform/CFn/CDK + 4スキル追加 |
| v3.3 残ギャップ（予定） | ~300 | 移行/手戻り等 |
| **合計** | **~2,050** | |

### 1-2. Claude Code の消費パターン

エージェント/スキルの `.md` ファイルを生成するとき、Claude Code が実際に必要とする情報:

```
エージェント X を生成する場合:
  必要: X の仕様（frontmatter、プロンプト、入出力定義）  ← ~50-80行
  必要: X が参照するスキル名一覧                        ← ~5行
  必要: 共通のfrontmatter規約                            ← ~20行
  不要: 他の21エージェントの詳細仕様                      ← ~1,000行が無駄

スキル Y を生成する場合:
  必要: Y の内容定義                                     ← ~100-300行
  必要: Y が他スキル/エージェントとどう関連するか        ← ~10行
  不要: フェーズ別プロセスフロー全体                      ← ~200行が無駄
  不要: オーケストレーション/ルーティング定義              ← ~200行が無駄
```

**結論:** 1ファイルに全て入れると、生成対象以外の情報がコンテキストの 80-90% を占め、品質が劣化する。

### 1-3. 忘却リスクの分類

| リスク | 発生条件 | 影響 |
|-------|---------|------|
| **エージェント間の整合性崩壊** | Agent A と Agent B を別セッションで生成し、共通の前提を忘れる | 入出力のIF不整合、スキル参照のズレ |
| **スキル内容のドリフト** | スキル生成時にメタデータスキーマの規約を忘れる | メタデータ形式の不統一 |
| **命名規則のブレ** | 30番目のスキル生成時に1番目の命名パターンを忘れる | ファイル名/変数名の不整合 |
| **依存関係の見落とし** | エージェントが参照すべきスキルを忘れる | frontmatter の skills フィールド欠損 |

## 2. 分割戦略：5レイヤー構造

### 2-1. 全体像

```
レイヤー 0: マスターインデックス（~150行）
  ├─ 全エージェント一覧（名前 + 1行説明 + 参照スキル）
  ├─ 全スキル一覧（名前 + 1行説明 + 使用エージェント）
  ├─ 依存関係グラフ
  ├─ 共通規約（命名、frontmatter、出力パス）
  └─ 各レイヤーファイルへのパス

レイヤー 1: エージェント仕様書（22ファイル、各50-100行）
  ├─ 1つのファイル = 1つのエージェントの完全仕様
  ├─ そのまま .claude/agents/xxx.md として使える内容
  └─ 生成時に「レイヤー0 + レイヤー1の対象ファイル」だけ読めばOK

レイヤー 2: スキル仕様書（~40ファイル、各100-500行）
  ├─ 1つのファイル = 1つのスキルの完全仕様
  ├─ そのまま .claude/skills/xxx/SKILL.md として使える内容
  └─ 生成時に「レイヤー0 + レイヤー2の対象ファイル」だけ読めばOK

レイヤー 3: 共有データ（参照用、変更頻度低い）
  ├─ 成果物メタデータレジストリ（97件のYAML）
  ├─ 標準WBSテンプレート（116タスク）
  ├─ 工数係数テーブル
  ├─ 5W1H設計書テンプレート集
  └─ IaC構造規約（Terraform/CFn/CDK）

レイヤー 4: オーケストレーション（1ファイル）
  ├─ CLAUDE.md テンプレート
  ├─ Hooks 定義
  ├─ Plugin.json
  └─ settings.json
```

### 2-2. 生成タスク別の読み込みパターン

| タスク | 読むファイル | 推定トークン |
|-------|------------|-------------|
| エージェント X を生成 | L0（インデックス）+ L1/X（エージェント仕様） | ~300行 ≈ 1.5K tok |
| スキル Y を生成 | L0（インデックス）+ L2/Y（スキル仕様） | ~400行 ≈ 2K tok |
| IaCスキルを生成 | L0 + L2/Y + L3/iac-conventions | ~600行 ≈ 3K tok |
| CLAUDE.md を生成 | L0 + L4（オーケストレーション） | ~300行 ≈ 1.5K tok |
| 全体整合性チェック | L0 のみ（依存グラフで検証） | ~150行 ≈ 0.8K tok |
| **対比: 現行1ファイル** | **v3.2全体** | **~2,000行 ≈ 10K tok** |

→ 読み込み量が **1/5〜1/10** に圧縮される。忘却リスクが大幅に低下。

## 5. レイヤー1: エージェント仕様書のフォーマット

各エージェント仕様ファイルは以下のフォーマットに従う。
これがそのまま `.claude/agents/xxx.md` になる。

```markdown
# .claude/agents/{agent-name}.md
---
name: {agent-name}
description: >
  {1-2行の説明}
model: {opus|sonnet}
tools: [{使用ツール}]
skills:
  - {skill-1}
  - {skill-2}
# 以下は該当する場合のみ
isolation: worktree        # 並行ファイル操作が必要な場合
background: true           # 長時間タスクの場合
# memory: project は設定不可（settings.json側で制御）
---

あなたは{役割}の専門エージェントです。

## コンテキスト
{このエージェントがプロジェクト全体のどこに位置するか、1-2段落}

## 入力
{何を受け取るか。ファイルパス or データ形式}

## 処理ステップ
1. {step-1}
2. {step-2}
...

## 出力 → outputs/{category}/
{生成するファイル一覧とフォーマット}

## 品質基準
{このエージェント固有の品質チェック項目}

## 禁止事項
- {やってはいけないこと}
```

### サイズ目標: 50-100行/エージェント

## 7. 生成ワークフロー

### 7-1. 逐次生成パターン（推奨）

Claude Code で実際にファイルを生成する手順:

```bash
# Step 1: マスターインデックスを先に作る（人間がレビュー）
> impl/00-index.md を読んで、全体の依存関係を確認して。

# Step 2: 依存関係の上流から順にエージェントを生成
> impl/00-index.md と impl/agents/tailoring.md を読んで、
> .claude/agents/tailoring.md を生成して。

# Step 3: エージェントが参照するスキルを生成
> impl/00-index.md と impl/skills/tailoring-decision-matrix.md を読んで、
> .claude/skills/tailoring-decision-matrix/SKILL.md を生成して。

# Step 4: 次のエージェントへ（新しいセッションでもOK）
> impl/00-index.md と impl/agents/infra-estimation.md を読んで、
> .claude/agents/infra-estimation.md を生成して。
```

**ポイント:**
- 毎回 `00-index.md`（150行）+ 対象ファイル（50-500行）だけ読む
- 合計 200-650行 ≈ 1-3K トークン。コンテキストの 5% 以下
- 残り 95% を「実際に高品質なコードを書く」ことに使える

### 7-2. バッチ生成パターン（Agent Teams）

関連するエージェント群を一括生成する場合:

```bash
# 設計系エージェント 6体を並行生成
> Agent Teams で以下を並行実行して:
> - teammate-1: impl/00-index.md + impl/agents/infra-network.md を読んで .claude/agents/infra-network.md を生成
> - teammate-2: impl/00-index.md + impl/agents/infra-security.md を読んで .claude/agents/infra-security.md を生成
> - teammate-3: impl/00-index.md + impl/agents/infra-monitoring.md を読んで .claude/agents/infra-monitoring.md を生成
```

**ポイント:**
- 各 teammate が読むのは 00-index + 自分の担当ファイルだけ
- 他の teammate の仕様を読む必要がない（依存はインデックスで解決済み）
- isolation: worktree で .claude/agents/ への書き込み衝突も防げる

### 7-3. 整合性検証パターン

全生成後のクロスチェック:

```bash
# 00-index.md の依存グラフと、実際に生成されたファイルを突合
> impl/00-index.md を読んで、.claude/agents/ と .claude/skills/ の全ファイルを
> リストアップして、以下を検証して:
> 1. インデックスに載っている全エージェント/スキルが生成されているか
> 2. 各エージェントの frontmatter.skills が実在するスキルを参照しているか
> 3. 各スキルの「使用エージェント」が実在するエージェントか
> 4. outputs/ ディレクトリのパスが全エージェント間で衝突していないか
```

→ これは 00-index.md（150行）+ ファイル一覧だけで実行可能。

```
                                       ・外部リソースの選定理由

impl/                                ← Claude Code が読む実装仕様（機械用）
                                       ・具体的な仕様のみ
                                       ・判断根拠や検討経緯は書かない
                                       ・「何を作るか」だけに集中
```

**原則:** 同じ情報を2箇所に書かない。
- 人間用ドキュメント → 「なぜこう設計したか」（Why）
- 実装仕様 → 「何をどう作るか」（What / How）

### 9-2. 「ファイル多すぎ問題」への対策

75ファイルは一見多いが:

1. **Claude Code は気にしない** — 毎回 2-3ファイルしか読まないので、総ファイル数は無関係
2. **人間のナビゲーション** — 00-index.md がディレクトリ。ここだけ見ればどこに何があるか分かる
3. **Git管理** — ファイル単位の差分が見やすくなる（「infra-network.md を変更した」が一目瞭然）
4. **レビュー効率** — エージェント単位でレビューできる。1054行の巨大ファイルを全部見なくていい
