# aidev-gc プラグイン設計 — 全体まとめ

**最終更新:** 2026/04/05
**目的:** これまでの設計ドラフト群がどういう関係で、今どこまで決まっていて、次に何をするのかを整理する

---

## 1. そもそも何を作っているか

**「aidev-gc」** = ガバメントクラウド（GC）のAWSインフラ案件を、Claude Code で提案から運用まで一気通貫でやるためのプラグイン。

中身は:
- エージェント（専門の担当者）が **23体**
- スキル（エージェントが参照するナレッジ集）が **42件**
- 成果物（設計書、見積書、IaCコードなど）が **104件**
- フェーズ（プロジェクトの進め方）が **9フェーズ**

### ③ v3.3 見積プロセス（ドラフト）
**ファイル:** `govcloud-infra-agent-design-v3.3-draft-estimation-process.md`（約300行）

**何を決めたか:**
- 案件が来たら最初にやる4ステップを詳細化
  1. 案件情報を10軸で構造化する（tailoring エージェントの強化）
  2. 標準WBSテンプレートから概算WBSを自動生成する（7フェーズ×116タスク）
  3. 工数を算出する（ボトムアップ + 類推法のクロスチェック）
  4. 見積書・提案書を用途別テンプレートで生成する
- 追加スキル3件: gc-project-profiling, gc-standard-wbs, gc-estimation-output-templates

### ④ v3.3 成果物/IaC構造（ドラフト）
**ファイル:** `govcloud-infra-agent-design-v3.3-draft-artifacts-iac.md`（約400行）

**何を決めたか:**
- **成果物メタデータ** — 104件の成果物それぞれに「何が書かれているべきか」をYAMLで定義。LLMが生成するときの品質チェックリストになる
- **設計書5W1Hテンプレート** — NW設計書やセキュリティ設計書の「章立てと各章に何を書くか」を定義
- **IaC構造規約** — Terraform / CloudFormation / CDK の3パターンそれぞれについて:
  - ディレクトリ構成（modules / stacks / environments の3層）
  - 命名規則
  - パラメーター化の方法
  - Policy as Code（tflint, checkov, cfn-guard, cdk-nag）
- **基本設計→詳細設計→IaCの連携フロー** — パラメーターシート（PARAM-001）が設計書とIaCコードの橋渡し役
- 追加スキル4件: gc-artifact-metadata, gc-design-document-template, gc-iac-structure-terraform, gc-iac-structure-cfn-cdk

### ⑤ v3.4 分割戦略（ドラフト）
**ファイル:** `govcloud-infra-agent-design-v3.4-draft-split-strategy.md`（約300行）

**何を決めたか:**
- **問題:** 全設計を1ファイル（2,000行超）に入れると、Claude Code が後半のスキル生成時に前半の仕様を忘れる
- **解決:** 5レイヤー構造に分割する

```
L0: マスターインデックス（150行） — 全体の依存関係マップ。毎回必ず読む唯一のファイル
L1: エージェント仕様（22ファイル）— 1ファイル = 1エージェント。そのまま .claude/agents/ に配置可能
L2: スキル仕様（42ファイル）    — 1ファイル = 1スキル。そのまま .claude/skills/ に配置可能
L3: 共有データ（8ファイル）     — WBSテンプレート、メタデータ、IaC規約など
L4: オーケストレーション（4ファイル）— CLAUDE.md, Hooks, Plugin定義
```

- **効果:** 生成時の読み込み量が 2,000行 → 200-650行（1/5〜1/10）に圧縮。忘却リスク激減
- **方針転換:** 今後の設計追加は統合ドキュメントに追記せず、分割後の個別ファイル（impl/）に直接書く

### ⑥ v3.5 要件定義・分岐フロー（ドラフト）
**ファイル:** `govcloud-infra-agent-design-v3.5-draft-requirements-flow.md`（約400行）

**何を決めたか:**
- **問題:** 要件定義フェーズが明示的に存在しなかった
- **解決:** RFP完成度に応じて3パターンに分岐するフローを設計

```
パターンA（最も多い）: 概算見積 → 受注 → 要件定義 → 詳細見積 → 設計
  → RFPが曖昧な中小自治体案件向け（全体の60-70%）

パターンB: 詳細見積 → 受注 → 設計（要件定義スキップ）
  → RFPが充実した公開入札案件向け（10-15%）

パターンC: 概算見積 → 要件定義フェーズだけ先に受注 → 要件定義 → 詳細見積 → 本体受注 → 設計
  → 大規模案件の2段階契約パターン（15-25%）
```

- tailoring エージェントが RFP を7項目でスコアリングして自動判定
- 新エージェント1件: **infra-requirements**（要件定義の支援・要件定義書の生成）
- 新スキル2件: gc-requirements-template, gc-nonfunctional-checklist
- フェーズを7→9に再構成（Phase 0: 入口 と Phase 2: 要件定義 を新設）
- WBSタスクが 116 → 132 に増加（要件定義タスク16件追加）
- 標準準拠案件の場合、GCテンプレート+ASP要件で要件の6-7割が自動的に埋まるため要件定義工数を40-50%に圧縮可能（未反映、次回更新で対応）

## 4. フェーズ構成（最新版）

```
Phase 0: 案件入口・プロファイリング
  └─ tailoring がRFP完成度を判定 → パターンA/B/Cに分岐

Phase 1: 提案・見積
  └─ パターンA,C → 概算見積
  └─ パターンB   → 詳細見積（一発で精度高い）

Phase 2: 要件定義 ★新設
  └─ パターンA   → 受注後に実施
  └─ パターンB   → スキップ（RFP=要件定義書）
  └─ パターンC   → 第1契約のメイン成果物

Phase 3: 詳細見積・計画
  └─ パターンA,C → 要件定義結果ベースで詳細見積
  └─ パターンB   → 計画のみ（見積はPhase 1で完了済み）

Phase 4: 設計            ← 旧Phase 3
Phase 5: 構築            ← 旧Phase 4
Phase 6: テスト          ← 旧Phase 5
Phase 7: 移行・本番切替  ← 旧Phase 6
Phase 8: 運用・保守      ← 旧Phase 7
```

## 6. 次のステップ

設計フェーズはほぼ完了。残りの未対応ギャップは、実装時に個別ファイルへ直接書き込む方針。

### 実装の進め方

```
Step 1: impl/00-index.md を作る
  ↓  （最重要。全体の依存関係マップ。150行。人間レビュー必須）
Step 2: impl/agents/ にエージェント仕様を23ファイル展開
  ↓  （v3.2 + v3.5 の内容を個別ファイルに分解）
Step 3: impl/skills/ にスキル仕様を42ファイル展開
  ↓  （v3.2 + v3.3 の内容を個別ファイルに分解）
Step 4: impl/shared/ に共有データを配置
  ↓  （WBSテンプレート、メタデータ、IaC規約等）
Step 5: impl/orchestration/ にCLAUDE.md等を配置
  ↓
Step 6: 整合性チェック（00-index vs 実ファイルの突合）
```

この順番で `impl/` ディレクトリに実装用ファイルを展開していけば、
Claude Code で1エージェント/1スキルずつ高品質に生成できる。
