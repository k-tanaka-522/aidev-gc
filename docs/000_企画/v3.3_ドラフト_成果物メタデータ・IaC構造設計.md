## パート1: 成果物メタデータ定義

### 1-1. 設計思想

97件のアウトプットそれぞれに「何が書かれているべきか」をメタデータとして定義する。
LLMがエージェントとして成果物を生成する際、このメタデータを参照することで
記載漏れ・構成のブレを防ぐ。

メタデータはスキル `gc-artifact-metadata` に集約し、
全エージェントが参照可能にする。

### 1-2. メタデータスキーマ

各成果物に以下のメタデータを定義する:

```yaml
artifact:
  id: "NW-001"                          # 一意識別子
  name: "ネットワーク設計書（VPC）"        # 日本語名
  phase: 3                               # 生成フェーズ
  owner_agent: "infra-network"           # 生成責任エージェント
  owner_role: "実装"                     # 担当ロール
  format: "markdown"                     # 出力形式（markdown / excel / docx / terraform / yaml）
  output_path: "outputs/04_設計/04-2_ネットワーク/"        # 出力先ディレクトリ

  # 入力（何を読んで作るか）
  inputs:
    - artifact_id: "PROF-001"            # 案件プロファイルシート
      required: true
    - artifact_id: "REQ-001"             # 要件定義書
      required: true
    - skill: "gc-network-patterns"       # 参照スキル
      required: true

  # 出力先（誰が使うか）
  consumers:
    - artifact_id: "SEC-001"             # セキュリティ設計書がSGルールを参照
    - artifact_id: "IAC-001"             # IaC設計書がVPC構成を参照
    - artifact_id: "MON-001"             # 監視設計書がNWメトリクスを参照

  # 記載必須要素（これが設計書の骨格になる）
  required_sections:
    - id: "overview"
      name: "概要"
      description: "設計の目的、スコープ、前提条件"
    - id: "architecture"
      name: "アーキテクチャ"
      description: "構成図、コンポーネント一覧、接続関係"
    - id: "parameters"
      name: "パラメータ一覧"
      description: "設定値の一覧表。環境別（dev/stg/prd）の差分を明示"
    - id: "security"
      name: "セキュリティ考慮"
      description: "この領域固有のセキュリティ対策"
    - id: "operations"
      name: "運用考慮"
      description: "監視項目、障害時の対応方針、変更手順"
    - id: "dependencies"
      name: "依存関係"
      description: "他の設計書との関係、前提となる決定事項"
    - id: "decisions"
      name: "設計判断記録（ADR）"
      description: "選択肢、比較、採用理由"
    - id: "iac_mapping"
      name: "IaCマッピング"
      description: "この設計がIaCのどのモジュール/リソースに対応するか"

  # 品質チェック項目
  quality_checks:
    - "全required_sectionsが記載されているか"
    - "パラメータ一覧にdev/stg/prdの値が揃っているか"
    - "依存先の成果物IDが実在するか"
    - "IaCマッピングが空でないか（Phase 3完了時点）"
    - "ADRに選択肢と理由が記録されているか"
```

# 設計書 5W1H テンプレート

## 共通ヘッダ（全設計書共通）

すべての設計書は以下のヘッダで始める:

### What（何を）
- 設計対象のコンポーネント/領域
- スコープ（対象に含むもの/含まないもの）
- 前提条件と制約

### Why（なぜ）
- この設計が必要な理由（要件からのトレース）
- 要件定義書の該当セクション参照
- 非機能要件標準v1.2の該当項目

### Who（誰が）
- 設計者（エージェント名 + 人間レビュー者）
- レビュー者
- 承認者

### When（いつ）
- 作成日 / 最終更新日
- 有効期限（次回レビュー日）
- 前提となる先行設計書の完成日

### Where（どこに）
- 適用環境（dev/stg/prd）
- AWSリージョン / アカウント
- 出力先パス

### How（どう）
- 実装方式（IaCツール: Terraform / CFn / CDK）
- IaCモジュールへのマッピング（iac_mapping）
- パラメータシートへの転記方法

## パート3: IaC構造設計

### 3-1. 設計思想：基本設計→詳細設計→IaC の写像

```
Phase 3 基本設計（設計書テンプレートの §1-6）
  │ What/Why/アーキテクチャ/セキュリティ方針
  │
  ▼
Phase 3 詳細設計（設計書テンプレートの §3 パラメータ + §8 IaCマッピング）
  │ 具体的な設定値、環境別パラメータ、リソース定義
  │ ★ ここが「詳細設計の構造 = IaC構造」になる
  │
  ▼
Phase 4 IaC実装
  │ 詳細設計のパラメータ → tfvars / parameters.json / cdk.context.json
  │ 詳細設計のリソース定義 → modules/ / stacks/ / constructs/
  │
  ▼
Phase 4 構築（terraform apply / cfn deploy / cdk deploy）
```

**核心的な設計原則:**
詳細設計書のパラメータ一覧表の「行」が、IaCのvariable/parameterの「行」に1対1で対応する。
詳細設計書のIaCマッピングテーブルが、moduleの構造を規定する。
この写像関係を崩さないことで、設計変更→IaC変更の追跡が可能になる。

### 3-2. IaCツール選定基準

```
| 基準 | Terraform | CloudFormation | CDK |
|------|-----------|---------------|-----|
| GCでの採用率 | ◎ 最多 | ○ AWS固有案件 | △ 開発者寄り |
| マルチCSP対応 | ◎ | × | △（CDK for Terraform） |
| モジュール再利用 | ◎ Registry/社内 | △ Nested Stacks | ○ Constructs |
| 学習コスト | 中 | 低 | 高（プログラミング必須） |
| 状態管理 | S3 backend | CloudFormation管理 | CloudFormation管理 |
| Policy as Code | OPA/Sentinel/tflint | cfn-guard | cfn-guard + cdk-nag |
| 推奨場面 | デフォルト選択 | CFn資産がある案件 | アプリチームと協業時 |
```

tailoringエージェントがCSPと案件特性に基づいてIaCツールを選択し、
対応するスキルを有効化する。

### 3層アーキテクチャの設計思想

```
modules/（部品）     → 単一責任。1モジュール = 1論理コンポーネント
  ↓ 組み合わせ
stacks/（構造体）    → 複数モジュールの組み合わせ。デプロイ単位
  ↓ パラメータ注入
environments/（環境） → パラメータ値のみ。コードは書かない
```

**なぜ3層か:**
- modules/ はチーム/案件を超えて再利用可能（社内モジュールレジストリ）
- stacks/ は案件固有のアーキテクチャ判断を反映
- environments/ はパラメータの差し替えだけで環境を増やせる

## 2. 命名規則

### リソース命名

```
{project}-{environment}-{component}-{identifier}

例:
  gc-tantosha-dev-vpc-main
  gc-tantosha-prd-rds-primary
  gc-tantosha-stg-sg-app
```

| 要素 | ルール | 例 |
|------|-------|---|
| project | プロジェクト略称（小文字、ハイフン区切り） | gc-tantosha |
| environment | dev / stg / prd | dev |
| component | リソース種別の略称 | vpc, subnet, sg, rds, ec2, s3, kms |
| identifier | 用途を示す識別子 | main, app, db, public, private |

### Terraform命名

```hcl
# リソース名: snake_case、目的を示す
resource "aws_vpc" "main" { }
resource "aws_subnet" "private_app" { }
resource "aws_security_group" "app_server" { }

# 変数名: snake_case、型と用途が分かる名前
variable "vpc_cidr" { }
variable "private_subnet_cidrs" { }
variable "db_instance_class" { }

# 出力名: snake_case、用途_型
output "vpc_id" { }
output "private_subnet_ids" { }
```

### 禁止事項

- `count` で論理的に異なるリソースを作らない → `for_each` を使う
- `any` 型を使わない → 明示的な型定義
- ハードコードされた値 → 必ず variable 化
- `*` のIAMポリシー → 最小権限原則

## 3. モジュール設計規約

### モジュールの構成ファイル（必須）

```
modules/{component}/
  ├── main.tf          # リソース定義
  ├── variables.tf     # 入力変数（全て型・説明・validation付き）
  ├── outputs.tf       # 出力値
  ├── versions.tf      # プロバイダーバージョン制約
  ├── locals.tf        # ローカル変数（計算値、タグ統合等）
  └── README.md        # 用途、入出力、使用例
```

### variables.tf のルール

```hcl
# すべてのvariableに必須:
# 1. type（明示的な型）
# 2. description（日本語OK、設計書の参照先を含む）
# 3. validation（可能な限り）
# 4. default は「環境によらない共通値」がある場合のみ

variable "vpc_cidr" {
  type        = string
  description = "VPCのCIDRブロック（設計書: NW-001 §3.2）"

  validation {
    condition     = can(cidrhost(var.vpc_cidr, 0))
    error_message = "有効なCIDR表記で指定してください"
  }
}

variable "common_tags" {
  type = map(string)
  description = "全リソースに付与する共通タグ"
  default = {}

  # 必須タグのチェックはlocals.tfで実施
}
```

### タグ戦略

```hcl
# locals.tf
locals {
  required_tags = {
    Project     = var.project_name
    Environment = var.environment
    Owner       = var.owner
    CostCenter  = var.cost_center
    ManagedBy   = "terraform"
    ISMAPScope  = var.ismap_scope  # ISMAP管理策の対象かどうか
  }
  tags = merge(local.required_tags, var.common_tags)
}
```

全リソースに `tags = local.tags` を付与。
tflint / cfn-guard でタグ漏れを検出。

## 4. パラメータ化戦略

### 設計書 → tfvars の変換ルール

```
設計書のパラメータ一覧表（§3）
  │
  │ 1. パラメータ名 → variable名（snake_case変換）
  │ 2. 型 → Terraform type
  │ 3. dev/stg/prd列 → 各環境のtfvars
  │ 4. validation列 → variable validation block
  │ 5. 設計書参照 → variable description
  │
  ▼
variables.tf + environments/{env}/terraform.tfvars
```

### 環境間で変わるもの / 変わらないもの

| 分類 | 例 | 管理方法 |
|------|---|---------|
| 環境で変わる | instance_type, vpc_cidr, replica数 | tfvars |
| 環境で変わらない | タグ戦略, SG基本ルール, KMS設定 | modules内のdefault |
| 秘密情報 | DBパスワード, APIキー | AWS Secrets Manager → data source |
| 動的な値 | AMI ID, AZ一覧 | data source で取得 |

### 秘密情報の扱い

```hcl
# ❌ 禁止: tfvarsに平文
db_password = "MyPassword123"

# ✅ 正解: Secrets Managerから取得
data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "${var.project_name}-${var.environment}-db-password"
}

resource "aws_db_instance" "main" {
  password = data.aws_secretsmanager_secret_version.db_password.secret_string
}
```

## 5. スタック設計（デプロイ順序）

### デプロイ順序グラフ

```
Level 0: foundation （Organizations, SCP, IAM基盤）
  ↓
Level 1: network （VPC, TGW, DirectConnect）
  ↓
Level 2: security （KMS, WAF, GuardDuty） + dns （Route53）
  ↓
Level 3: application （EC2/ECS, RDS, S3）
  ↓
Level 4: monitoring （CloudWatch, CloudTrail） + backup （AWS Backup）
```

各スタックは独立したstate fileを持つ。
スタック間のデータ受け渡しは `terraform_remote_state` data source または SSM Parameter Store。

### スタック間依存の管理

```hcl
# network スタックの outputs.tf
output "vpc_id" { value = module.vpc.vpc_id }
output "private_subnet_ids" { value = module.vpc.private_subnet_ids }

# application スタックの main.tf
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "gc-tantosha-tfstate"
    key    = "network/${var.environment}/terraform.tfstate"
    region = "ap-northeast-1"
  }
}

module "ec2" {
  source     = "../../modules/compute/ec2"
  vpc_id     = data.terraform_remote_state.network.outputs.vpc_id
  subnet_ids = data.terraform_remote_state.network.outputs.private_subnet_ids
}
```

### テンプレート構成ルール

```yaml
AWSTemplateFormatVersion: "2010-09-09"
Description: "[プロジェクト名] [コンポーネント] - [概要]（設計書: XX-001）"

# ★ パラメータ = 設計書のパラメータ一覧と1対1
Parameters:
  ProjectName:
    Type: String
    Description: "プロジェクト名（設計書: PROF-001）"
  Environment:
    Type: String
    AllowedValues: [dev, stg, prd]
  VpcCidr:
    Type: String
    Description: "VPCのCIDR（設計書: NW-001 §3.2）"
    AllowedPattern: "^(\\d{1,3}\\.){3}\\d{1,3}/\\d{1,2}$"

# ★ Mappings = 環境間で変わらない定数
Mappings:
  RegionMap:
    ap-northeast-1:
      AZ1: ap-northeast-1a
      AZ2: ap-northeast-1c

# ★ Resources = 設計書のアーキテクチャセクションと対応
Resources:
  MainVPC:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: !Ref VpcCidr
      Tags:
        - Key: Name
          Value: !Sub "${ProjectName}-${Environment}-vpc-main"
        - Key: Project
          Value: !Ref ProjectName
        - Key: Environment
          Value: !Ref Environment
        - Key: ManagedBy
          Value: cloudformation

# ★ Outputs = 他スタックへの受け渡し
Outputs:
  VpcId:
    Value: !Ref MainVPC
    Export:
      Name: !Sub "${ProjectName}-${Environment}-vpc-id"
```

### CFn固有の規約

| ルール | 理由 |
|--------|------|
| 1テンプレート = 1スタック = 1論理コンポーネント | blast radius制限 |
| Cross-Stack参照は `Fn::ImportValue` | Nested Stackは依存が強すぎる |
| DeletionPolicy: Retain をDB/S3に付与 | 誤削除防止 |
| パラメータの AllowedValues/AllowedPattern 必須 | 入力バリデーション |
| Description に設計書参照を必ず記載 | トレーサビリティ |
| cfn-lint + cfn-guard をCI必須 | 品質ゲート |
