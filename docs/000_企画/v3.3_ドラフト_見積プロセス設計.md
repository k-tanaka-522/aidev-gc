# GC案件プロファイリング知識ベース

## 自治体規模別の特性

### 小規模（人口5万以下）
- 既存環境: 自治体クラウド（共同利用）が多い
- GC移行の特徴: 共同利用グループ単位での移行が一般的
- 注意点: 専任IT人材不在のケースが多い。運用管理補助者への依存度が高い
- コスト傾向: イニシャル+121%増の先行事業データあり（共同利用の既存効率が高いため）

### 中規模（人口5-30万）
- 既存環境: DC（データセンター）+ 自治体クラウドの混在が多い
- GC移行の特徴: DC利用分のリフトが中心。段階的移行が多い
- 注意点: 複数ベンダーの既存契約が錯綜。移行順序の調整が重要
- コスト傾向: 案件による差が大きい

### 大規模（人口30万以上）
- 既存環境: DC単独利用が多い
- GC移行の特徴: フルスタック移行。専任チーム組成が可能
- 注意点: データ量が大きく移行期間が長い。並行運用期間の管理が重要
- コスト傾向: イニシャル+50%増（神戸市事例）、ランニングは最適化余地あり

## 移行方式別の工数係数

| 方式 | 係数 | 説明 | 典型的な適用場面 |
|------|------|------|---------------|
| リフト | 1.0x | 現行構成をそのままGCに移設 | 期限が迫っている、アプリ改修不可 |
| R1（リプラットフォーム） | 1.3x | OS/MW更新＋GC移設 | EOL対応と同時移行 |
| R2（リファクタリング） | 1.8x | アーキテクチャ変更＋GC移設 | マネージドサービス活用でコスト削減 |
| 新規構築 | 2.5x | ゼロからGC上に構築 | 標準準拠システムの刷新 |

※係数は「リフトの工数を1.0」とした場合の相対値。
　類似案件実績と先行事業データから導出。

## GC固有の追加タスク（従来のクラウド移行との差分）

1. GCAS利用申請（2-4週間の審査期間）
2. GCテンプレート適用判断（必須/推奨/任意の3層）
3. 運用管理補助者の選定・契約
4. デジタル庁への移行計画報告（調査票提出）
5. ISMAP管理策対応の証跡整備
6. LGWAN接続設計（機密性2の場合）
7. GC接続回線の調達（DirectConnect/LGCS）
8. ASPとの責任分界確定
9. 非機能要件標準v1.2チェックシート対応
10. 移行完了報告（デジタル庁への報告義務）

これらは従来のクラウド移行見積には含まれない「GC固有コスト」として
別途積算が必要。見積テンプレートでは明示的な行として用意する。

### 2-3. infra-estimation エージェントの WBS生成ロジック

```markdown
# infra-estimation WBS生成処理（追加部分）

## 入力
- 案件プロファイルシート（Step 1の出力）
- gc-standard-wbs スキル（全タスクテンプレート）

## WBS テーラリングロジック

案件プロファイルの10軸に基づいて、標準WBSから該当タスクを取捨選択する。

### 条件フィルタ

| 条件ラベル | 適用条件 |
|-----------|---------|
| 必須 | 全案件で実施 |
| 機密性2時 | セキュリティレベル = 機密性2 |
| 標準準拠時 | 標準準拠 = 標準準拠 or 混在 |
| マルチVPC時 | 対象システム数 >= 6 |
| Web公開時 | ネットワーク要件にインターネット公開が含まれる |
| 大規模時 | 自治体規模 = 大 or 対象システム数 >= 11 |
| DR設計時 | 非機能要件でRTO < 4h が要求される |
| ISMAP要時 | 全案件（GCはISMAP必須） |
| 推奨 | デフォルト含む。明示的に除外指示がある場合のみ除外 |
| 任意 | 顧客要望がある場合のみ含む |

### 工数レンジの調整

各タスクの工数目安（人日）に対して、以下の係数を掛ける:

1. 移行方式係数: リフト(1.0) / R1(1.3) / R2(1.8) / 新規(2.5)
2. 規模係数: 小(0.7) / 中(1.0) / 大(1.5) / 省庁(2.0)
3. 複雑度係数: 単純(0.8) / 標準(1.0) / 複雑(1.3)

計算式: タスク工数 = 基準工数 × 移行方式係数 × 規模係数 × 複雑度係数

3点見積:
- 楽観: タスク工数 × 0.7
- 標準: タスク工数 × 1.0
- 悲観: タスク工数 × 1.5

## 出力

outputs/01_提案見積/wbs-draft.md に以下を生成:

1. テーラリング済みWBS（該当タスクのみ、工数レンジ付き）
2. 除外タスク一覧（除外理由付き）
3. 工数サマリ（フェーズ別 × 楽観/標準/悲観）
4. 前提条件・確認事項（Step 1からの引継ぎ）
```

## Step 3: 工数算出

### 3-1. 工数算出の2方式クロスチェック

```markdown
# infra-estimation 工数算出処理

## 方式A: ボトムアップ積算

Step 2で生成した概算WBSの各タスク工数を積み上げる。

合計工数 = Σ(各タスクの標準工数)

フェーズ別集計:
- Phase 1: 提案・見積
- Phase 2: 計画
- Phase 3: 設計
- Phase 4: 構築
- Phase 5: テスト
- Phase 6: 移行
- Phase 7: 運用（月額 × 契約月数）

マネジメント工数（Phase横断）:
- PM工数 = 合計工数 × 0.15（15%）
- QA工数 = 合計工数 × 0.05（5%）
- リスクバッファ = 合計工数 × 0.10-0.20（10-20%、不明項目数に応じて）

## 方式B: 類推法

### GCインフラ案件の工数レンジ（参考値）

| 自治体規模 | リフト | R1 | R2 | 新規 |
|-----------|-------|-----|-----|------|
| 小規模（5万以下） | 15-25人月 | 20-35人月 | 30-50人月 | 40-70人月 |
| 中規模（5-30万） | 25-50人月 | 35-70人月 | 50-100人月 | 70-150人月 |
| 大規模（30万+） | 50-100人月 | 70-140人月 | 100-200人月 | 150-350人月 |

※対象システム数によりレンジ内で変動。
　1システムあたり追加5-15人月を目安に加算。
　上記は「インフラのみ」の工数。アプリ移行は別途。

### クロスチェック

方式A（ボトムアップ）と方式B（類推）の差が30%以上ある場合:
- 差異の原因を分析（タスク漏れ or 過大見積 or 案件特殊性）
- 統括ロールに判断を求める
- 不明項目が多い場合は方式Bを優先（ボトムアップは不確実性が高い）

## コスト算出

### 人件費

| 職種 | 単価目安(万円/人月) | 備考 |
|------|------------------|------|
| PM/PL | 80-120 | プロジェクト規模による |
| リードアーキテクト | 100-150 | GC経験者はプレミアム |
| インフラエンジニア | 60-90 | Terraform/AWS経験 |
| SRE | 70-100 | 運用フェーズ中心 |

※単価は顧客に直接提示しない内部参考値。
　見積書には人月数と合計金額のみ記載が一般的。

### AWS利用料

- AWS Pricing Calculator で算出
- VM+DBで85-90%のコストが決まる（先行事業データ）
- infra-cost エージェント / cost-analysis-mcp-server で算出支援
- RI/SP適用前と適用後の2パターンを提示

### GC固有コスト（別掲）

| 項目 | 概算 | 備考 |
|------|------|------|
| GC接続回線（DirectConnect） | 月額10-50万円 | 帯域による |
| LGWAN接続（LGCS） | 月額10-30万円 | J-LIS提供 |
| 運用管理補助者委託料 | 月額30-100万円 | 契約範囲による |
| デジタル庁調査票作成支援 | 5-15人日 | 初回のみ |

## 出力

outputs/01_提案見積/ に以下を生成:

1. estimation-summary.md — 工数サマリ（方式A/B/クロスチェック結果）
2. cost-breakdown.md — コスト内訳（人件費/AWS利用料/GC固有コスト）
3. assumptions.md — 前提条件・確認事項（Step 1からの引継ぎ + 見積上の仮定）
```
