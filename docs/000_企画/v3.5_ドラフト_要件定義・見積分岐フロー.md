# 設計書 v3.5 追加セクション（ドラフト）
# 要件定義プロセス + 見積分岐フロー

**ステータス:** ドラフト
**解決する問題:** 要件定義フェーズが明示的に定義されていない / RFP完成度による分岐が未設計
**追加エージェント:** 1件（infra-requirements）
**追加スキル:** 2件（gc-requirements-template, gc-nonfunctional-checklist）
**フェーズ構成変更:** Phase 1-3 を再構成

---

## 1. 問題：現行フェーズ構成のギャップ

### 1-1. 現行（v3.2）

```
Phase 1: 案件相談・提案（概算見積）
Phase 2: 受注・計画
Phase 3: 設計              ← 要件定義はどこ？
Phase 4: 構築
Phase 5: テスト
Phase 6: 移行・本番切替
Phase 7: 運用・保守
```

### 1-2. 問題点

1. **要件定義フェーズが不在** — IPA共通フレーム2013では「要件定義プロセス」（JIS X0160:2012 6.3）が独立プロセスとして定義されている
2. **RFP完成度による分岐がない** — RFPが曖昧な場合と詳細な場合で、見積精度もフローも全く違う
3. **2段階契約パターンが未対応** — 大規模案件で「要件定義フェーズだけ先に受注」するケースが考慮されていない
4. **非機能要件の深掘りタイミングが不明** — Phase 2の「2.13 非機能要件チェックシート初期記入」だけでは不十分

---

## 2. 解決：3パターン分岐フロー

### 2-1. パターン分岐の全体像

```
案件入口
  │
  ▼
[tailoring] 案件プロファイリング（10軸）
  │
  ▼
★ RFP完成度の判定 ← tailoring が自動判定
  │
  ├─── 完成度 HIGH（調達仕様書レベル）
  │      → パターンB: 詳細見積 → 受注 → 設計
  │
  ├─── 完成度 MID（RFPはあるが非機能要件が曖昧）
  │      → パターンA: 概算見積 → 受注 → 要件定義 → 詳細見積 → 設計
  │
  └─── 完成度 LOW（口頭メモ / 構想レベル）
         → パターンC: 概算見積 → 要件定義フェーズ受注 → 要件定義 → 詳細見積 → 本体受注 → 設計
```

### 2-2. RFP完成度の判定基準

tailoring エージェントの案件プロファイリング後に、以下のチェックリストで自動判定する。

```yaml
rfp_completeness_check:
  # HIGH（7/7 を満たす場合）
  high_criteria:
    - name: "システム一覧が明記されている"
      check: "対象システム名・数が具体的に列挙されているか"
    - name: "非機能要件が定量的に記載されている"
      check: "可用性(99.x%)、RTO/RPO、性能目標が数値で記載されているか"
    - name: "ネットワーク要件が具体的"
      check: "接続先、帯域、LGWAN要否が明記されているか"
    - name: "移行対象データが特定されている"
      check: "データ種別・量・移行方式の指定があるか"
    - name: "スケジュールが具体的"
      check: "マイルストーン or 期限が日付レベルで記載されているか"
    - name: "予算が提示されている"
      check: "概算予算 or 上限が明示されているか"
    - name: "セキュリティ要件が明確"
      check: "機密性レベル、ISMAP対応範囲、認証方式が記載されているか"

  # MID（3-6/7 を満たす場合）
  # LOW（0-2/7 を満たす場合）

  scoring:
    high: 7    # 全て満たす → パターンB
    mid: 3-6   # 部分的 → パターンA
    low: 0-2   # ほぼない → パターンC
```

### 2-3. パターン A: 概算見積 → 受注 → 要件定義 → 詳細見積 → 設計

**最も一般的なパターン。** 「GCに移行したい」という相談から始まるケース。

```
Phase 1: 案件相談・提案
  ├─ [tailoring] 案件プロファイリング → RFP完成度 = MID
  ├─ [infra-estimation] 概算WBS + 概算見積
  ├─ [infra-proposal] 提案書作成
  └─ 顧客提出・受注

Phase 1.5: 要件定義 ★新設
  ├─ [infra-requirements] 現行システム調査
  ├─ [infra-requirements] 非機能要件詳細化
  ├─ [infra-requirements] 移行対象の特定・優先度付け
  ├─ [infra-requirements] IF要件整理（ASP連携等）
  ├─ [infra-requirements] 要件定義書の生成
  └─ 顧客レビュー・合意

Phase 2: 詳細見積・計画
  ├─ [infra-estimation] 詳細WBS（要件定義結果ベース）
  ├─ [infra-estimation] 詳細見積（確定版）
  ├─ [pm-planning] プロジェクト計画
  └─ キックオフ

Phase 3: 設計
  └─ （既存のまま）
```

### 2-4. パターン B: 詳細見積 → 受注 → 設計

**RFPが充実しているケース。** 自治体の公開入札で調達仕様書がしっかり書かれている場合。

```
Phase 1: 案件相談・提案
  ├─ [tailoring] 案件プロファイリング → RFP完成度 = HIGH
  ├─ [infra-requirements] RFP → 要件定義書への変換 ★ RFPを構造化するだけ
  ├─ [infra-estimation] 詳細WBS + 詳細見積 ← 概算をスキップ
  ├─ [infra-proposal] 提案書作成
  └─ 顧客提出・受注

Phase 2: 計画
  ├─ [pm-planning] プロジェクト計画
  └─ キックオフ
  ※ 要件定義はスキップ（RFP = 要件定義書）
  ※ 詳細見積は Phase 1 で完了済み

Phase 3: 設計
  └─ （既存のまま）
```

### 2-5. パターン C: 要件定義フェーズ先行受注（2段階契約）

**大規模・高リスク案件。** まず「何を作るか」を明確にしてから本体を受注する。

```
【第1契約: 要件定義フェーズ】

Phase 0: 要件定義受注 ★新設
  ├─ [tailoring] 案件プロファイリング → RFP完成度 = LOW
  ├─ [infra-estimation] 要件定義フェーズのみの概算見積
  ├─ [infra-proposal] 要件定義フェーズの提案書
  └─ 要件定義フェーズの受注

Phase 0.5: 要件定義の実施
  ├─ [infra-requirements] 現行システム詳細調査
  ├─ [infra-requirements] 非機能要件の策定（顧客と共同）
  ├─ [infra-requirements] 移行対象のアセスメント
  ├─ [infra-requirements] IF要件の詳細化
  ├─ [infra-requirements] 要件定義書（完成版）
  ├─ [infra-estimation] 本体フェーズの詳細見積
  └─ 要件定義完了報告

【第2契約: 設計〜運用フェーズ】

Phase 1: 本体受注
  ├─ [infra-proposal] 本体フェーズの提案書
  └─ 本体受注

Phase 2-7: （既存のまま）
```

## 3. フェーズ番号の再構成

### 3-1. 統一フェーズ体系

3パターンすべてに対応する統一的なフェーズ番号体系:

```
Phase 0:  案件入口・プロファイリング     [全パターン共通]
Phase 1:  提案・概算見積                 [パターンA,C]  / 提案・詳細見積 [パターンB]
Phase 2:  要件定義                       [パターンA,C]  / スキップ [パターンB]
Phase 3:  詳細見積・計画                 [パターンA,C]  / 計画のみ [パターンB]
Phase 4:  設計                           [全パターン共通]  ← 旧Phase 3
Phase 5:  構築                           [全パターン共通]  ← 旧Phase 4
Phase 6:  テスト                         [全パターン共通]  ← 旧Phase 5
Phase 7:  移行・本番切替                 [全パターン共通]  ← 旧Phase 6
Phase 8:  運用・保守                     [全パターン共通]  ← 旧Phase 7
```

### 3-2. パターン別のフェーズ実行マップ

```
             Phase:  0    1    2    3    4    5    6    7    8
パターンA:           ●    ●    ●    ●    ●    ●    ●    ●    ●
パターンB:           ●    ●    ─    ●*   ●    ●    ●    ●    ●
パターンC:           ●    ●₁   ●    ●₂   ●    ●    ●    ●    ●

● = 実施
─ = スキップ
●* = 計画のみ（見積はPhase 1で完了）
●₁ = 第1契約の提案・見積
●₂ = 第2契約の提案・見積
```

### 3-3. WBS番号体系への影響

旧 Phase 1-7 の WBS番号は Phase 0-8 にリナンバリングが必要:

| 旧WBS# | 新WBS# | 内容 |
|--------|--------|------|
| — | 0.x | 案件入口・プロファイリング（新設） |
| 1.x | 1.x | 提案・見積（変更なし） |
| — | 2.x | 要件定義（新設） |
| 2.x | 3.x | 計画（旧Phase 2、見積部分は分離） |
| 3.x | 4.x | 設計（旧Phase 3） |
| 4.x | 5.x | 構築（旧Phase 4） |
| 5.x | 6.x | テスト（旧Phase 5） |
| 6.x | 7.x | 移行（旧Phase 6） |
| 7.x | 8.x | 運用（旧Phase 7） |

## 4. 新エージェント: infra-requirements

### 4-1. 責務の明確化

| エージェント | 責務 | 要件定義との関係 |
|------------|------|----------------|
| **tailoring** | 案件の構造化、エージェント/スキルの取捨選択 | 要件定義の「前」に動く。入力情報を整理するだけ |
| **infra-requirements** ★新規 | 顧客要件の詳細化・構造化、要件定義書の生成 | 要件定義そのものを担当 |
| **infra-estimation** | WBS生成、工数算出、見積書生成 | 要件定義の「後」に動く。要件を受けて見積もる |

### 4-2. エージェント仕様

```markdown
# .claude/agents/infra-requirements.md
---
name: infra-requirements
description: >
  GCインフラ案件の要件定義を支援する。
  現行システム調査、非機能要件の詳細化、移行対象の特定、
  IF要件の整理を行い、要件定義書を生成する。
model: opus
tools: [Read, Write, Grep, Glob, Edit]
skills:
  - gc-requirements-template
  - gc-nonfunctional-checklist
  - gc-network-patterns
  - gc-security-template
  - ismap-infra-controls
  - gc-project-profiling
---

あなたはGCインフラ案件の要件定義を支援する専門エージェントです。

## コンテキスト

要件定義は設計の前提条件を確定させるフェーズです。
案件プロファイルシート（tailoring の出力）を入力として受け取り、
顧客との対話を通じて要件を詳細化・構造化します。

## 動作モード

### モード1: フル要件定義（パターンA, C）

入力情報が不十分な場合、以下のステップで要件を詳細化する。

1. **現行システム調査**
   - 既存システムの構成情報を読み込み、構成図を生成
   - 既存のNW構成、セキュリティ設定、運用体制を把握
   - データ量・アクセスパターン・ピーク時負荷を調査
   - 出力: outputs/02_要件定義/current-system-analysis.md

2. **非機能要件の詳細化**
   - gc-nonfunctional-checklist スキルのテンプレートに沿って全項目を整理
   - 可用性（SLA/SLO）、性能（レスポンスタイム、スループット）、
     拡張性、セキュリティ、運用性、移行性の6カテゴリ
   - 顧客が未定義の項目には「GC推奨値」をデフォルト提案
   - 出力: outputs/02_要件定義/nonfunctional-requirements.md

3. **移行対象の特定と優先度付け**
   - 対象システム × 移行方式（リフト/R1/R2/新規）のマトリクス生成
   - 移行順序の提案（依存関係、リスク、ビジネスインパクトで判定）
   - データ移行の要件（量、方式、許容ダウンタイム）
   - 出力: outputs/02_要件定義/migration-scope.md

4. **IF要件の整理**
   - ASPとの連携IF（API仕様、データ連携頻度、認証方式）
   - 外部システム接続（LGWAN、インターネット、庁内LAN）
   - 他GCアカウントとの接続（共同利用グループ内）
   - 出力: outputs/02_要件定義/interface-requirements.md

5. **要件定義書の統合**
   - 上記1-4の出力を統合し、要件定義書（完成版）を生成
   - 未決事項リスト（TBD）を明記
   - 前提条件と制約条件を整理
   - 出力: outputs/02_要件定義/requirements-definition.md

### モード2: RFP変換（パターンB）

RFPが充実している場合、以下のステップでRFPを要件定義書に変換する。

1. **RFP構造化**
   - RFPの全文を読み込み、要件定義書のテンプレートにマッピング
   - RFPの記載がテンプレートのどの項目に対応するかを整理
   - 記載がない項目を「未記載項目」として抽出

2. **ギャップ補完**
   - RFPに記載がないがGC案件で必要な項目を自動検出
   - GC推奨値を仮設定し、「確認事項」として明記
   - 出力: outputs/02_要件定義/requirements-definition.md
     + outputs/02_要件定義/rfp-gap-list.md

### モード3: 要件確認（Phase 4 設計中のフィードバック）

設計フェーズ中に要件の不明点が見つかった場合に呼ばれる。

1. 不明点を受け取り、要件定義書の該当箇所を特定
2. 未決事項リストに追加
3. 確認が必要な質問を生成（顧客向け）
4. 出力: outputs/02_要件定義/clarification-requests.md

## 品質基準

- 要件定義書の全項目が「確定」「仮定」「未決（TBD）」のいずれかに分類されていること
- 非機能要件の6カテゴリ全てに記載があること（「該当なし」も可）
- 移行対象の全システムに移行方式が割り当てられていること
- IF要件の全外部接続先が列挙されていること

## 禁止事項

- 顧客の確認なしに要件を確定しない（「仮定」と明記する）
- 設計判断を要件定義書に書かない（「何を実現するか」のみ。「どう実現するか」は設計フェーズ）
- 非機能要件の数値を根拠なしに設定しない（GC推奨値 or 顧客指定のみ）
```

## 5. 新スキル

### 5-1. gc-requirements-template

```markdown
# .claude/skills/gc-requirements-template/SKILL.md
---
description: GCインフラ案件の要件定義書テンプレートと記載ガイド
---

# GCインフラ要件定義書テンプレート

## テンプレート構成

要件定義書は以下の章立てとする。

### 第1章: 案件概要
- 1.1 対象システム一覧
- 1.2 案件背景・目的
- 1.3 スコープ（対象/対象外の明示）
- 1.4 体制（顧客側・SIer側・運用管理補助者）
- 1.5 前提条件
- 1.6 制約条件（GC固有: GCAS審査、テンプレート適用、ISMAP準拠）

### 第2章: 機能要件（インフラ観点）
- 2.1 コンピュート要件（EC2/ECS/Lambda/サイジング基準）
- 2.2 ストレージ要件（S3/EFS/EBS/容量見込み）
- 2.3 データベース要件（RDS/Aurora/DynamoDB/データ量）
- 2.4 ネットワーク要件（接続先一覧、帯域、レイテンシ）
- 2.5 外部IF要件（ASP連携、他GCアカウント、庁内LAN）

### 第3章: 非機能要件
- 3.1 可用性（SLA/SLO、計画停止、冗長構成）
- 3.2 性能・拡張性（レスポンスタイム、スループット、スケーリング）
- 3.3 セキュリティ（機密性レベル、認証、暗号化、ISMAP対応）
- 3.4 運用性（監視、バックアップ、パッチ管理、障害対応）
- 3.5 移行性（移行方式、許容ダウンタイム、データ移行方式）
- 3.6 環境・エコロジー（省電力、CO2排出、PUE） ← 非機能要件標準v1.2対応

### 第4章: GC固有要件
- 4.1 GC利用方式（単独/共同、アカウント構成）
- 4.2 GCテンプレート適用範囲（必須/推奨/任意の判断結果）
- 4.3 LGWAN接続要件
- 4.4 運用管理補助者の要件
- 4.5 デジタル庁報告要件
- 4.6 標準準拠状況（20業務のどれが対象か）

### 第5章: 移行要件
- 5.1 移行対象システム × 移行方式マトリクス
- 5.2 移行スケジュール（マイルストーン）
- 5.3 データ移行要件（量・方式・検証方法）
- 5.4 並行運用期間の要件
- 5.5 切替方式（一括/段階/ブルーグリーン）
- 5.6 ロールバック要件

### 第6章: 未決事項・確認事項
- 6.1 未決事項一覧（TBD、期限、担当）
- 6.2 顧客確認事項一覧
- 6.3 前提条件のリスク

## 記載ルール

### 要件のステータス管理

全ての要件項目に以下のいずれかのステータスを付与する:

| ステータス | 意味 | 次のアクション |
|-----------|------|--------------|
| **確定** | 顧客と合意済み | なし |
| **仮定** | SIer側の仮定値。顧客未確認 | 顧客確認を依頼 |
| **未決(TBD)** | 情報不足で決められない | 確認事項リストに追加 |
| **対象外** | スコープ外と合意 | なし |

### 非機能要件の記載粒度

- 定量的に記載できるものは必ず数値で記載
  - 良い例: 「可用性 99.9%（月間ダウンタイム 43.8分以内）」
  - 悪い例: 「高可用性を実現する」
- 数値が未定の場合は「GC推奨値」をデフォルトとして仮設定
  - 例: 「可用性 99.9%【GC推奨値、顧客確認中】」
```

# GCインフラ非機能要件チェックリスト

## 参照元

## 1. 可用性

| # | 項目 | GC推奨値 | 選択肢 | 備考 |
|---|------|---------|--------|------|
| A-1 | サービス稼働率 | 99.9% | 99.0% / 99.5% / 99.9% / 99.95% / 99.99% | AWSリージョン SLAに依存 |
| A-2 | 計画停止の有無 | 月1回（夜間） | なし / 月1回 / 週1回 | パッチ適用タイミング |

## 2. 性能・拡張性

| # | 項目 | GC推奨値 | 選択肢 | 備考 |
|---|------|---------|--------|------|

## 6. tailoring エージェントの強化: RFP完成度判定

### 6-1. 追加する処理

```markdown
# tailoring.md（追加部分）

## RFP完成度判定機能

案件プロファイリング（10軸）の実施後、入力情報の完成度を判定する。

### 判定ロジック

入力情報を以下の7項目でチェックし、スコアリングする:

1. □ システム一覧が明記されている（対象システム名・数が具体的）
2. □ 非機能要件が定量的（可用性%、RTO/RPO、性能目標が数値）
3. □ ネットワーク要件が具体的（接続先、帯域、LGWAN要否）
4. □ 移行対象データが特定されている（種別・量・方式）
5. □ スケジュールが具体的（マイルストーンが日付レベル）
6. □ 予算が提示されている（概算予算 or 上限）
7. □ セキュリティ要件が明確（機密性レベル、ISMAP範囲、認証方式）

### スコアと推奨パターン

| スコア | 完成度 | 推奨パターン | 理由 |
|--------|--------|-------------|------|
| 7/7 | HIGH | パターンB（詳細見積→受注→設計） | RFP = 要件定義書。要件定義フェーズ不要 |
| 3-6/7 | MID | パターンA（概算→受注→要件定義→詳細見積→設計） | 不明項目の詳細化が必要 |
| 0-2/7 | LOW | パターンC（要件定義フェーズ先行受注） | 見積精度が出ない。要件定義から先にやるべき |

### 出力への追加

案件プロファイルシートに以下を追加:

```yaml
rfp_completeness:
  score: 5          # 7項目中のチェック数
  level: "MID"      # HIGH / MID / LOW
  recommended_pattern: "A"   # A / B / C
  unchecked_items:
    - "非機能要件が定量的でない（定性的な記載のみ）"
    - "移行対象データの詳細が不明"
  recommendation: >
    RFP完成度は MID です。概算見積で受注後、
    要件定義フェーズで非機能要件とデータ移行要件を詳細化することを推奨します。
```

## 7. infra-estimation エージェントの強化: 分岐対応

### 7-1. 見積モードの追加

```markdown
# infra-estimation.md（追加部分）

## 見積モード

### モード1: 概算見積（パターンA, C の Phase 1）

- 入力: 案件プロファイルシート（RFP完成度 MID/LOW）
- 処理: 標準WBSテンプレート × 概算係数
- 出力: 概算見積書（工数レンジ: 楽観/標準/悲観）
- 精度目標: ±30-50%

### モード2: 詳細見積（パターンB の Phase 1、パターンA,C の Phase 3）

- 入力: 要件定義書（確定版）
- 処理: 標準WBSテンプレート × 詳細係数 × タスク分解
- 出力: 詳細見積書（工数: 確定値 ± バッファ）
- 精度目標: ±10-20%

### モード3: 要件定義フェーズ見積（パターンC の Phase 0）

- 入力: 案件プロファイルシート（RFP完成度 LOW）
- 処理: 要件定義タスクのみをWBSから抽出して積算
- 出力: 要件定義フェーズのみの見積書
- 特記: 本体フェーズの概算も「レンジ」として添付

### モードの自動選択

案件プロファイルシートの rfp_completeness.recommended_pattern に基づいて
自動的にモードを選択する。統括ロールが明示的にモードを指定することもできる。
```

### 7-2. 見積精度と前提条件の明示

```markdown
## 見積書の必須記載事項

### 概算見積書（モード1）の場合

| セクション | 内容 |
|-----------|------|
| 見積条件 | RFP完成度スコア、未確定項目、仮定した前提条件 |
| 工数サマリ | フェーズ別 × 楽観/標準/悲観 の3点見積 |

| 変更管理 | 「要件変更が発生した場合は追加見積を実施します。」 |
