## 2. プラットフォーム機能マッピング

各Claude Code機能をGCインフラ案件のどのシーンで使うか。

### Subagents vs Agent Teams の使い分け

| 基準 | Subagents | Agent Teams |
|------|-----------|-------------|
| **通信** | 親に結果を返すのみ。相互通信なし | タスクリスト共有、直接メッセージ |
| **適用場面** | 独立した単一タスク（設計書1本生成等） | 複数領域の協調（NW↔セキュリティの整合等） |
| **トークンコスト** | 低（個別コンテキスト） | 高（3チームメイトで3-4倍） |
| **本設計での使い方** | Phase 1-2（提案/見積）、Phase 4（個別モジュール構築） | Phase 3（設計フェーズの並行協調）、Phase 5（テスト種別の並行実行） |

### /loop, /schedule の運用フェーズ活用

| スケジュール | タスク | エージェント |
|-------------|--------|------------|
| 毎日 9:00 | セキュリティアラートサマリ生成 | infra-monitoring |
| 毎日 22:00 | IaCドリフト検知（terraform plan） | infra-iac |
| 毎週月曜 | コスト週次レポート生成 | infra-cost |
| 毎月1日 | ISMAP管理策適合確認 | infra-security |
| 毎月1日 | SLA/SLO実績レポート生成 | infra-operations |

### Dispatch + Channels の CI/CD連携

```
CI/CDパイプライン
  │ terraform plan 完了
  │ Dispatch API呼出し
  ▼
Claude Code（infra-qa）
  │ planの差分をレビュー
  │ セキュリティポリシー適合チェック
  │ Channels経由でSlackに結果通知
  ▼
人間が承認 → terraform apply
```

### Plugin パッケージング

20体のエージェント + 31件のスキルを1つのPluginとして配布可能。
チーム内の全メンバーが `claude plugin install` で即座に利用開始。

## 3. ユースケースとロール定義

### 3-1. ロール

| ロール | 責任範囲 | 典型例 |
|---|---|---|
| **統括** | 全体設計方針、顧客折衝、品質保証、フェーズゲート判定 | PM/PMO、リードアーキテクト |
| **実装** | 詳細設計・構築・テスト実行、技術的深掘り | インフラエンジニア、SRE |

一人が兼務もあり。テーラリングエージェントが案件特性に応じて調整。

### 3-2. 案件の流れとエージェント起動タイミング

```
Phase 1 案件相談・提案
  統括: こんな案件あるんだけど → [tailoring] → [infra-proposal]
  統括→実装: 工数見積もりして → [infra-estimation] → 見積書（根拠付き）

Phase 2 受注・計画
  統括: 受注した、計画立てよう → [pm-planning] → WBS/体制/品質計画
  実装: 詳細見積確定 → [infra-estimation] → 詳細見積書
  統括: GC利用申請 → [infra-gc-environment] → GCAS手続き

Phase 3 設計 ← ★Agent Teamsで並行協調
  統括: 全体設計方針 → [infra-gc-environment] [infra-security]
  実装: 詳細設計（並行）→ Agent Teams {
    teammate-1: [infra-network]
    teammate-2: [infra-security]（実装部分）
    teammate-3: [infra-monitoring]
    → 共有タスクリストでIF整合を相互確認
  }
  実装: 移行設計 → [infra-migration]
  実装: 運用設計 → [infra-operations]

Phase 4 構築 ← ★Git Worktreesで並行開発
  実装: 環境構築 → [infra-gc-environment] [infra-iac]
  実装: IaCコード実装（並行）→ isolation: worktree で分離
  実装: CI/CDパイプライン → [pm-infra-cicd]
  ★ background: true で terraform plan をバックグラウンド実行

Phase 5 テスト ← ★Agent Teamsで並行テスト
  統括: テスト計画 → [infra-test]
  実装: テスト実行（並行）→ Agent Teams {
    teammate-1: 結合テスト
    teammate-2: 性能テスト
    teammate-3: セキュリティテスト
  }
  統括: 品質判定 → [pm-quality] [infra-qa]

Phase 6 移行・本番切替
  統括: Go/No-Go判定 → [infra-migration]
  実装: リハーサル・切替実施 → [infra-migration]
  ★ --remote でリモート実行、Channels で進捗通知

Phase 7 運用・保守 ← ★/loop で自動化
  実装: 定常運用 → [infra-operations]
  ★ /loop "daily at 9am" → セキュリティアラートサマリ
  ★ /loop "weekly on monday" → コストレポート
  ★ Dispatch → CI/CDからのIaCレビュー自動化
```

## 6. 変更オーケストレーションと早期検知

### 6-1. 設計思想：「抜け漏れは必ずある」前提

要件の抜け漏れはどのフェーズでも発覚し得る。
遅く発覚するほどコストが指数的に増大するため、2つの戦略を組み合わせる。

```
戦略A: 早期検知（予防）
  → 各フェーズ完了時と定期的に、抜け漏れを能動的に検知

戦略B: 変更オーケストレーション（対応）
  → 発覚した変更を統一フローで処理し、影響範囲を自動特定
```

### 6-2. 早期検知エージェント（infra-gap-detector）

```markdown
# .claude/agents/infra-gap-detector.md
---
name: infra-gap-detector
description: >
  要件・設計・IaC・テストの抜け漏れを各フェーズで能動的に検知する。
  フェーズゲート時に自動起動、または/loopで定期実行。
model: opus
tools: [Read, Grep, Glob]
skills:
  - gap-detection-patterns
  - phase-gate-criteria
background: true
---

あなたは抜け漏れ検知の専門エージェントです。
成果物間の網羅性を検証し、漏れている項目を報告します。

## 検知パターン

### Phase 2完了時（計画→設計のゲート）
- RFPの全要件がWBSのタスクにマッピングされているか
- 非機能要件（v1.2）の全項目に対応方針があるか
- ISMAP管理策のインフラ担当分が全て識別されているか

### Phase 3完了時（設計→構築のゲート）
- 要件トレーサビリティ: 全要件に対応する設計書セクションがあるか
- 設計書→IaCモジュール: 全設計項目のIaC化方針が決まっているか
- 設計書間の整合: NW設計のSGルールとセキュリティ設計のIAMポリシーが矛盾しないか
- 外部IF: アプリチームとのIF定義に未決事項が残っていないか
- 運用設計: 全インフラコンポーネントの監視/バックアップ/パッチ方針が定義されているか
- 移行設計: 全データ/環境の移行方式が決まっているか

### Phase 4完了時（構築→テストのゲート）
- IaCコードカバレッジ: 設計書の全項目がIaCで実装されているか
- terraform plan: 意図しないリソース差分がないか
- cfn-guard: セキュリティポリシー違反がないか
- 環境間差分: dev/stg/prdの意図しない構成差分がないか

### Phase 5完了時（テスト→移行のゲート）
- テストカバレッジ: 全要件に対応するテストケースが実行済みか
- 性能テスト: 非機能要件の性能目標を全て達成しているか
- セキュリティテスト: ISMAP管理策の全項目が検証済みか
- 移行リハーサル: 実施済みで結果がOKか

### 定期検知（/loop で設計・構築フェーズ中に週次実行）
- 新たに追加された要件/変更要求がWBS/設計書に反映されているか
- 課題管理表のオープン課題に設計への影響があるものがないか
- GCASガイド/テンプレートの更新が自環境に反映されているか
```

### 6-3. 影響分析エージェント（infra-impact-analysis）

```markdown
# .claude/agents/infra-impact-analysis.md
---
name: infra-impact-analysis
description: >
  変更要求や追加要件が来たとき、影響を受ける成果物・IaCコード・
  テストケースを横断的に特定し、対応計画を生成する。
model: opus
tools: [Read, Grep, Glob, Write]
skills:
  - impact-analysis-rules
  - estimation-methods
---

あなたは変更影響分析の専門エージェントです。

## 入力
- 変更要求の内容（自然言語）
- 現在のフェーズ

## 処理
1. 変更要求を構造化（対象領域、変更種別、影響範囲の仮説）
2. 成果物依存マップに基づき影響を受ける成果物を特定
3. IaCコードへの影響をgrep/解析で特定
4. テストケースへの影響を特定
5. 追加工数を概算
6. 対応方針（修正すべきエージェントと順序）を生成

## 成果物依存マップ
要件定義書
  ├→ 非機能要件チェックシート
  ├→ 各設計書（NW/セキュリティ/監視/バックアップ/IaC/運用/移行/コスト）
  │    ├→ IaCコード（modules/）
  │    ├→ テストケース（test/）
  │    └→ 運用手順書（operations/）
  ├→ WBS/見積書
  └→ ISMAP管理策対応表

## 出力 → outputs/90_品質管理/90-2_影響分析/
1. 影響分析報告書
   - 影響を受ける成果物一覧（ファイルパス付き）
   - 影響を受けるIaCモジュール一覧
   - 影響を受けるテストケース一覧
   - 追加工数概算
   - 対応優先度（今すぐ/次フェーズ/次リリース）
2. エージェント再起動指示
   - どのエージェントをどの順番で再起動するか
   - 各エージェントへの入力（変更内容の要約）
```

### 6-7. 発覚タイミング別の対応パターン

| 発覚タイミング | コスト影響 | 対応パターン |
|-------------|----------|------------|
| ① 設計中に気づく | 低 | 該当設計エージェントが自己修正。pm-reviewで確認 |
| ② 構築中に気づく | 中 | infra-impact-analysis → 設計へ部分的に戻る → IaC再実装 |
| ③ テストで発覚 | 中〜高 | infra-impact-analysis → 影響範囲に応じて設計/構築に戻る |
| ④ 顧客レビューで指摘 | 高 | pm-config-change → infra-impact-analysis → infra-estimation（追加見積）→ 全体再計画 |
| ⑤ 本番稼動後に判明 | 最高 | インシデント扱い → infra-operations → infra-impact-analysis → 緊急変更フロー |

**共通ルール:** どのタイミングでもinfra-impact-analysisを通す。
影響分析なしにエージェントを個別再起動しない（二次的な抜け漏れを防ぐ）。

## 7. フェーズ別プロセス詳細

※全7フェーズ×約100タスクのプロセス定義は別紙
（govcloud-infra-process-detail.md）を参照。
本セクションでは各フェーズの概要とClaude Code機能活用ポイントを記載。

### Phase 1: 案件相談・提案
- **tailoring** → **infra-proposal** → **infra-estimation**
- 1Mコンテキストを活かしてRFP全文を一括読込・分析
- memory: project でテーラリング結果をセッション横断で永続化

### Phase 2: 受注・計画
- **pm-planning** → **infra-estimation**（詳細）→ **infra-gc-environment**
- WBSベースのボトムアップ見積をinfra-estimationが実施
- GCAS利用申請の手続き支援

### Phase 3: 設計 ★Agent Teams活用フェーズ
- Agent Teamsで設計の並行協調:
  - Lead: 統括ロールが全体方針を指示
  - Teammate-1: infra-network（NW詳細設計）
  - Teammate-2: infra-security（セキュリティ実装設計）
  - Teammate-3: infra-monitoring（監視設計）
  - 共有タスクリストでIF整合を相互確認
- isolation: worktree で各teammateのIaCファイル衝突を防止
- **pm-review** が各設計書のレビューチェックリストを生成

### Phase 4: 構築 ★Git Worktrees + background活用
- infra-iacをisolation: worktreeで環境別に分離実行
- background: trueで長時間のterraform plan/applyをバックグラウンド化
- pm-infra-cicdがCI/CDパイプラインを構築
- PostToolUse hookでIaCバリデーション（cfn-lint/tflint）を自動実行

### Phase 5: テスト ★Agent Teams並行テスト
- Agent Teamsで3種テストを並行実行:
  - Teammate-1: 結合テスト
  - Teammate-2: 性能テスト
  - Teammate-3: セキュリティテスト
- infra-qaがテスト結果の横断品質チェック
- pm-qualityがフェーズゲート判定

### Phase 6: 移行・本番切替 ★--remote + Channels
- --remoteでリモートマシン上で移行実行
- Channelsで切替進捗をリアルタイム通知
- infra-migrationがGo/No-Go判定チェックリストを生成
- SubagentStop hookのlast_assistant_messageで判定結果を取得

### Phase 7: 運用・保守 ★/loop + Dispatch自動化
- /loopで定期タスクを自動化（日次監視、週次コスト、月次ISMAP）
- DispatchでCI/CDパイプラインからinfra-qaを自動呼出し
- memory: projectで運用ナレッジを蓄積・再利用

```markdown

あなたはオーケストレーターです。ユーザーの発話を理解し、

### 行動ルール

1. **成果物を自分で作らない**
   設計書、IaCコード、見積書、テスト計画、手順書などの

3. **複数エージェントの結果は統合・要約してよい**

4. **判断に迷ったら聞く**

#### 案件初期セットアップ（1回だけ）

### 委譲の判断基準

| 条件 | 対応 |
|------|------|
| 成果物の生成（設計書/コード/見積/手順書） | **必ず委譲** |
| 複数ファイルの読解・分析が必要 | **必ず委譲** |
| ドメイン固有の判断が必要 | **必ず委譲** |
| 1-2文で回答できる質問 | 直接回答OK |
| エージェントの使い方の説明 | 直接回答OK |
| 次に何をすべきかのガイド | 直接回答OK |

### 並行・逐次の判断基準

| 条件 | ディスパッチ方式 |
|------|----------------|
| 3つ以上の無関係タスク、共有状態なし | **並行**（Agent Teams） |
| タスク間に依存関係あり | **逐次**（順番に委譲） |
| 共有ファイル/状態あり | **逐次** |
| リサーチや分析（ファイル変更なし） | **バックグラウンド** |

### 変更発生時の統一フロー

追加要件や変更が発生したら、必ず以下のフローに従う:
1. @pm-config-change で変更要求を受付・分類
2. @infra-impact-analysis で影響範囲を特定
3. 統括ロールが承認判断（ユーザーに確認）
4. @infra-estimation で追加工数見積（必要な場合）
5. 影響を受けるエージェント群を再起動
6. @infra-qa で変更後の整合性チェック
7. @infra-gap-detector で新たな抜け漏れがないか確認

影響分析なしにエージェントを個別再起動しないこと。
```

## 13. 利用方法

### 13-1. 初期セットアップ

```bash
# Claude Code v2.1.88以上を確認
claude --version

# Agent Teams有効化
# settings.jsonに追加するか:
claude config set env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS 1

# Plugin経由でエージェント・スキルをインストール
claude plugin install govcloud-infra

# または手動で.claude/agents/, .claude/skills/に配置
```

### 13-2. 案件相談（Phase 1）

```bash
claude

> @tailoring docs/010_RFP/のRFPを分析して構成を最適化して。
> 統括ロール。自治体向けR1案件、ウォーターフォール。

> @infra-estimation 概算見積を作成して。類推法ベースで根拠もつけて。
```

### 13-3. 設計（Phase 3）— Agent Teams

```bash
> 設計フェーズ開始。Agent Teamsで以下の3チームメイトを生成して:
> - teammate-1: @infra-network でVPC/TGW設計
> - teammate-2: @infra-security でIAM/暗号化設計
> - teammate-3: @infra-monitoring で監視/ログ設計
> 共有タスクリストでインターフェース整合を確認しながら進めて。
```

### 13-4. 構築（Phase 4）— background

```bash
> @infra-iac VPCモジュールをTerraformで実装して。
> 完了したらbackgroundでterraform planを実行して。
```

### 13-5. 運用（Phase 7）— /loop

```bash
/loop "daily at 9am" @infra-monitoring セキュリティアラートのサマリを生成して outputs/07_運用/ に保存して
/loop "weekly on monday at 10am" @infra-cost 先週のクラウド利用料をanalyzeして週次レポートを生成して
```

### 13-6. CI/CD連携（Dispatch）

```bash
claude -p "@infra-qa iac/modules/ のterraform planの差分をレビューして。セキュリティポリシー違反がないか確認して。"
```

### 13-7. 突発的な追加要件への対応

```bash
# 顧客から「LGWAN接続が追加で必要になった」と連絡

> @infra-impact-analysis 以下の変更要求の影響を分析して:
> 「既存のインターネット接続に加えて、LGWAN閉域網接続が必要になった」
> 現在Phase 3（設計中）。影響を受ける成果物とIaCモジュール、
> 追加工数を報告して。

# → 影響分析報告書が生成される
# → 統括が承認

> @infra-estimation 影響分析結果に基づいて追加工数を正式に見積もって。

# → 承認後、影響を受けるエージェントを再起動
> Agent Teamsで以下を並行対応して:
> - @infra-network LGWAN接続の設計追加
> - @infra-security 閉域網向けのセキュリティ設計修正
> - @infra-iac DirectConnectモジュールの追加
> 完了後 @infra-gap-detector で抜け漏れチェック。
```

### 13-8. 定期的な抜け漏れ検知

```bash
# 設計フェーズ中に週次で自動チェック
/loop "weekly on friday at 17:00" @infra-gap-detector 今週の成果物変更をチェック。要件トレーサビリティの漏れ、設計書間の矛盾、未決事項を報告して。
```
