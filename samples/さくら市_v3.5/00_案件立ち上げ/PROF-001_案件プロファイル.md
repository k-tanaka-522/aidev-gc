## 4. 移行方式判定

### 4.1 判定根拠

**結論: R1（リプラットフォーミング）**

**理由:**
1. **現行：Heroku PaaS** → **移行先：AWS IaS（VPC + EC2/ECS + RDS）**
   - Heroku上のNode.js × 3 dyno を AWS 上の EC2/ECS コンテナに置き換え
   - 既存アプリケーションロジックはほぼそのまま活用（リフト相当）

2. **ただしアーキテクチャに調整あり（R1要件）**
   - Heroku Redis Premium-3 → AWS RDS for PostgreSQL （キャッシュは ElastiCache 検討）
   - Heroku 管理ストレージ → AWS S3 （既に使用中）
   - Heroku 監視（Datadog）→ CloudWatch + CloudTrail + GuardDuty

3. **GC・ISMAP対応で設計変更**
   - LGWAN接続の VPC 分離、DirectConnect 設定
   - KMS暗号化の導入、CloudTrail ログ保持 1年
   - IAM Role・ポリシーの ISMAP 認定構成に準じた設計

→ 既存ロジック活用＋アーキテクチャ調整 = **R1判定**

### 4.2 工数係数への影響

| 係数 | 値 | 根拠 |
|------|-----|------|
| 移行方式係数 | 1.3 | R1 は標準（1.0）より 30% 増（既存資産活用による短縮を相殺するアーキテクチャ調整） |

## 5. セキュリティレベル判定

### 5.1 判定: 高（ISMAP対応）

**根拠:**
- マイナンバー関連サービス → 個人番号保護法に準拠

## 6. ネットワーク複雑度判定

### 6.1 判定: 中程度

**構成要素:**

| 要素 | 複雑度 | 摘要 |
|------|--------|------|
| LGWAN接続 | 中 | 県庁経由で住基ネット接続。DirectConnect ＋ VPN バックアップ要求 |
| インターネット接続 | 低 | NAT Gateway 経由の単一経路 |
| VPC分割 | 中 | LGWAN専用VPC + インターネット専用VPC の 2VPC 構成（推奨） |
| DNS構成 | 中 | オンプレ（庁舎内 AD）+ GC（Route53）の並行運用 |

→ **中程度** （シンプルではないが、複雑（複数拠点、複数DirectConnect）でもない）

## 9. 案件リスク・前提条件

### 9.1 高リスク項目

| リスク | 影響 | 対策 |
|--------|------|------|
| **ユーザー側 PM・リソース確保遅延** | Phase 2 開始遅延（+2週間） | 契約時に顧客コミットメント確認、PM専任化要求 |
| **GCAS申請却下** | Phase 0 延長（+4週間） | CEP 要件事前確認、既登録企業での実施 |
| **既存システム複雑性（Heroku 運用情報不足）** | ネットワーク・DB設計遅延 | Phase 1 で詳細な現行調査タスク追加（+20人日） |
| **セキュリティ要件の追加変更** | Phase 6 修正工数増（+30人日） | Phase 4 設計審査時に ISMAP チェックリスト事前実施 |

### 9.2 前提条件

1. **顧客側体制**
   - PM 1名（専任、週4日以上）
   - ユーザー代表 3～5名（各部門、週1回ヒアリング参加）
   - セキュリティ責任者 1名

2. **既存システム資料の提供**
   - Heroku 運用ドキュメント（接続情報、スケーリング設定）
   - 現行 AD/LDAP 構成情報
   - セキュリティ・コンプライアンス方針書

3. **外部体制**
   - GCAS登録企業（提案企業）による申請主体
   - 県庁のネットワーク部門と LGWAN 接続の調整
