## 1. テスト概要・目的

### 1.1 背景

さくら市マイナンバーサービス基盤は、住民約12万人のマイナンバー（特定個人情報）を取り扱うシステムであり、現行Heroku基盤からガバメントクラウド（AWS ap-northeast-1）への移行を2027年3月31日本稼働予定で進めている。

本テスト計画書は、移行先システムが要件定義書（REQ-001）に定義された機能要件・非機能要件を満たすことを検証し、かつISMAP準拠・マイナンバー法安全管理措置の実装を確認するための全テスト活動の基本方針を定める。

### 1.2 テスト目的

| # | 目的 | 対応するテスト種別 |
|---|------|-----------------|
| 1 | 移行後システムが現行機能と同等の動作を提供すること | 結合テスト・UAT |
| 2 | 非機能要件（性能・可用性）のSLO達成を実証すること | 性能テスト |
| 3 | ISMAP 305統制項目・マイナンバー法安全管理措置の実装を確認すること | セキュリティテスト |
| 4 | RTO/RPOのSLA目標値をテスト環境で実測・検証すること | DR・バックアップテスト |
| 5 | 本番移行手順の正確性と移行後データ整合性を確認すること | 移行テスト |
| 6 | 住民代表・市職員が本番同等の操作受入確認を行うこと | UAT |

### 1.3 テスト対象システム

| システム | 主要コンポーネント | テスト優先度 |
|---------|----------------|------------|
| 住民向けWebポータル | CloudFront + WAF + ALB + ECS Fargate（住民ポータル）+ RDS PostgreSQL + ElastiCache Redis | 最高 |
| 庁内業務システム | Internal ALB + ECS Fargate（庁内業務）+ RDS PostgreSQL + 庁内AD連携 | 高 |
| バッチ・連携処理 | ECS Fargate（バッチワーカー）+ 住基ネット/コンビニ交付/マイナポータル外部IF | 高 |
| インフラ基盤 | VPC・セキュリティグループ・NACL・TGW・LGWAN接続・IAM・KMS | 最高 |
| 監視・ログ基盤 | CloudWatch・CloudTrail・VPC Flow Logs・GuardDuty・Security Hub | 高 |

### 1.4 テスト対象外

| 対象外事項 | 理由 |
|-----------|------|
| 住基ネット側システムの機能テスト | 県庁管轄システム。さくら市の責任範囲外 |
| 庁内AD（LDAP）サーバーの機能テスト | オンプレミス継続運用。接続確認のみ実施 |
| アプリケーション機能改修の検証 | R1移行のため機能変更なし（接続先変更のみ） |
| 利用者端末（PC/スマートフォン）の動作保証 | 標準的なブラウザ動作を前提とする |
| コンビニ交付端末側のシステムテスト | 事業者側の責任範囲 |

## 2. テスト戦略

### 2.1 テストレベルと実施方針

本プロジェクトでは以下5レベルのテストを実施する。各レベルの責任者・実施タイミング・合格基準を明確化する。

```
                        テストレベル全体像
  ┌──────────────────────────────────────────────────────┐
  │  Level 5: UAT（ユーザー受入テスト）      2027/02     │
  │  ─────────────────────────────────────────────────   │
  │  Level 4: 移行テスト（データ移行検証）  2027/02-03  │
  │  ─────────────────────────────────────────────────   │
  │  Level 3: 非機能テスト                 2027/01-02  │
  │     ├─ 性能テスト（負荷・耐久）                      │
  │     ├─ セキュリティテスト（WAF/ISMAP/Pen-Test）      │
  │     └─ DR・バックアップテスト（RTO/RPO実測）         │
  │  ─────────────────────────────────────────────────   │
  │  Level 2: 結合テスト                   2026/12-01  │
  │     ├─ インフラ結合（ネットワーク/IAM/監視）          │
  │     ├─ 機能結合（AP-DB-Cache-S3）                   │
  │     └─ 外部IF結合（住基ネット/コンビニ/マイナポータル） │
  │  ─────────────────────────────────────────────────   │
  │  Level 1: 単体確認（IaC検証）           2026/12    │
  │     └─ terraform plan / validate、AWS Config Rules  │
  └──────────────────────────────────────────────────────┘
```

### 2.2 テスト種別と方針の詳細

#### Level 1: 単体確認（IaC検証）

- **目的**: Terraform/CloudFormationコードの構文検証・リソース設定値の正確性確認
- **実施者**: インフラエンジニア（IaC担当）
- **手法**: `terraform plan`出力レビュー、`aws cloudformation validate-template`、AWS Config Rules
- **自動化**: GitHub Actionsパイプラインで自動実行
- **合格基準**: 全Terraform planがエラーゼロ、Config Rules違反ゼロ

#### Level 2: 結合テスト

- **目的**: 複数コンポーネント間の連携動作確認（ネットワーク疎通・機能連携・外部IF）
- **実施者**: インフラエンジニア + AP担当エンジニア
- **手法**: 手動テスト（ping/curl/ssh）+ 自動テストスクリプト
- **環境**: ステージング環境（本番同等構成）
- **合格基準**: テスト実施率95%以上、合格率98%以上

#### Level 3: 非機能テスト

| 種別 | 実施者 | ツール | 合格基準 |
|------|--------|--------|---------|
| 性能テスト（負荷） | QAエンジニア + インフラ | Apache JMeter 5.6 | 画面p95 ≤ 2秒、API p95 ≤ 1秒、エラー率 ≤ 0.1% |
| 性能テスト（耐久） | QAエンジニア + インフラ | Apache JMeter 5.6 | 24時間連続稼働でレスポンス劣化なし |
| セキュリティテスト | セキュリティエンジニア | Nessus / OWASP ZAP / SSL Labs | 高・重大脆弱性ゼロ |
| WAFテスト | セキュリティエンジニア | カスタムスクリプト | SQLインジェクション等をすべてブロック |
| ペネトレーションテスト | 外部委託（認定業者） | 指定なし（業者依存） | 高リスク所見ゼロ |
| DRテスト | インフラ運用チーム | AWS Console / CLI | RTO/RPO SLA達成率100% |

#### Level 4: 移行テスト

- **目的**: 本番相当データ量での移行手順の正確性・データ整合性確認
- **実施者**: インフラエンジニア + DBAエンジニア
- **手法**: 匿名化したデータを使用した移行リハーサル（2回実施）
- **合格基準**: データ件数100%一致、チェックサム一致、移行時間 ≤ 目標値

#### Level 5: UAT（ユーザー受入テスト）

- **目的**: 住民代表・市職員による実運用シナリオでの動作確認と受入サイン取得
- **実施者**: さくら市 市民課・税務課・福祉課職員、住民代表（モニター）
- **手法**: シナリオ基づく操作確認
- **合格基準**: 受入テスト合格率100%、重大指摘事項ゼロ

### 2.3 テスト実施の優先順位（リスクベース）

マイナンバーシステムの特性から、以下の優先順位でテスト資源を配分する。

| 優先度 | テスト領域 | リスク |
|--------|-----------|--------|
| 最高 | マイナンバーデータのアクセス制御・暗号化 | ISMAP違反、マイナンバー法違反 |
| 最高 | 住基ネット連携の疎通・データ整合性 | 住民基本台帳との不整合 |
| 最高 | 住民向け認証（JPKI）の動作確認 | 住民サービス不能 |
| 高 | 性能SLO（p95レスポンスタイム） | 住民体験・可用性違反 |
| 高 | RTO/RPO達成（DRテスト） | SLA未達 |
| 高 | WAF・DDoS防御の有効性 | セキュリティインシデント |
| 中 | 監視・アラーム動作 | 障害検知遅延 |
| 中 | バッチ処理の完了時間（2時間以内） | 日次同期遅延 |
| 低 | 管理系機能（レポート生成等） | 業務影響軽微 |

## 3. テスト環境設計

### 3.1 テスト環境構成

本プロジェクトでは以下3環境を使用する。

| 環境 | 目的 | 構成 | 管理者 |
|------|------|------|--------|
| 開発環境（dev） | 単体確認・結合テスト開発 | 本番の50%スペック（ECS最小タスク数1） | インフラエンジニア |
| ステージング環境（stg） | 結合テスト・性能テスト・セキュリティテスト | 本番同等構成（ECS最小タスク数2、RDS Multi-AZ） | QAリード |
| 本番環境（prod） | UAT最終確認・移行リハーサル | 本番構成 | 運用チーム |

#### ステージング環境（主要テスト環境）詳細

```
ステージング環境アーキテクチャ

[インターネット]
      │
      ▼
[CloudFront + WAF（stg用ディストリビューション）]
      │
      ▼
[ALB（住民向け stg）]
      │
      ▼
[ECS Fargate（住民ポータル stg）]         [ECS Fargate（バッチワーカー stg）]
- タスク数: 2（各AZ 1台）               - タスク数: 1（テスト時のみ起動）
      │
      ▼
[RDS PostgreSQL 15 Multi-AZ（stg）]       [ElastiCache Redis 7（stg）]
- インスタンス: db.r6g.large（本番同等）  - ノード: cache.r6g.large
      │
      ▼
[Internal ALB（庁内業務 stg）]
      │
[ECS Fargate（庁内業務 stg）]
- タスク数: 2

[LGWAN接続（スタブサーバ使用）]          [コンビニ交付（スタブサーバ使用）]
[マイナポータル（Sandbox環境使用）]       [庁内AD（本番ADをLDAPS参照）]
```

### 3.2 外部IF接続方針（スタブ・サンドボックス）

本番外部システムへのテストアクセスは原則禁止とし、以下の代替手段を使用する。

| 外部IF | 接続方式 | 備考 |
|--------|---------|------|
| 住基ネット（IF-001） | スタブサーバ（SOAP/XML疑似応答） | 実際の住民データを使用しない。架空データで疎通確認 |
| コンビニ交付（IF-002） | 事業者提供のテスト環境（VPN接続） | 事業者側でテスト環境を提供する。2026年11月末までに接続確認 |
| マイナポータル（IF-003） | デジタル庁提供のSandbox環境 | Sandbox APIエンドポイントを使用 |
| 庁内AD（IF-004） | 本番ADのテスト用OUに接続 | テスト用アカウントを使用。本番アカウントは使用しない |
| SES/SNS（IF-005/006） | テスト用メール/SMSエンドポイント | テスト専用の送信先を設定。実住民へのメール配信はしない |

### 3.3 テストデータ方針

#### 原則
- 実際の住民個人情報は一切使用しない（ISMAP要件・マイナンバー法）
- テストデータはすべて架空データとする
- 住民情報に近いデータパターン（12万件相当）を生成して使用する

#### テストデータ生成方法

| データ種別 | 件数 | 生成方法 | 管理者 |
|-----------|------|---------|--------|
| 架空住民情報 | 30万レコード | Fakerライブラリ（Node.js）で生成。現行データ量と同規模 | DBAエンジニア |
| 架空申請・届出データ | 50万件 | スクリプト自動生成。申請種別・年月を均等分布 | DBAエンジニア |
| テスト用職員アカウント | 20件 | さくら市AD担当者が手動作成。課別（市民・税務・福祉・管理者・テスト用運用者） | インフラエンジニア |
| テスト用住民モックアカウント | 100件 | JPKI認証不要のモックトークンを生成（テスト環境限定） | APエンジニア |
| 性能テスト用大量データ | 本番想定の120%規模 | 本番データ量より20%多いデータで余裕を確認 | DBAエンジニア |

#### データ管理ルール
- テストデータはステージング環境のRDSにのみ格納する
- テスト終了後、ステージング環境のRDSデータは全件削除する
- テストデータの本番環境への混入を防止するため、環境タグによる誤操作防止策を設ける

## 5. 結合テスト計画

### 5.1 テスト方針

結合テストは3つのレイヤーで実施する。

1. **インフラ結合テスト**: ネットワーク疎通・IAM権限・ログ出力の確認
2. **機能結合テスト**: AP・DB・Cache・S3間の連携動作確認
3. **外部IF結合テスト**: 住基ネット・コンビニ交付・マイナポータル・庁内ADとの接続確認

### 5.2 インフラ結合テストケース

#### 5.2.1 ネットワーク疎通テスト

| TC番号 | テストケース名 | テスト手順 | 期待結果 | 優先度 |
|--------|-------------|-----------|---------|--------|
| TC-NET-001 | 同一Subnet内ECSタスク間疎通 | ECSタスク間でcurlまたはping実行 | 通信成功 | 高 |
| TC-NET-002 | 異Subnet同一VPC間疎通（住民AP→DB） | 住民APサブネットからDBサブネットへポート5432でnc | 接続成功 | 最高 |
| TC-NET-003 | 異Subnet同一VPC間疎通（庁内AP→DB） | 庁内APサブネットからDBサブネットへポート5432でnc | 接続成功 | 最高 |
| TC-NET-004 | ECS→ElastiCache疎通（ポート6379） | APタスクからRedisクラスターエンドポイントへnc | 接続成功 | 高 |
| TC-NET-005 | ECS→S3 VPCエンドポイント経由 | APタスクからS3バケットへaws s3 ls実行 | アクセス成功 | 高 |
| TC-NET-006 | ECS→SES VPCエンドポイント経由 | APタスクからSESエンドポイントへHTTPS疎通確認 | 接続成功 | 中 |
| TC-NET-007 | ECS→SNS VPCエンドポイント経由 | APタスクからSNSエンドポイントへHTTPS疎通確認 | 接続成功 | 中 |
| TC-NET-008 | インターネット向け通信（ALB経由） | 外部クライアントからCloudFront経由でHTTPS接続 | HTTP 200、CloudFrontヘッダー確認 | 最高 |
| TC-NET-009 | セキュリティグループ拒否（DB直接接続不可） | 許可されていないソースからポート5432へ接続試行 | タイムアウト（接続拒否） | 最高 |
| TC-NET-010 | NACL拒否（不正ポートブロック） | NACLで明示的拒否設定されたポートへ接続試行 | 即時接続拒否 | 高 |
| TC-NET-011 | TGW経由LGWAN疎通確認 | バッチサブネットからLGWANスタブサーバへSOAP疎通 | HTTP 200（スタブ応答） | 最高 |
| TC-NET-012 | Site-to-Site VPN経由コンビニ交付疎通 | バッチサブネットからコンビニ交付テスト環境へHTTPS接続 | HTTP 200（テスト環境応答） | 最高 |

## 7. セキュリティテスト計画

### 7.1 セキュリティテスト方針

ISMAP 305統制項目への準拠確認を最優先とし、以下3つの観点でセキュリティテストを実施する。

1. **設定確認テスト**: AWSリソースの設定値が設計書通りであることを確認

## 12. バグ管理・エスカレーションフロー

### 12.1 バグ重大度分類

| 重大度 | 定義 | 例 |
|--------|------|-----|
| Critical（重大） | システム全体の機能停止・データ消失・セキュリティインシデント | マイナンバーデータの漏洩・住民ポータル全面停止・DBアクセス不能 |

| Medium（中） | 一部機能の不具合・性能劣化（SLO範囲内） | 統計レポートの表示不具合・特定画面のレスポンス遅延 |
| Low（低） | 軽微な表示不具合・UI改善要求 | 誤字・デザイン崩れ・操作説明文の不明瞭 |

| Medium | 翌営業日までに対応方針決定 | 次フェーズゲートまで（原則） | QAリード（週次レビューで） |
| Low | 週次レビューで対応方針を決定 | 本番移行前（優先度に応じて） | QAリード（週次レビューで） |
