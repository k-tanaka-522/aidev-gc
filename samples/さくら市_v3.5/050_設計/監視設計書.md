## 1. 監視設計方針

### 1.1 背景・目的

さくら市マイナンバーサービス基盤（AWS ガバメントクラウド）は、住民ポータル・庁内業務システム・バッチ処理の3系統で構成される。本設計書は以下の目的を実現するための監視・ロギング基盤を定義する。

| 目的 | 内容 |
|------|------|
| 可用性保証 | 住民向けSLA 99.9%、庁内SLA 99.5% の継続的な計測・管理 |
| インシデント早期検知 | 障害の予兆をアラームで捕捉し、30分以内の初期対応を実現 |
| 監査証跡の確保 | CloudTrail + CloudWatch Logs で1年間の操作ログ保持（コンプライアンス要件） |
| 運用可視性 | 担当者・管理者・経営層それぞれの視点に対応した階層ダッシュボード |
| EBPM報告 | 総務省EBPMへの月次統計データ自動送信 |

### 1.2 監視対象スコープ

| 層 | 対象リソース | 監視種別 |
|----|------------|---------|
| エッジ層 | CloudFront、WAF | メトリクス、ログ |
| ロードバランサー層 | ALB（住民向け・庁内向け各1台） | メトリクス、アクセスログ |
| コンピュート層 | ECS Fargate（住民ポータル、庁内システム、バッチ） | メトリクス、コンテナログ |
| データ層 | RDS for PostgreSQL（Multi-AZ）、ElastiCache for Redis（Multi-AZ） | メトリクス、スローログ |
| セキュリティ層 | GuardDuty、Security Hub | Findings連携 |
| ネットワーク層 | VPC Flow Logs | フロー分析 |
| API・認証層 | Cognito（マイナンバー認証連携） | ログイン失敗検知 |
| バッチ処理 | ECS Scheduled Task（夜間バッチ） | 完了/失敗ステータス |

### 1.3 SLI/SLO 定義（概要）

詳細は[セクション10](#10-slisloエラーバジェット設計)に記載する。

| システム | SLO | 月間許容ダウンタイム |
|---------|-----|-----------------|
| 住民ポータル | 99.9% | 約43.8分/月 |
| 庁内業務システム | 99.5% | 約3.65時間/月 |
| バッチ処理 | 99.0% | 約7.3時間/月 |

### 1.4 監視体制

| 区分 | 担当 | 連絡先 |
|------|------|-------|
| 一次対応（24/365） | さくら市 情報政策課 運用チーム（委託先：クラウド運用会社） | PagerDuty → 担当者オンコール |
| 二次対応（業務時間内） | さくら市 情報政策課 | メール／Slack #alert-critical |
| インフラ変更・恒久対応 | クラウド運用会社 インフラチーム | Slack #infra-ops |
| セキュリティインシデント | さくら市 CSIRT | PagerDuty → CSIRT リーダー |

## 3. アラーム設計

### 3.1 アラーム設計方針

- アラーム状態遷移: `OK` → `ALARM`（障害）、`OK` → `INSUFFICIENT_DATA`（データ欠落）
- 評価期間: 誤検知抑制のため原則2〜3ポイント連続で状態遷移
- 静的閾値と異常検知を組み合わせ（業務繁忙期のフォールスポジティブを低減）
- アラーム優先度: P1（即時対応）、P2（1時間以内）、P3（翌営業日対応）

### 3.2 ECS Fargate アラーム一覧

| アラーム名 | メトリクス | 閾値 | 評価周期 | 優先度 | 通知先 | オーナー | 意図 |
|----------|----------|-----|--------|------|------|------|------|
| ecs-portal-cpu-warning | CPUUtilization (resident-portal) | > 70% | 3分×2 | P2 | SNS-ops | インフラチーム | スケーリング前の早期警告 |
| ecs-portal-cpu-critical | CPUUtilization (resident-portal) | > 90% | 1分×2 | P1 | SNS-critical | インフラチーム | CPU飽和によるSLO影響回避 |
| ecs-portal-mem-warning | MemoryUtilization (resident-portal) | > 75% | 3分×2 | P2 | SNS-ops | インフラチーム | メモリリーク早期発見 |
| ecs-portal-mem-critical | MemoryUtilization (resident-portal) | > 90% | 1分×2 | P1 | SNS-critical | インフラチーム | OOMキラー発動前の対処 |
| ecs-portal-task-count-low | RunningTaskCount (resident-portal) | < 2 | 1分×1 | P1 | SNS-critical | インフラチーム | 最小冗長性割れによる可用性低下検知 |

### 3.7 複合条件アラーム（Composite Alarm）

複数リソースの複合障害を検知するための Composite Alarm を設定する。

```
alb-public-all-unhealthy: 住民ポータル完全停止（ALB全台障害）
  条件: alb-public-all-unhealthy ALARM

resident-portal-slo-breach: 住民ポータルSLO違反リスク
  条件: alb-public-latency-critical ALARM AND alb-public-5xx-critical ALARM
  通知先: SNS-critical + PagerDuty + メール（課長以上）

db-degradation: DBレイヤー複合劣化
  条件: rds-cpu-critical ALARM OR rds-connections-critical ALARM OR rds-freemem-critical ALARM
  通知先: SNS-critical + DBチームPagerDuty
```

### 5.2 実装例（ECS Fargate コンテナ側）

```python
import boto3
from datetime import datetime

cloudwatch = boto3.client('cloudwatch', region_name='ap-northeast-1')

def send_login_metrics(success_count: int, failure_count: int, service_name: str):
    """ログインメトリクスをCloudWatchに送信"""
    cloudwatch.put_metric_data(
        Namespace='Sakura/Application',
        MetricData=[
            {
                'MetricName': 'LoginSuccessCount',
                'Value': success_count,
                'Unit': 'Count',
                'Timestamp': datetime.utcnow(),
                'Dimensions': [
                    {'Name': 'Service', 'Value': service_name},
                ]
            },
            {
                'MetricName': 'LoginFailureCount',
                'Value': failure_count,
                'Unit': 'Count',
                'Timestamp': datetime.utcnow(),
                'Dimensions': [
                    {'Name': 'Service', 'Value': service_name},
                ]
            },
        ]
    )

def send_batch_result(batch_name: str, duration_sec: float, success: bool, record_count: int):
    """バッチ処理結果をCloudWatchに送信"""
    cloudwatch.put_metric_data(
        Namespace='Sakura/Application',
        MetricData=[
            {
                'MetricName': 'BatchProcessingDuration',
                'Value': duration_sec,
                'Unit': 'Seconds',
                'Timestamp': datetime.utcnow(),
                'Dimensions': [{'Name': 'BatchName', 'Value': batch_name}]
            },
            {
                'MetricName': 'BatchSuccessCount' if success else 'BatchFailureCount',
                'Value': record_count,
                'Unit': 'Count',
                'Timestamp': datetime.utcnow(),
                'Dimensions': [{'Name': 'BatchName', 'Value': batch_name}]
            },
        ]
    )
```

## 8. ログ集約設計

### 8.1 ログ集約アーキテクチャ

```
[ECS Fargate コンテナ]
    ↓ CloudWatch Logs Driver
[CloudWatch Logs ロググループ]
    ├── サブスクリプションフィルタ（エラー検知）
    │       ↓
    │   [Lambda] → [SNS] → [Slack / メール]
    └── CloudWatch Logs Insights（対話的クエリ）

[CloudTrail]
    ├── [S3 バケット] → Glacier（長期保存）
    └── [CloudWatch Logs] → Logs Insights / アラーム

[ALBアクセスログ / VPC Flow Logs / WAFログ]
    └── [S3 バケット]
            ↓ Amazon Athena
        SQLクエリによるアドホック分析
```

**Kinesis Firehose連携（オプション）:**  
現時点でSIEM導入予定なし。将来的にSplunk/Elasticsearch導入時はKinesis Data Firehose経由でストリーミング連携する。遅延目標: リアルタイム（<60秒）。

### 8.2 CloudWatch Logs Insights クエリ集

#### エラーログ分析（ECSアプリケーション）


## 10. SLI/SLO/エラーバジェット設計

### 10.1 住民ポータル SLI 定義

| SLI名 | 定義 | 計測方法 | 良好条件 |
|------|------|--------|--------|
| 可用性（Availability） | 成功リクエスト数 / 全リクエスト数 | ALB HTTPCode_Target_5XX_Count / RequestCount | 5xxエラー率 < 0.1% |
| レイテンシ（Latency） | ALB TargetResponseTime P99 | ALB TargetResponseTime (p99) | P99 < 1,000 ms |
| キャッシュ可用性 | ElastiCache セッション機能の稼働状態 | ElastiCache CacheHitRate | CacheHitRate > 80% |

### 10.2 SLO 目標値

| システム | SLI | SLO | 根拠 |
|---------|-----|-----|------|
| 住民ポータル | 可用性（5xxエラー率 < 0.1%） | 月間 99.9% | 住民向けSLA 99.9% |
| 住民ポータル | レイテンシ（P99 < 1,000 ms） | 月間 95%の時間帯でP99 < 1,000 ms | ユーザー体感品質基準 |
| 庁内業務システム | 可用性（5xxエラー率 < 0.5%） | 月間 99.5% | 庁内向けSLA 99.5% |
| バッチ処理 | バッチ成功率 | 月間 99.0% | 運用要件 |

### 10.3 エラーバジェット計算（住民ポータル・可用性）

```
月間総分数 = 30日 × 24時間 × 60分 = 43,200 分
SLO = 99.9%
月間許容ダウン分数 = 43,200 × (1 - 0.999) = 43.2 分

エラーバジェット残量 = (実際のダウン分数 / 43.2分) × 100
  →  0% = バジェット完全消費（これ以上ダウンタイム不可）
  → 50% = 21.6分消費（要注意ライン → 運用リーダーへ報告）
  →100% = バジェット未使用（問題なし）
```

**エラーバジェット アラーム設定:**

| アラーム名 | 条件 | 優先度 | 通知先 |
|----------|-----|------|------|
| error-budget-50pct-consumed | 月間ダウン分数 > 21.6分 | P2 | SNS-ops + 運用リーダーメール |
| error-budget-90pct-consumed | 月間ダウン分数 > 38.9分 | P1 | SNS-critical + 市担当課長メール |
| error-budget-burned | 月間ダウン分数 > 43.2分 | P1 | SNS-critical + 副市長メール + PagerDuty |

**エラーバジェット計測用 CloudWatch Logs Insights クエリ（月次確認）:**

```
# 当月の5xxエラー発生比率（ALBアクセスログから算出）
fields elb_status_code
| stats
    count() as total_requests,
    sum(if(elb_status_code >= 500, 1, 0)) as error_requests
  by bin(1mo)
| fields total_requests, error_requests, (error_requests / total_requests * 100) as error_rate_pct
```

| SLI | SLO | 計測方法 |
|-----|-----|--------|

| レイテンシ（P99 < 2,000 ms） | 90%の時間帯 | ALB TargetResponseTime |

```python
from datetime import datetime, timedelta

SYSTEM_ID = 'GC-Sakura-Mynumber-001'

def lambda_handler(event, context):
    end_time = datetime.utcnow()
    start_time = end_time.replace(day=1, hour=0, minute=0, second=0)

    ebpm_data = {
        'systemId': SYSTEM_ID,
        'reportDate': end_time.isoformat(),
        'reportPeriod': {
            'start': start_time.isoformat(),

        'metrics': {

                'internal_system': get_alb_request_count('sakura-prod-alb-internal', start_time, end_time),
            },
            'mynumberAccessCount': get_custom_metric_sum('MynumberAccessCount', start_time, end_time),
            'monthlyActiveUsers': get_mau_from_logs(start_time, end_time),
            'availability': {

                'internal_system': calculate_availability('sakura-prod-alb-internal', start_time, end_time),
            },
            'avgResponseTime_ms': get_alb_avg_response_time(start_time, end_time),
            'batchSuccessRate': calculate_batch_success_rate(start_time, end_time),
            'securityIncidents': get_guardduty_high_findings(start_time, end_time),
            'monthlyCostJPY': get_monthly_cost_jpy(),
        }
    }

    send_to_ebpm(ebpm_data)
    save_submission_log(ebpm_data)
    return {'statusCode': 200, 'message': 'EBPM submission completed'}
```
