## 1. セキュリティ設計方針

### 1.1 背景

さくら市マイナンバーサービス基盤は、住民のマイナンバー（特定個人情報）を取り扱うシステムであり、ガバメントクラウド（AWS）上に関東圏県庁グループの共同利用環境として構築する。マイナンバー法（行政手続における特定の個人を識別するための番号の利用等に関する法律）に基づく安全管理措置の実装、およびISMAP（政府情報システムのためのセキュリティ評価制度）305管理策への準拠が必須となる。

### 1.2 設計原則

本セキュリティ設計は以下の3つの原則に基づく。

**原則1: ゼロトラストアーキテクチャ**

すべてのアクセスをデフォルト拒否（Deny All）とし、明示的に許可されたもののみアクセスを認める。4本柱（Identity、Device、Network、Data & Apps）を包括的に実装する。

- Identity: MFA必須化、IAMロールベースアクセス、Permission Boundary適用
- Device: 庁内端末の検疫ポリシー（OS Patch、Antivirus確認）
- Network: マイクロセグメンテーション（SG/NACL多層制御）
- Data & Apps: KMS暗号化、リソースベースポリシーによるアクセス制御

**原則2: 多層防御（Defense in Depth）**

単一のセキュリティ対策に依存せず、WAF/Shield（境界防御）、SG/NACL（ネットワーク制御）、IAM（認可制御）、KMS（データ保護）、GuardDuty/SecurityHub（検知・対応）を重層的に配置する。

**原則3: ISMAP305管理策への完全対応**

ISMAP305の管理策カテゴリ（アクセス制御/暗号化/ログ管理/ネットワーク分離/脆弱性管理/インシデント対応）に対し、設計段階で100%カバレッジを達成する。

### 1.3 制約条件・前提条件

| 項目 | 内容 |
|------|------|
| GC利用方式 | 共同利用（関東圏県庁グループ） |
| AWSリージョン | ap-northeast-1（東京） |
| GCセキュリティテンプレート | 自動適用テンプレート + 必須適用テンプレート適用済み |
| SCPポリシー | 県庁グループOrganizations管理アカウントにより適用 |
| IdP | 庁内Active Directory（LDAP）+ Azure AD連携 |
| 住民認証 | JPKI（マイナンバーカード電子証明書）+ ID/パスワード |
| CCISガイドライン | 県庁準拠（情報セキュリティポリシーガイドライン） |
| DS-310 | セキュリティグループ閣議決定指針への準拠 |

### 1.4 セキュリティ構成概要

```
[住民]──JPKI認証──>[CloudFront]──>[WAF]──>[ALB]──>[ECS/EC2]──>[RDS]
                     + Shield           Web ACL     Private     Private
                     Advanced                       Subnet      Subnet

[職員]──LDAP/MFA──>[VPN/LGWAN]──>[TGW]──>[内部ALB]──>[ECS/EC2]
```

## 3. IAM設計

### 3.1 認証方針

#### 住民認証

| 認証方式 | 用途 | 実装 |
|---------|------|------|
| JPKI（電子証明書） | マイナンバーカードによる本人確認 | JPKI認証基盤（外部連携） |
| ID/パスワード | フォールバック認証 | Amazon Cognito User Pool |

- JPKI認証は外部ASP事業者のJPKI認証基盤と連携
- Cognito User Poolでセッション管理、トークン発行
- パスワードポリシー: 14文字以上、大文字/小文字/数字/記号を含む、90日ごとの変更

#### 職員認証

| 認証方式 | 用途 | 実装 |
|---------|------|------|
| LDAP（庁内AD） | 庁内業務システムへのログイン | Azure AD → AWS IAM Identity Center（SSO） |
| MFA（TOTP） | 二要素認証 | AWS IAM Identity Center MFA設定 |

- 庁内Active DirectoryとAzure ADを同期（Azure AD Connect）
- Azure ADからAWS IAM Identity Center（旧SSO）へSAML連携
- 全職員ユーザーにMFA（TOTP）を必須化
- セッションタイムアウト: 8時間（業務時間内）

#### IAMパスワードポリシー

```json
{
  "MinimumPasswordLength": 14,
  "RequireSymbols": true,
  "RequireNumbers": true,
  "RequireUppercaseCharacters": true,
  "RequireLowercaseCharacters": true,
  "MaxPasswordAge": 90,
  "PasswordReusePrevention": 12,
  "HardExpiry": false
}
```

#### アカウントライフサイクル管理

| イベント | 対応 | 所要時間 |
|---------|------|---------|
| 職員着任 | AD登録 → Azure AD同期 → IAMロール自動付与 | 24時間以内 |
| 職員異動 | AD更新 → ロール変更自動反映 | 24時間以内 |
| 職員退職 | AD無効化 → IAMセッション即時無効化 | 即時（AD連携） |
| 退職後30日 | AD削除 → 関連リソースクリーンアップ | 30日後自動実行 |

### 3.2 IAMロール一覧

本システムで使用するIAMロールは以下の通り。最小権限の原則に基づき、各ロールには業務遂行に必要最小限の権限のみを付与する。

#### アプリケーション系ロール

| ロール名 | 用途 | 主要権限 | アタッチ先 |
|---------|------|---------|----------|
| `sakura-ecs-task-role` | ECSタスク実行用 | S3 GetObject/PutObject（アプリバケット）、RDS接続、KMS Decrypt、Secrets Manager GetSecretValue | ECSタスク定義 |
| `sakura-ecs-execution-role` | ECSタスク起動用 | ECR GetAuthorizationToken/BatchGetImage、CloudWatch Logs CreateLogStream/PutLogEvents | ECSタスク定義 |
| `sakura-lambda-mynumber-role` | マイナンバー処理Lambda | KMS Encrypt/Decrypt（マイナンバー専用キー）、DynamoDB PutItem/GetItem、CloudWatch Logs | Lambda関数 |
| `sakura-lambda-notification-role` | 通知処理Lambda | SNS Publish、SES SendEmail、CloudWatch Logs | Lambda関数 |
| `sakura-batch-role` | バッチ処理用 | S3 GetObject/PutObject、RDS接続、SQS SendMessage/ReceiveMessage | ECSタスク/EC2 |

#### 運用系ロール

| ロール名 | 用途 | 主要権限 | 利用者 |
|---------|------|---------|-------|
| `sakura-admin-role` | システム管理者 | EC2/RDS/ECS/S3の管理権限。IAM変更権限は除外 | さくら市IT管理者（2名） |
| `sakura-operator-role` | 運用担当者 | EC2 Describe/Start/Stop、RDS Describe、CloudWatch ReadOnly、SSM StartSession | 運用担当者（5名） |
| `sakura-readonly-role` | 参照専用 | 全リソースDescribe/Get/List（ReadOnly） | 監査担当者（2名） |
| `sakura-security-audit-role` | セキュリティ監査 | SecurityHub/GuardDuty/Config/CloudTrail ReadOnly、IAM Access Analyzer | セキュリティ担当（1名） |

#### クロスアカウント系ロール

| ロール名 | 用途 | 信頼ポリシー | 主要権限 |
|---------|------|------------|---------|
| `sakura-cross-account-admin` | 県庁管理者からのアクセス | 県庁管理アカウント（arn:aws:iam::PREFECTURE_ACCOUNT:root） | AdministratorAccess（Permission Boundaryで制限） |
| `sakura-cross-account-audit` | 県庁監査チームからのアクセス | 県庁監査アカウント | ReadOnlyAccess + SecurityHub/GuardDuty |
| `sakura-cross-account-billing` | 県庁コスト管理 | 県庁管理アカウント | Billing ReadOnly、Cost Explorer |

#### GC自動化系ロール

| ロール名 | 用途 | 主要権限 |
|---------|------|---------|
| `sakura-config-remediation-role` | Config自動修復 | 修復対象リソースの変更権限（SG/S3/RDS等） |
| `sakura-guardduty-response-role` | GuardDuty自動応答 | EC2 ModifyInstanceAttribute（SG変更）、SNS Publish |
| `sakura-backup-role` | AWS Backup実行 | Backup:*、対象リソースのSnapshot/Restore |

**ロール数合計: 14ロール**（アプリ5 + 運用4 + クロスアカウント3 + 自動化2）

### 3.3 特権アカウント管理

#### rootアカウント

| 項目 | 設定 |
|------|------|
| MFA | ハードウェアMFAトークン必須 |
| アクセスキー | 無効化（削除済み） |
| 利用条件 | 緊急時のみ（SCP変更、アカウント設定変更等） |
| 利用承認 | 県庁管理者 + さくら市IT管理者の双方承認必須 |
| 利用ログ | CloudTrailで記録、即座にSNS通知 |

#### 特権操作の制御

- SSM Session Managerを唯一のサーバーアクセス手段とする（SSH直接接続禁止）
- Session Manager経由の全操作をCloudWatch Logsに記録
- 特権操作（インスタンス削除、DB変更等）は承認ワークフロー必須

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDirectSSH",
      "Effect": "Deny",
      "Action": "ec2:AuthorizeSecurityGroupIngress",
      "Resource": "*",
      "Condition": {
        "ForAnyValue:IpPermissions.FromPort": "22",
        "ForAnyValue:IpPermissions.ToPort": "22"
      }
    }
  ]
}
```

### 3.4 SCP設計（共同利用グループ制約）

県庁グループOrganizations管理アカウントから適用されるSCPに加え、さくら市アカウント固有の制約を定義する。

#### SCP一覧

| SCP名 | 目的 | 主な制約 |
|-------|------|---------|
| `scp-deny-region-outside-apne1` | リージョン制限 | ap-northeast-1以外のリソース作成禁止 |
| `scp-deny-root-actions` | root操作制限 | root以外からのOrganizations/IAM変更禁止 |
| `scp-require-encryption` | 暗号化強制 | 非暗号化S3/EBS/RDSの作成禁止 |
| `scp-deny-public-access` | パブリックアクセス禁止 | S3パブリックアクセス、パブリックEC2の作成禁止 |
| `scp-deny-dangerous-services` | 危険サービス禁止 | GameLift、Lightsail等の不要サービス利用禁止 |

#### SCP例: リージョン制限

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideAPNE1",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": [
            "ap-northeast-1"
          ]
        },
        "ArnNotLike": {
          "aws:PrincipalArn": [
            "arn:aws:iam::*:role/OrganizationsAdmin"
          ]
        }
      }
    }
  ]
}
```

#### SCP例: 暗号化強制

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnencryptedS3",
      "Effect": "Deny",
      "Action": "s3:PutObject",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "aws:kms"
        }
      }
    },
    {
      "Sid": "DenyUnencryptedEBS",
      "Effect": "Deny",
      "Action": "ec2:CreateVolume",
      "Resource": "*",
      "Condition": {
        "Bool": {
          "ec2:Encrypted": "false"
        }
      }
    },
    {
      "Sid": "DenyUnencryptedRDS",
      "Effect": "Deny",
      "Action": "rds:CreateDBInstance",
      "Resource": "*",
      "Condition": {
        "Bool": {
          "rds:StorageEncrypted": "false"
        }
      }

}
```

### 3.5 Permission Boundary

全IAMロールにPermission Boundaryを適用し、たとえAdministratorAccessが付与されても、以下の操作を禁止する。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowedServices",
      "Effect": "Allow",
      "Action": [
        "ec2:*",
        "ecs:*",
        "rds:*",
        "s3:*",
        "lambda:*",
        "dynamodb:*",
        "elasticloadbalancing:*",
        "cloudwatch:*",
        "logs:*",
        "ssm:*",
        "kms:Decrypt",
        "kms:GenerateDataKey",
        "kms:DescribeKey",
        "secretsmanager:GetSecretValue",
        "sqs:*",
        "sns:*",
        "ses:*"
      ],
      "Resource": "*"
    },
    {
      "Sid": "DenyDangerousActions",
      "Effect": "Deny",
      "Action": [
        "iam:CreateUser",
        "iam:DeleteUser",
        "iam:CreateRole",
        "iam:DeleteRole",
        "iam:AttachUserPolicy",
        "iam:PutUserPolicy",
        "organizations:*",
        "account:*",
        "kms:ScheduleKeyDeletion",
        "kms:DisableKey",
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "config:StopConfigurationRecorder",
        "guardduty:DisableDetector"
      ],
      "Resource": "*"
    }
```

### 4.1 CMKの用途別設計

### 4.3 キーローテーション設計

| キー | ローテーション周期 | 方式 | 備考 |
|-----|---------------|------|------|
| 一般用キー（RDS/S3/EBS/SSM/Backup/Log） | 年1回 | KMS自動ローテーション | AWS管理の自動ローテーション |
| マイナンバー専用キー | 半年1回 | KMS自動ローテーション | 高セキュリティ要件のため周期短縮 |

- KMS自動ローテーションでは、旧キーマテリアルも保持されるため、既存データの復号に影響なし
- ローテーション実行時にCloudTrailイベント `RotateKey` を検出し、SNS通知

### 4.4 鍵の廃棄手順

1. キー無効化（`kms:DisableKey`）— 即座にキーを利用不可にする
2. 依存リソースの確認 — CloudTrailログからキー利用履歴を確認（過去90日）
3. スケジュール削除設定 — 30日間の待機期間を設定（`kms:ScheduleKeyDeletion`）
4. 待機期間中の監視 — 削除予定キーへのアクセス試行をCloudWatch Alarmsで監視
5. 自動削除 — 30日経過後にAWSが自動削除


```json
{
  "source": ["aws.guardduty"],
```

#### 自動隔離Lambda概要

```python
# sakura-guardduty-auto-remediation
# GuardDuty High Severity Finding → 自動隔離処理

def handler(event, context):
    finding = event['detail']
    severity = finding['severity']
    resource_type = finding['resource']['resourceType']

    if resource_type == 'Instance':
        instance_id = finding['resource']['instanceDetails']['instanceId']
        # 隔離セキュリティグループに変更
        ec2.modify_instance_attribute(
            InstanceId=instance_id,
            Groups=['sg-quarantine']  # Ingress/Egress全拒否
        )
        # EBSスナップショット取得（証拠保全）
        # SNS通知

    elif resource_type == 'AccessKey':
        access_key_id = finding['resource']['accessKeyDetails']['accessKeyId']
        # アクセスキー無効化
        # SNS通知
```

## 11. インシデント対応

### 11.1 インシデント分類

| レベル | 定義 | 例 | 対応時間 |
|-------|------|-----|---------|
| P1（緊急） | サービス停止、データ漏洩の可能性 | マイナンバー情報漏洩、DDoS攻撃によるサービスダウン | 即時（15分以内に初動） |
| P2（重大） | セキュリティ侵害の兆候 | GuardDuty HIGH Finding、不正ログイン成功 | 1時間以内 |
| P3（注意） | セキュリティ設定の逸脱 | Config Rule非準拠、Security Hub MEDIUM Finding | 24時間以内 |
| P4（情報） | 通常のセキュリティイベント | ログイン失敗、WAFブロック | 週次レビュー |

### 11.2 エスカレーションフロー

```
[検知]
  GuardDuty / SecurityHub / CloudWatch Alarm / WAF
    ↓
[通知]
  EventBridge → SNS → メール + Slack
    ↓
[初動判定]
  ┌─ P1（緊急）────────────────────────────────────┐
  │ 15分以内に初動                                    │
  │ セキュリティチーム → さくら市IT管理者 → 県庁CSIRT  │
  │ 自動隔離（Lambda）実行                            │
  │ マイナンバー関連の場合: 個人情報保護委員会への報告   │
  └──────────────────────────────────────────────────┘
  ┌─ P2（重大）────────────────────────────────────┐
  │ 1時間以内に対応開始                               │
  │ セキュリティチーム → さくら市IT管理者              │
  │ 手動調査・対応                                    │
  └──────────────────────────────────────────────────┘
  ┌─ P3（注意）────────────────────────────────────┐
  │ 24時間以内に対応計画策定                           │
  │ セキュリティチーム内で対応                         │
  └──────────────────────────────────────────────────┘
  ┌─ P4（情報）────────────────────────────────────┐
  │ 週次レビューで確認                                │
  └──────────────────────────────────────────────────┘
    ↓
[調査]
  CloudTrail / VPC Flow Logs / GuardDuty Findings / WAF Logs
    ↓
[対応]
  隔離 → 証拠保全 → 原因特定 → 復旧 → 再発防止
    ↓
[報告]
  インシデント報告書作成 → 関係者共有 → 改善措置実施
```

### 11.3 連絡体制

| 役割 | 担当 | 連絡先 | 対応時間 |
|------|------|-------|---------|
| 一次対応 | 運用担当者（委託先） | Slack + メール | 24/365 |
| セキュリティリード | さくら市IT管理者 | 電話 + メール | 平日 9:00-18:00 |
| エスカレーション先 | 県庁CSIRT | 電話 + メール | 平日 9:00-17:00 |
| 緊急連絡先 | 県庁セキュリティ責任者 | 電話（緊急回線） | 24/365（P1のみ） |
| 外部通報 | 個人情報保護委員会 | 所定の報告書式 | マイナンバー漏洩時のみ |

### 11.4 証拠保全手順

インシデント発生時、以下の証拠を保全する。

1. **EBSスナップショット取得** — 影響を受けたインスタンスのEBSボリュームのスナップショットを即座に取得
2. **メモリダンプ取得** — SSM Run Commandでメモリダンプを取得（可能な場合）
3. **CloudTrailログ保全** — 対象期間のログをS3から別バケット（フォレンジック用）にコピー
4. **VPC Flow Logs保全** — 対象VPC/ENIのFlow Logsを保全
5. **GuardDuty Findingsエクスポート** — 関連Findingsをエクスポート
6. **タイムライン作成** — 検知から対応完了までの全アクションを時系列で記録

## 12. マイナンバー安全管理措置

マイナンバー法（番号法）第12条に基づく安全管理措置を、以下の4つの側面で実装する。

### 12.1 組織的安全管理措置

| 措置項目 | 実装内容 |
|---------|---------|
| 組織体制の整備 | セキュリティ責任者（さくら市IT管理者）、取扱担当者（職員5名）を指定 |
| 取扱規程の策定 | マイナンバー取扱規程を策定し、システム利用手順を明文化 |
| 取扱状況の記録 | CloudTrailでマイナンバーアクセスAPIを全記録。アクセスログを月次レビュー |
| 情報漏洩等への対応 | インシデント対応計画（本書セクション11）に基づく。個人情報保護委員会への報告手順を整備 |
| 取扱状況の把握・安全管理措置の見直し | 四半期ごとのセキュリティレビュー、年次のISMAP監査対応 |

### 12.2 人的安全管理措置

| 措置項目 | 実装内容 |
|---------|---------|
| 事務取扱担当者の監督 | アクセス権限はIAMロールで厳格に制御。操作ログを監査 |
| 事務取扱担当者の教育 | 年2回のセキュリティ研修（マイナンバー取扱い含む）を実施 |
| 秘密保持義務 | 秘密保持誓約書の取得。退職時のアカウント即時無効化 |
| アクセス権限の明確化 | IAMロール一覧（本書セクション3.2）で権限を明確に定義 |

### 12.3 物理的安全管理措置

| 措置項目 | 実装内容 |
|---------|---------|
| 特定個人情報の区域管理 | AWSリージョン: ap-northeast-1（日本国内）。データの国外持ち出し禁止（SCPで制御） |
| 機器及び電子媒体等の管理 | EBS/S3は全てKMS暗号化。物理媒体はAWSが自動廃棄（AWS SOC2/ISO27001準拠） |
| 電子媒体等の持ち出し制限 | S3からのダウンロードはIAMポリシーで制限。VPC Endpoint経由のみアクセス可能 |
| 個人番号の削除、機器及び電子媒体等の廃棄 | データ削除はKMSキー削除による暗号学的消去。EBSボリューム削除時はAWSによるゼロ化処理 |

### 12.4 技術的安全管理措置

| 措置項目 | 実装内容 | 対応セクション |
|---------|---------|-------------|
| アクセス制御 | IAMロールによる最小権限。マイナンバーアクセスは専用Lambda（`sakura-lambda-mynumber-role`）のみ | 3.2 |
| アクセス者の識別と認証 | 職員: MFA必須。住民: JPKI認証 | 3.1 |
| 外部からの不正アクセス防止 | WAF/Shield、GuardDuty、SG/NACL多層防御 | 5, 6 |
| 情報漏洩等の防止 | 保存時: KMS暗号化（マイナンバー専用キー）。転送時: TLS 1.2以上 | 4 |

### 12.5 マイナンバー特有の追加保護

| 保護策 | 実装 |
|-------|------|
| マイナンバーフィールドの二重暗号化 | RDS暗号化（ストレージレベル）+ アプリケーションレベルでのKMS Envelope Encryption（`alias/sakura-mynumber-key`） |
| マイナンバーアクセスの専用ログ | CloudTrailイベント + カスタムアプリケーションログで全アクセスを記録 |
| マイナンバーデータの分離 | DynamoDBの専用テーブルに格納。アクセスポリシーで`sakura-lambda-mynumber-role`のみに制限 |
| マイナンバーの表示制限 | アプリケーション層でマスキング処理（下4桁のみ表示） |
| マイナンバーの保存期間管理 | 法定保存期間経過後の自動削除（DynamoDB TTL）。削除ログをCloudTrailで記録 |
