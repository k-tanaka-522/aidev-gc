## 1. 案件概要

### 1.1 プロジェクト基本情報

| 項目 | 内容 |
|------|------|
| プロジェクト名 | さくら市マイナンバーサービス基盤移行プロジェクト |
| 顧客 | さくら市 総務部 情報システム課 |
| 対象システム | マイナンバーサービス基盤（住民向けWebポータル、庁内業務システム、バッチ・連携処理） |
| 現行環境 | Heroku（Node.js + PostgreSQL + Redis + AWS S3 + Cloudflare CDN） |
| 移行先 | ガバメントクラウド（AWS） |
| GC利用方式 | 共同利用（関東圏県庁グループ） |
| 移行方式 | R1（リホスティング：IaaS基盤にリホスト＋一部マネージドサービス置換） |
| 開始時期 | 2026年7月 |
| 本稼働予定 | 2027年3月31日 |
| 予算概況 | 約1.2億円（概算、AWS利用料3年分含む） |

### 1.2 ビジネス目標

| 優先度 | 目標 | 期待効果 |
|--------|------|---------|
| プライマリ | マイナンバー関連サービスをISMAP準拠のガバメントクラウドへ移行し、セキュリティ・コンプライアンスを確保する | 個人情報保護法・マイナンバー法への完全準拠 |
| セカンダリ | 現行Heroku基盤の運用課題（スケーラビリティ制約、LGWAN非対応）を解消する | 住基ネット連携のLGWAN直接接続実現、ピーク時の柔軟なスケーリング |
| 第三 | 将来的なデジタル行政サービス拡張の基盤を構築する | 3年間で新規サービス追加時のリードタイムを50%短縮 |

### 1.4 プロジェクトスコープ

#### スコープ内

| # | 対象 | 概要 |
|---|------|------|
| 1 | 住民向けWebポータル | マイナンバーカード申請状況確認、電子申請、証明書交付申請、通知機能 |
| 2 | 庁内業務システム | 住民情報照会、届出承認・処理フロー、統計分析、監査ログ、ユーザー管理 |
| 3 | バッチ・連携処理 | 住基ネット同期（日次）、コンビニ交付連携、マイナポータル連携、月次統計 |
| 4 | インフラ基盤 | VPC/ネットワーク設計、セキュリティ設計、監視設計、バックアップ・DR設計 |
| 5 | データ移行 | Heroku PostgreSQL → RDS、S3オブジェクト移行、Redis設定移行 |
| 6 | LGWAN接続 | 県庁経由のLGWAN接続設計・構築 |

#### スコープ外

| # | 対象 | 理由 |
|---|------|------|
| 1 | アプリケーションの機能改修 | 移行方式がR1のため、機能変更は最小限（接続先変更等のみ） |
| 2 | 住基ネット側のシステム改修 | 県庁管轄であり、さくら市の責任範囲外 |
| 3 | 庁内AD（LDAP）サーバーの移行 | オンプレミス継続（GCからLDAP参照のみ） |
| 4 | 利用者端末の整備 | 既存端末を継続利用 |
| 5 | 業務プロセスの見直し | 本プロジェクトでは現行踏襲 |

## 3. システム要件

### 3.1 機能要件詳細

#### REQ-F-001: マイナンバーカード認証

```
【REQ-F-001: マイナンバーカード認証】

1. 概要
   住民がマイナンバーカードの利用者証明用電子証明書を用いて
   Webポータルにログインする機能

2. 入出力
   入力: 利用者証明用電子証明書（JPKI）
   出力: 認証トークン（JWT）、セッション情報

3. 前提条件
   - マイナンバーカードにICチップが搭載されていること
   - 利用者端末にカードリーダーまたはNFC対応スマートフォンがあること
   - JPKI認証局との通信が可能であること

4. 処理フロー
   Step 1: 住民が「ログイン」ボタンをクリック
   Step 2: カード読み取り画面を表示
   Step 3: マイナンバーカードの電子証明書を読み取り
   Step 4: JPKI認証局にて電子証明書の有効性を検証
        - 失効時: 「証明書が失効しています」エラー表示
        - 有効時: Step 5へ
   Step 5: 住民情報DBと照合し、利用者を特定
   Step 6: JWTトークンを発行、セッション開始
   Step 7: ダッシュボードへリダイレクト

5. エラー処理
   - カード読み取り失敗: 「カードを正しくセットしてください」メッセージ
   - 証明書失効: 「電子証明書が失効しています。市役所窓口で更新してください」
   - 未登録利用者: 「本サービスへの登録が必要です」→ 登録画面へ誘導
   - タイムアウト（30秒）: 「時間切れです。再度お試しください」

6. 優先度
   Must（本機能がなければ住民向けサービス利用不可）
```

#### REQ-F-103: 住民情報照会

```
【REQ-F-103: 住民情報照会】

1. 概要
   職員が氏名・住所・マイナンバー等の検索条件で住民情報を照会する機能。
   グループ権限に基づき、表示項目が制御される。

2. 入出力
   入力: 検索条件（氏名、住所、生年月日、マイナンバー（下4桁可））
   出力: 住民情報一覧（氏名、住所、生年月日、世帯情報等）

3. 前提条件
   - 職員がAD認証済みであること
   - 照会権限を持つグループに所属していること
   - マイナンバー表示には特別権限（市民課長以上）が必要

4. 処理フロー
   Step 1: 職員が検索条件を入力
   Step 2: バリデーション実行（最低1項目の入力必須）
   Step 3: DB検索実行（インデックス利用、1秒以内）
   Step 4: グループ権限に基づくフィルタリング
        - 市民課: 全項目表示可
        - 税務課: 税務関連項目のみ表示可
        - 福祉課: 福祉関連項目のみ表示可
   Step 5: 検索結果を一覧表示（ページネーション: 20件/ページ）
   Step 6: 監査ログに記録（照会者、検索条件、検索日時、表示件数）

5. エラー処理
   - 検索条件不足: 「最低1項目を入力してください」
   - 該当なし: 「該当する住民情報が見つかりません」
   - 権限不足: 「この情報を照会する権限がありません」
   - DB接続エラー: 「システムエラーが発生しました。管理者に連絡してください」

6. 優先度
   Must（庁内業務の基幹機能）

7. 監査要件
   - 全照会操作を監査ログに記録（保持期間: 1年）
   - マイナンバー照会は特別ログとして別途記録（保持期間: 5年）
```

## 5. 移行要件

### 5.1 移行方式

| 項目 | 内容 |
|------|------|
| 移行方式 | R1（リホスティング） |
| 概要 | Heroku上のNode.jsアプリケーションをGC(AWS)のEC2/ECS上にリホスト。DBはHeroku PostgreSQL → RDS PostgreSQL、RedisはElastiCache、S3は既存AWS S3からGCアカウントのS3へコピー |
| アプリケーション変更 | 最小限（接続先エンドポイント変更、環境変数変更、LGWAN接続対応のみ） |
| 並行稼働期間 | 2週間（2027年3月中旬～3月31日） |

### 5.2 移行対象データ

| # | データ種別 | 現行環境 | 移行先 | データ量 | 移行方式 |
|---|-----------|---------|--------|---------|---------|
| 1 | 住民基本情報DB | Heroku PostgreSQL | RDS PostgreSQL | 約5GB | pg_dump/pg_restore |
| 2 | 申請・届出データDB | Heroku PostgreSQL | RDS PostgreSQL | 約15GB | pg_dump/pg_restore |
| 3 | 監査ログDB | Heroku PostgreSQL | RDS PostgreSQL | 約500GB | pg_dump（増分）+ AWS DMS |
| 4 | 添付ファイル | AWS S3（現行アカウント） | S3（GCアカウント） | 約200GB | S3 Cross-Account Copy |
| 5 | Redisデータ | Heroku Redis | ElastiCache Redis | 約1GB | 移行不要（セッション再作成） |
| 6 | 環境設定・秘密情報 | Heroku Config Vars | Parameter Store / Secrets Manager | - | 手動移行 |

### 5.3 移行スケジュール（概要）

| フェーズ | 期間 | 内容 |
|---------|------|------|
| Phase 1: 環境構築 | 2026年7月-9月 | GCアカウント設定、VPC構築、LGWAN接続、セキュリティ設計実装 |
| Phase 2: 開発・テスト環境移行 | 2026年10月-11月 | dev/stg環境構築、アプリケーションデプロイ、接続確認 |
| Phase 3: 結合テスト | 2026年12月-2027年1月 | 外部IF連携テスト、性能テスト、セキュリティテスト |
| Phase 4: データ移行リハーサル | 2027年2月 | 本番データを用いた移行リハーサル（2回実施） |
| Phase 5: 本番移行 | 2027年3月中旬 | 本番データ移行、並行稼働開始 |
| Phase 6: 並行稼働・検証 | 2027年3月中旬-3月31日 | 並行稼働（2週間）、Go/No-Go判定 |
| Phase 7: 本稼働 | 2027年3月31日 | Heroku停止、GC本稼働 |

### 5.4 移行制約

| # | 制約事項 | 対応方針 |
|---|---------|---------|
| 1 | 本番データ移行時のサービス停止は最大6時間（土日深夜） | 段階移行方式：大容量データ（監査ログ）は事前にDMSで増分同期、最終カットオーバーは差分のみ |
| 2 | マイナンバーを含むデータの移行は暗号化必須 | pg_dumpの出力をKMS暗号化したS3経由で転送 |
| 3 | 住基ネット接続切替は県庁との調整が必要（申請2ヶ月前） | 2027年1月末までに切替申請を提出 |
| 4 | コンビニ交付連携先のVPN切替は事業者との調整が必要 | 2026年12月末までに切替スケジュールを確定 |
| 5 | 切戻し時はHeroku環境を2027年4月末まで維持 | Heroku環境のスケールダウン（最小構成）で維持 |

### 5.5 Go/No-Go判定基準

| # | 判定項目 | 合格基準 |
|---|---------|---------|
| 1 | 全機能テスト | 全テストケース合格（Critical/High不具合ゼロ） |
| 2 | 性能テスト | レスポンスタイムp95が基準値以内 |
| 3 | セキュリティテスト | Critical/High脆弱性ゼロ |
| 4 | データ整合性 | 移行前後のレコード数・チェックサム一致（100%） |
| 5 | 外部IF連携 | 全IF（IF-001～IF-006）の正常通信確認 |
| 6 | 監視・アラート | 全アラームの発火テスト完了 |
| 7 | 切戻し手順 | 切戻しリハーサル完了（RTO内に復旧確認） |
| 8 | 運用チーム準備 | Runbook完成、運用者トレーニング完了 |

### C. 用語集

| 用語 | 定義 |
|------|------|
| GC | ガバメントクラウド。デジタル庁が整備する政府・自治体向けクラウドサービス |
| GCAS | ガバメントクラウド補助システム。GCを利用するための申請・承認プロセスおよび管理ポータル |
| ISMAP | 政府情報システムのためのセキュリティ評価制度。クラウドサービスの安全性評価 |
| LGWAN | 総合行政ネットワーク。自治体間を結ぶ行政専用の閉域ネットワーク |
| JPKI | 公的個人認証サービス。マイナンバーカードの電子証明書による認証基盤 |
| TGW | Transit Gateway。複数VPCおよびオンプレミスネットワークを集約接続するAWSサービス |
| RTO | Recovery Time Objective。障害発生からサービス復旧までの目標時間 |
| RPO | Recovery Point Objective。障害発生時に許容されるデータ損失の最大時間幅 |
| PITR | Point-in-Time Recovery。任意の時点へのデータベース復旧機能 |
| RBAC | Role-Based Access Control。ロール（役割）に基づくアクセス制御方式 |
| SLA | Service Level Agreement。サービス水準に関する合意・契約 |
| R1 | リホスティング。既存システムをIaaS上に移行し、一部マネージドサービスに置換する移行方式 |
| Multi-AZ | 複数のアベイラビリティゾーンにリソースを配置する冗長構成 |
| WAF | Web Application Firewall。Webアプリケーションへの攻撃を検知・防御する仕組み |
| CMK | Customer Managed Key。利用者が管理するKMS暗号化キー |
| DMS | Database Migration Service。AWS上のデータベース移行サービス |
| CEP | 契約企業プロフィール。GCの申請時に提出する企業情報・セキュリティ情報 |
