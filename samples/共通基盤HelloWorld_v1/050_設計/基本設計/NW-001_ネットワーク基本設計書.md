## 1. 概要・目的

### 1.1 背景

本案件は同一の Spring Boot 製 Hello World ワークロードを 3 つのバッチ／非同期アーキテクチャパターンで構築・見積比較する検証案件であり（根拠: [PROF-001 §1.1](../../00_案件立ち上げ/PROF-001_案件プロファイル.md)）、ネットワーク複雑度は「複雑」（LGWAN接続＋共同利用テナント分離＋閉域）と判定されている（根拠: [PROF-001 §6](../../00_案件立ち上げ/PROF-001_案件プロファイル.md)）。本書は [GC-002 §5.2](./GC-002_GC環境システム全体構成基本設計書.md) で提示されたテナントVPC・サブメット区分を **具体的なCIDR・ルーティング・接続構成として確定**する基本設計書である。

### 1.2 目的・スコープ

- **対象**: テナントVPC（初期2テナント＋将来N拡張）のCIDR/サブネット設計、Multi-AZ冗長、ルーティング方針、Network Hub（TGW/DX/LGWAN）接続、オンライン2経路（パブリック/プライベート）、3パターン（A/B/C）のNW差分、VPC Endpoint/DNS、SG/NACL設計方針。
- **本書のレベル**: 基本設計（CIDR帯・サブネット区分・接続トポロジ・SG/NACLの方針確定が主眼。詳細パラメータ値・IaC実装・SGルールの完全な列挙は後続フェーズ/SEC設計と連携）。
- **スコープ外**: 実際のVPC/ルート/SGの作成（設計に留める）、LGWAN/DX回線の実申請（プロセス提示のみ）、ネットワークテストの実施（計画のみ）、DR（ap-northeast-3）の実装（構造のみ確保）。

### 1.3 制約条件・前提条件

| # | 前提・制約 | 出所 |
|---|----------|------|
| 1 | テナント分離は **VPC/サブネット/タグ分離**（QA-003仮採用、アカウント分離は将来オプション） | GC-002 §4.2 |
| 2 | テナントA VPC=10.20.0.0/16、テナントB VPC=10.21.0.0/16、将来N=10.2x.0.0/16 | GC-002 §4.1 |
| 3 | Network Hub Account に TGW / Direct Connect / LGWAN接続を集約（Shared Services OU） | GC-002 §4.1 |
| 4 | 自動適用層（Network Base＝基盤VPC/ルーティング/DNSの一部）は **上書きしない**。テナントVPCはCDK（必須適用）で構築 | GC-002 §3.1, §4.4 |
| 5 | リージョンは ap-northeast-1（東京）主、ap-northeast-3（大阪）はDR候補（本案件はDRスコープ外） | GC-002 前提8 |

## 3. 設計方針

### 3.1 基本設計原則

1. **テナント毎独立VPC＋CIDR重複排除**。テナント間通信は原則遮断し、必要時のみTGWルートテーブルで明示許可する（マイクロセグメンテーション）。
2. **共通サブネットテンプレートを全テナントに適用**（比較の公正性）。サブネット区分・第3オクテットの割当規則を統一し、テナント差はVPC第2オクテットのみとする。
3. **Hub-and-Spoke**（TGW中心）。テナントVPC↔Network Hub↔LGWAN/DX/他テナントの経路をTGWに集約し、フルメッシュPeeringを避ける（拡張性・保守性）。
4. **閉域優先**。プライベートサービスおよびバッチ/非同期はインターネット非経由。AWS API は VPC Endpoint 経由で閉域アクセス。NAT GW は限定用途（外部HTTPS取得が必要な場合のみ）。
5. **自動適用層非上書き**（GC-002 §3.1）。CDKはテナントVPC（必須適用Network Base）以下のみ構築。基盤側CloudTrail/Config/ログ集約のNW的前提は参照に留める。
6. **Multi-AZ冗長**（ap-northeast-1a / 1c）。各サブネット区分をAZ対で配置。SPOFを排除（NAT/TGW Attachment/Endpoint をAZ冗長）。
7. **全VPCでVPC Flow Logs有効・KMS CMK暗号化**（CEP/ConMon要件、GC-002 §4.5）。

### 3.2 デジタル庁GCAS準拠事項

| 項目 | 準拠内容 |
|------|---------|
| Network Base（テンプレート第1層・必須適用） | テナントVPCはCDKで構築。CIDRはGCAS推奨範囲（10.0.0.0/8内）に収納（GC-002 §4.4 Level2） |
| リージョン制限 | ap-northeast-1/3 のみ（SCP DenyRegionRestriction準拠） |
| タグ統制 | 全NWリソースに environment/owner/cost_center/project/compliance=ismap/tenant を付与（GC-002 §4.6） |
| ConMon/CEP | VPC Flow Logs全VPC、Security OUへログ集約（GC-002 §4.5 CEPチェック充足） |

## 4. VPC / CIDR / サブネット設計

> VPC詳細図: ![VPC詳細図](./diagrams/NW-002-vpc-detail.drawio)
> 全体構成（経路俯瞰）は GC-002 全体構成図を参照。本書は TGW接続図（NW-003）とデータフロー図（NW-004）を追加。

### 4.1 VPC一覧

| VPC | CIDR | 用途 | 所属アカウント/OU |
|-----|------|------|-----------------|
| Network Hub VPC | 10.0.0.0/16 | TGW Attachment、DX/LGWAN終端、Inspection（将来） | Shared Services OU / Network Hub Account |
| テナントA VPC | 10.20.0.0/16 | Hello World ワークロード（オンライン＋バッチ3パターン） | Tenant Workloads OU |
| テナントB VPC | 10.21.0.0/16 | 同上（テナントB） | Tenant Workloads OU |
| テナントN VPC（将来） | 10.2x.0.0/16 | 水平拡張 | Tenant Workloads OU |

**成長余裕**: 各VPCは/16（約65,000ホスト）。後述のサブネット割当は1テナントあたり/24×最大8サブネット（2区分×2AZ＋予約）で、利用率は数%に留まる。/16内に3〜5年の拡張余地（追加サービス・AZ追加）を十分確保。

### 4.2 サブネット分割パターン（共通テンプレート）

テナントA（10.20.0.0/16）を代表例として示す。テナントB以降は第2オクテットを置換（10.21.x.x 等）するのみで同一構造。AZは ap-northeast-1a / 1c の2AZ。

| サブネット区分 | AZ-a CIDR | AZ-c CIDR | 配置リソース | 公開性 | ルート（0.0.0.0/0） |
|--------------|-----------|-----------|------------|-------|--------------------|
| **Public** | 10.20.0.0/24 | 10.20.1.0/24 | 公開ALB、NAT GW | インターネット公開（WAF経由） | → IGW |
| **Private-App** | 10.20.10.0/24 | 10.20.11.0/24 | ECS Fargate(public/private)、内部ALB | 非公開 | → NAT GW（限定）/ なし |
| **Private-Batch** | 10.20.20.0/24 | 10.20.21.0/24 | バッチ/非同期 A/B/C（§8） | 非公開 | パターン依存（§8） |
| **Protected-Data** | 10.20.30.0/24 | 10.20.31.0/24 | VPC Endpoint(IF型ENI)、データ系 | 閉域 | なし（ローカル＋Endpointのみ） |
| **TGW-Attach** | 10.20.40.0/28 | 10.20.41.0/28 | TGW ENI（VPC Attachment専用） | 閉域 | → TGW（庁内/他テナント宛） |
| 予約 | 10.20.50.0/24〜 | 10.20.51.0/24〜 | 将来拡張（追加サービス/AZ） | — | — |

**第3オクテット割当規則（全テナント共通）**: 0〜9=Public、10〜19=Private-App、20〜29=Private-Batch、30〜39=Protected-Data、40〜49=TGW-Attach、50以降=予約。これにより、テナント横断でサブネット用途がCIDRから一意に判別可能（運用フィルタ・SGルール記述の簡素化）。

### 4.3 サブネット設計の根拠

- **Public/Private-App/Private-Batch/Protected-Data の4区分**は GC-002 §5.2 を踏襲。バッチ専用サブネット（Private-Batch）を独立させることで、3パターンのNWリソース差分（§8）をサブネット単位で管理可能とし、見積按分（pattern タグ）と整合させる。
- **TGW-Attach を専用 /28 サブネット**として分離。TGW ENI を業務サブネットから隔離し、ルーティング・SG影響範囲を最小化（AWSベストプラクティス）。
- **Protected-Data はデフォルトルートを持たない**（ローカル＋Endpoint経由のみ）。閉域要件（ISMAP 通信制御）を構造的に担保。

## 5. ルーティング設計

### 5.1 ルートテーブル方針（テナントA例）

| ルートテーブル | 関連サブネット | 主要ルート |
|--------------|--------------|----------|
| RT-Public | Public-1a/1c | local(10.20/16) / 0.0.0.0/0→IGW / 192.168.0.0/16→TGW（戻り） |
| RT-Private-App | Private-App-1a/1c | local / 0.0.0.0/0→NAT GW(同AZ)※限定 / 192.168.0.0/16→TGW / S3→GW Endpoint |
| RT-Private-Batch | Private-Batch-1a/1c | local / **パターン依存**（§8）/ S3→GW Endpoint |
| RT-Protected-Data | Protected-Data-1a/1c | local のみ（＋S3 GW Endpoint）。0.0.0.0/0なし | 
| RT-TGW-Attach | TGW-Attach-1a/1c | local / 0.0.0.0/0→（なし）/ 庁内・他テナント宛のみ |

### 5.2 ルーティング優先度・トラフィック制御

- **最長一致（Longest Prefix Match）** に従う。庁内宛（192.168.0.0/16）は TGW へ明示ルート、その他外向き（0.0.0.0/0）はPublic=IGW、Private-App=NAT GW。
- **NAT GW は各AZにローカル配置**（クロスAZ通信コスト回避、gc-network-patterns準拠）。Private-App-1a→NAT(1a)、Private-App-1c→NAT(1c)。
- **テナント間通信はデフォルト遮断**。TGWルートテーブルでテナントAのCIDRをテナントBのAttachに伝搬しない（ブラックホール/非伝搬）。共有が必要な場合のみ個別ルート追加。

### 5.3 TGW ルートテーブル設計

| TGW RT | 関連Attachment | 伝搬/静的ルート |
|--------|---------------|---------------|
| TGW-RT-Tenant | テナントA/B Attach | 庁内(192.168/16)→DX/LGWAN Attach、Hub(10.0/16)→Hub Attach。**他テナントCIDRは伝搬しない** |
| TGW-RT-Shared | Network Hub Attach、DX/LGWAN Attach | テナントA(10.20/16)・テナントB(10.21/16)→各Attach |
| （分離方針） | — | テナント用とHub/DX用のRTを分離し、テナント間の横断を構造的に防止 |

## 6. LGWAN / DirectConnect / TGW 接続設計

> TGW接続図: ![TGW接続図](./diagrams/NW-003-tgw-connectivity.drawio)

### 6.1 接続トポロジ（Hub-and-Spoke）

```
[自治体庁舎/職員] ──LGWAN──> [LGCS] ──> [Network Hub: DX/LGWAN終端] ──> [TGW]
                                                                          │
                              [テナントA VPC] <──TGW Attach── [TGW] ──Attach──> [テナントB VPC]
                                  └ 内部ALB → Fargate(プライベートサービス)
```

全テナントVPCと外部接続（LGWAN/DX）を TGW に集約。テナント追加時は TGW Attachment を1つ追加するのみで疎通（フルメッシュ回避＝拡張性）。

### 6.2 LGWAN接続パターン（QA-103: 単一LGCS接続・標準帯域）

`gc-lgwan-connectivity` パターン1（LGCS経由）を基本とし、庁内↔VPCの双方向通信が必要なプライベートサービスのため DX を併用するハイブリッド構成とする。

| 項目 | 設計値（仮確定） | 根拠 |
|------|----------------|------|
| LGWAN接続方式 | LGCS経由（単一接続） | QA-103仮確定。庁内→GCの閉域経路 |
| 想定帯域 | 標準帯域（実効 ≦500Mbps想定） | Hello World検証規模。回線選択マトリクス「50〜500Mbps」帯 |
| 庁内↔VPC双方向 | **DX（Private VIF）で実現**（LGCS単独では庁内側へ到達不可） | gc-lgwan-connectivity LGWAN比較表 |
| 接続先 | Network Hub Account 終端 → TGW → テナント内部ALB | Hub集約 |

> 注: LGWAN(LGCS)はGC公開サービス向け閉域、庁内サーバ↔VPCの双方向疎通はDX/VPNが必要、という特性（gc-lgwan-connectivity比較表）に基づき、プライベートサービスの実経路はDX主・LGWAN補完とする。

### 6.3 DirectConnect構成

| 項目 | 設計値（仮定: QA-105） |
|------|---------------------|
| 接続パターン | DirectConnect Single（1Gbps×1）＋ Site-to-Site VPN バックアップ（gc-lgwan パターン3＝最高可用性） |
| VIF | Private VIF（VPC向け）。BGP ASN=64512（Private）、VLAN例=1000 |
| Direct Connect Gateway | 複数テナントVPC（10.20/16, 10.21/16…）へ TGW 経由でアタッチ |
| 帯域計算 | 平常100Mbps×ピーク3＋バックアップ200Mbps=500Mbps → 1Gbps（余裕係数2倍）で充足 |

### 6.4 冗長化方針（SPOF排除の検証）

| 経路要素 | 冗長方式 | 単一障害時の挙動 |
|---------|---------|----------------|
| DirectConnect | DX（Primary）＋ Site-to-Site VPN（Backup） | DX障害時はBGPでVPNへ自動フェイルオーバー（RTO<5分） |
| LGWAN(LGCS) | 単一接続（QA-103仮確定） | **冗長は将来課題**。庁内疎通はDX/VPN側で確保されるため、LGWAN単一でも比較検証は成立 |
| TGW | マネージドサービス（AZ冗長内包） | AZ障害耐性あり。VPC Attachは各業務サブネットAZに ENI 配置 |
| NAT GW | 各AZ独立配置 | 片AZ障害時も他AZのNAT継続。クロスAZルートは設定しない（コスト/障害分離） |
| 内部ALB / 公開ALB | Multi-AZ（1a/1c） | 片AZ障害でも継続 |
| VPC Endpoint(IF型) | 各AZにENI配置（Protected-Data 1a/1c） | 片AZ障害でも他AZ Endpoint で継続 |

> SPOF検証結果: LGWAN単一接続を除き、主要経路はすべてMulti-AZまたはPrimary/Backup冗長。LGWAN冗長は本検証スコープ外（庁内疎通はDX/VPNで担保）として明示し、本番移行時に別LGCS回線追加を推奨（§15）。

### 6.5 回線調達プロセス（両側の手配・プロセス提示のみ）

| Phase | GC側 | オンプレミス/キャリア側 | 期間目安 |
|-------|------|----------------------|---------|
| 1. ベンダー選定 | RFQ作成、SLA確認 | NTT東/KDDI等から見積取得、LGWAN対応確認 | 2〜4週 |
| 2. 申込・工事 | DX VIF設定、TGW/DXGWアタッチ | 構内配線工事、LGCS接続申込 | 6〜12週 |
| 3. テスト | 疎通/スループット/BGP収束/フェイルオーバー確認 | 回線疎通立会 | 2〜4週 |

> 本書はプロセス提示に留める（回線の実申請・構築はスコープ外）。LGWAN/LGCS手配は運営主体・自治体側の行政手続を要するため、Phase 0で早期着手を推奨。

## 7. オンライン経路設計（パブリック／プライベート）

> データフロー図: ![データフロー図](./diagrams/NW-004-data-flow.drawio)

### 7.1 パブリックサービス経路（住民向け公開）

```
[住民] → インターネット → CloudFront(+Shield) → WAF(Web ACL) → 公開ALB(Public Subnet)
        → ECS Fargate パブリックサービス(Private-App Subnet) → (VPC Endpoint経由) AWS API
```

| ホップ | コンポーネント | NW設計ポイント |
|-------|--------------|--------------|
| 1 | CloudFront + WAF | エッジで境界防御。ACM証明書(us-east-1)。OAC/ALB Originのみ許可 |
| 2 | 公開ALB | Public Subnet(10.20.0/1.0/24)、Multi-AZ。SGはCloudFront管理プレフィックスリスト/443のみ |
| 3 | Fargate(public) | Private-App Subnet。ALBターゲットグループ。SGはALBからの動的ポートのみ |
| 4 | AWS API | S3=GW Endpoint、ECR/Logs等=IF Endpoint（閉域） |

### 7.2 プライベートサービス経路（庁内・職員向け閉域）

```
[職員/庁内] → LGWAN → LGCS → DX(Private VIF) → Network Hub → TGW
            → テナントVPC TGW-Attach → 内部ALB(Private-App Subnet)
            → ECS Fargate プライベートサービス → (VPC Endpoint経由) AWS API
```

| ホップ | コンポーネント | NW設計ポイント |
|-------|--------------|--------------|
| 1 | LGWAN/LGCS/DX | 閉域。庁内CIDR(192.168.0.0/16)からのみ |
| 2 | TGW | Hub集約。TGW-RTでテナント宛のみルーティング |
| 3 | 内部ALB（internal） | Private-App Subnet。インターネット非公開。SGは庁内CIDR/TGW経路限定 |
| 4 | Fargate(private) | Private-App Subnet。Private DNS(Route53 PHZ)で名前解決 |
| 5 | AWS API | VPC Endpoint（NAT/IGW非経由の閉域） |

### 7.3 経路の分離

- パブリックとプライベートは **同一VPC内で異なる経路・SG・ALB**で分離。公開ALB=IGW経由、内部ALB=TGW経由。両者は同じPrivate-AppサブネットのFargateを別サービスとして稼働（GC-002 §5.3準拠）。
- プライベートサービスのSGは 0.0.0.0/0 を一切持たず、庁内CIDR＋TGW経路のみを許可（ゼロトラスト・デフォルト拒否）。

## 8. 3パターンのネットワーク差分

バッチ/非同期3パターン（A/B/C）は全て Private-Batch サブネット（10.20.20.0/24, 10.20.21.0/24）に配置するが、必要となるNWリソース（VPC Endpoint種別・NAT要否・SQS経路・スケール連動メトリクス経路）が異なる。見積の構築要素として漏れなく差分を整理する。

### 8.1 NWリソース差分表

| NW要素 | A: Lambda | B: AWS Batch | C: SQS+ECS Fargate | 備考 |
|--------|-----------|--------------|--------------------|------|
| 配置サブネット | Private-Batch（VPC Lambda=ENI） | Private-Batch（Fargate/EC2 CE） | Private-Batch（Fargateワーカー） | 全パターン共通サブネット |
| ENI / タスクENI | Lambda ENI（VPC接続時） | CE タスクENI | サービスタスクENI | いずれもPrivate-Batchに払い出し |
| **S3 (GW Endpoint)** | 必要 | 必要 | 必要 | 成果物出力。全パターン共通（GW型のため追加コストなし） |
| **ECR (IF Endpoint)** | 不要（コンテナ非使用） | **必要**（イメージpull） | **必要**（ワーカーimage pull） | A=Lambdaはzip/コンテナ選択次第。本書はzip前提でECR不要と仮定 |
| **Logs (IF Endpoint)** | 必要 | 必要 | 必要 | CloudWatch Logs閉域送信 |
| **SQS (IF Endpoint)** | 必要（DLQ） | 任意（DLQ無しなら不要） | **必要**（メインキュー＋DLQ） | C は SQS が処理経路の中核 |
| **Batch (IF Endpoint)** | 不要 | **必要** | 不要 | AWS Batch API 閉域呼び出し |
| **STS / SSM / Monitoring (IF)** | 必要 | 必要 | 必要 | 実行ロール・メトリクス。共通 |
| **NAT GW 要否** | 原則不要（Endpoint閉域で完結） | 原則不要（同上） | 原則不要（同上） | 外部HTTPS取得が無ければNAT不要。**閉域優先で全パターンNATなしを基本** |
| EventBridge 経路 | ルール→Lambda（VPC外イベント面） | ルール→Batch Job投入 | ルール/Producer→SQS | トリガ入口は共通（EventBridge/Fargate/S3イベント） |
| スケール連動メトリクス経路 | 同時実行数（サービス側） | Job Queue深度（Batch側） | **SQS ApproximateNumberOfMessages→CloudWatch→App Auto Scaling** | C のみキュー深度連動でEndpoint(Monitoring/SQS)依存が高い |
| 追加SG | Lambda用SG | CE/ジョブ用SG | ワーカーサービス用SG | いずれもEndpoint宛443・S3のみ許可 |

### 8.2 差分の見積・設計上の含意

- **Endpoint数の差**: B（Batch）は ECR＋Batch Endpoint が追加で最多。C（SQS+Fargate）は SQS＋ECR が中核。A（Lambda/zip）は最少（S3/Logs/SQS(DLQ)/STS程度）。→ **構築工数・Endpoint時間課金は B > C > A** の傾向（GC-002 §6.4の構築工数相対と整合）。
- **NATは全パターン不要を基本**とし、閉域完結（ISMAP通信制御）。万一外部HTTPS（例: 外部時刻同期・パッケージ取得）が必要な場合のみPrivate-AppのNAT GWを共用（Private-Batchから同AZ NATへルート追加）。この要否はアプリ要件で確定（QA積み）。
- **C のスケール経路**: SQSキュー深度→CloudWatch→Application Auto Scaling のメトリクス経路が成立するよう、Monitoring/SQS Endpoint を必須とする。スケーリング設計の肝（GC-002 §6.3）はNW的にはEndpoint依存として表れる。

### 8.3 共通VPC Endpoint一覧（テナントVPC、IF型はProtected-Data 1a/1cに配置）

| Endpoint | 種別 | 用途 | 利用パターン |
|----------|------|------|------------|
| com.amazonaws.ap-northeast-1.s3 | Gateway | 成果物・ログ・イメージ層 | 共通（A/B/C/オンライン） |
| dynamodb | Gateway | （将来利用予約） | — |
| ecr.api / ecr.dkr | Interface | コンテナイメージpull | B/C/オンライン |
| logs | Interface | CloudWatch Logs | 共通 |
| sqs | Interface | キュー/DLQ | A(DLQ)/C |
| batch | Interface | AWS Batch API | B |
| sts | Interface | AssumeRole | 共通 |
| ssm / ssmmessages / ec2messages | Interface | Systems Manager | 共通（運用） |
| monitoring | Interface | CloudWatch メトリクス | 共通（特にC） |
| kms | Interface | CMK復号 | 共通（暗号化必須） |

## 9. VPC Endpoint / DNS 設計

### 9.1 VPC Endpoint配置

- **Gateway型（S3/DynamoDB）**: ルートテーブル（RT-Private-App/Batch/Protected-Data）に関連付け。追加課金なし、閉域でS3到達。
- **Interface型**: Protected-Data サブネット（10.20.30.0/24, 10.20.31.0/24）の各AZにENI配置。Private DNS有効化でサービス標準FQDNがVPC内で自動解決。SGは sg-vpc-endpoint（VPC内からの443のみ許可）。

### 9.2 DNS / Route53 設計

| 項目 | 設計 |
|------|------|
| Private Hosted Zone | `internal.helloworld.go.jp`（仮）。テナント毎にPHZを分離（tenant-a.internal… / tenant-b.internal…）し、VPC関連付けで名前解決を分離 |
| レコード例 | `private.tenant-a.internal.helloworld.go.jp` → 内部ALB（10.20.10.x） |
| VPC Endpoint名前解決 | Interface Endpoint の Private DNS で AWS サービスFQDNをVPC内解決（NAT非経由） |
| ハイブリッド名前解決 | 庁内ドメイン（例: `*.lg.jp`内部名）は Route53 Resolver の条件付きフォワーディングで庁内DNS（192.168.x.x:53）へ転送。逆に庁内→VPC内名は Inbound Resolver Endpoint で解決 |
| Resolver Endpoint | Inbound/Outbound Endpoint を Network Hub または各テナントProtected-Dataに配置（庁内⇔GCの双方向名前解決） |

### 9.3 名前解決フロー

| 解決対象 | 解決元 | 経路 |
|---------|-------|------|
| AWSサービスFQDN（s3/ecr等） | VPC内リソース | VPCリゾルバ→Interface Endpoint Private DNS（閉域） |
| 内部ALB（プライベートサービス） | VPC内 / 庁内 | PHZ / Inbound Resolver Endpoint |
| 庁内システム名 | VPC内リソース | Outbound Resolver Endpoint→条件付きフォワード→庁内DNS |
| 公開サービス（CloudFront） | 住民 | パブリックDNS（Route53 Public/委任） |

## 10. セキュリティグループ / NACL 設計方針

> 詳細なSGルール・NACLルールの完全な列挙は後続のセキュリティ設計書（SEC）と連携。本書は方針・骨子を提示する。

### 10.1 設計原則（ゼロトラスト・デフォルト拒否）

1. **デフォルト拒否**。全SGは明示的に許可した通信のみを通す。0.0.0.0/0 のInboundは公開ALB（443）に限定。
2. **SG参照（source security group）を優先**。CIDRハードコードを避け、`sg-internal-alb` → `sg-fargate` のようにSG間参照でルールを記述（保守性・ルール数削減）。
3. **NACLはサブネット境界の粗いガード**として補助的に使用（Stateless）。主防御はSG（Stateful）。
4. **ルール数を管理可能範囲に**（SG単位 概ね50ルール以下、gc-network-patterns準拠）。区分別SGを分割し肥大化を防ぐ。

### 10.2 SG設計骨子（テナントA）

| SG名 | 主なInbound | 主なOutbound |
|------|------------|------------|
| sg-public-alb | 443 ← CloudFrontマネージドプレフィックスリスト | Fargate(public)宛 動的ポート |
| sg-internal-alb | 庁内CIDR(192.168/16)/TGW経路 ← 443 | Fargate(private)宛 動的ポート |
| sg-fargate-app | sg-public-alb / sg-internal-alb ← アプリポート | 443→VPC Endpoint(sg-vpc-endpoint)、S3 |
| sg-batch（A/B/C共通骨子） | （Inbound原則なし＝アウトバウンド処理） | 443→Endpoint、SQS/Batch/S3/Logs |
| sg-vpc-endpoint | VPC内(10.20/16) ← 443 | —（Stateful戻り） |
| sg-tgw-attach | 庁内/他テナント許可分のみ | local |

### 10.3 NACL方針

| サブネット | NACL方針 |
|-----------|---------|
| Public | 80/443 In、エフェメラル(1024-65535)戻り許可、その他Deny |
| Private-App / Batch | VPC内＋TGW(192.168/16)＋エフェメラル許可。インターネット直Inは無し |
| Protected-Data | VPC内のみ。0.0.0.0/0 In/Out なし（閉域の二重化） |
| TGW-Attach | TGW経路（庁内/許可テナント）のみ |

> ゼロトラスト・テナント条件付きIAM・KMS CMKアクセス制御等の詳細はSEC設計書で確定（GC-002 §8の領域提示と連携）。
