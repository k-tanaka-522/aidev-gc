## 1. 概要・目的

### 1.1 背景

本案件は同一の Spring Boot 製 Hello World ワークロードを 3 つのバッチ／非同期アーキテクチャパターン（A: Lambda / B: AWS Batch / C: SQS+ECS Fargate）で構築・見積比較する検証案件であり、セキュリティレベルは「高（ISMAP対応・KMS CMK・DS-310準拠・ConMon/CSPM常時監視）」と判定されている（根拠: [PROF-001 §5](../../00_案件立ち上げ/PROF-001_案件プロファイル.md)）。本書は [GC-002 §8](./GC-002_GC環境システム全体構成基本設計書.md) で領域提示されたセキュリティ考慮事項と、[NW-001 §10](./NW-001_ネットワーク基本設計書.md) のSG/NACL方針を **具体的なIAM/KMS/境界防御/ConMon/ISMAPマッピングとして確定** する基本設計書である。

### 1.2 目的・スコープ

- **対象**: GCAS-SSO/Permission Set方針、最小権限IAM（サービスロール群）、テナント境界のIAM分離、KMS CMK方針（テナント別キー）、保存時/転送時暗号化、WAF/Shield/SG/NACL詳細、ゼロトラスト（DS-310）、ConMon/CSPM（GuardDuty/SecurityHub/Config Rules/IAM Access Analyzer/CloudTrail）、ISMAP305インフラ担当分マッピング、3パターンのセキュリティ差分。
- **本書のレベル**: 基本設計（IAMロール骨子・KMSキー設計・SG/NACL詳細方針・ConMon設定項目・ISMAP対応方針の確定が主眼。実際のIAMロール作成・KMSキー生成・各サービス有効化はスコープ外＝設計に留める）。
- **スコープ外**: 実際のIAM/KMS/WAF/GuardDuty等の作成・有効化（設計に留める）、Security Base自動適用層の改変（参照のみ）、外部ペネトレーションテストの実施（PROF-001 §5.2、必要時別途）、個人情報データを用いた暗号化テスト（禁止）。

### 1.3 制約条件・前提条件

| # | 前提・制約 | 出所 |
|---|----------|------|

## 3. 設計方針

### 3.1 基本設計原則

1. **最小権限の原則（Least Privilege）**。全Permission Set／サービスロールは必要なAction/Resourceのみを付与し、Permission Boundaryで上限を画定する。IAMユーザーは発行しない（SSO/STS一時クレデンシャルのみ）。
2. **ゼロトラスト（Deny All デフォルト）**。SG/NACL/IAM/リソースポリシーいずれも「明示許可のみ」。DS-310のC-1〜C-7に構造的に対応（§6.5）。
3. **暗号化はデフォルト**。保存時はKMS CMK（テナント別）、転送時はTLS1.2+。未暗号化アップロードはバケットポリシー/SCPで拒否。
4. **テナント境界をIAM/KMS/NW三層で担保**。IAM条件（タグ/リソースARN）＋テナント別CMKキーポリシー＋NW分離（NW-001）の多層でクロステナント参照を防止。
5. **自動適用層非上書き**（最重要）。Security Baseが提供する統制は参照のみ。本設計はテナントWorkloads側の追加統制に限定。
6. **ConMonは検出＋自動応答の両側**を設計。Config Rules/GuardDuty/SecurityHub/Access Analyzerで継続的検証（Continuous Verification）を実装。
7. **すべてのセキュリティルールに根拠を付す**（ISMAP305管理策番号・DS-310要件・NW/GC設計との連携）。

### 3.2 デジタル庁GCAS準拠事項

| 項目 | 準拠内容 |
|------|---------|
| Security Base（テンプレート第1層・自動適用） | IAM Identity Center/KMS基盤/ログ基盤は上書き禁止。本設計はCMK/サービスロール/SGを委任範囲で追加（GC-002 §4.4 Level1〜2） |
| SCP（Governance・自動適用） | ガードレール改変・リージョン逸脱・タグ欠落拒否を前提。テナントOU追加制約を提示（GC-002 §4.3） |
| タグ統制 | 全セキュリティ関連リソースに compliance=ismap 等を付与（SCP/Tag Policyで強制） |
| ConMon/CEP | GuardDuty/SecurityHub/Config Rules/IAM Access Analyzer/VPC Flow Logs/CloudTrail Org単位（GC-002 §4.5 CEPチェック充足） |

## 4. IAM設計（認証・認可・最小権限・テナント境界）

> セキュリティ構成図: ![セキュリティ構成図](./diagrams/SEC-001-security-posture.drawio)

### 4.1 認証設計（GCAS-SSO / CEP）

GC-002 §4.5 を継承し、認証はIAM Identity Center（CEP）に一元化する。**IAMユーザーは原則発行しない**（TAIL-001 §5.3）。

| 項目 | 設計方針 | 根拠 |
|------|---------|------|
| IdP | IAM Identity Center 中核。コーポレートIdP（Azure AD/Okta）があればSAML/OIDCフェデレーション | DS-310 C-6 / ISMAP AC-3 |
| 認証フロー | ユーザー → IdP → MFA確認 → Identity Center → Permission Set割当 → AssumeRole（STS一時クレデンシャル） | gc-zero-trust 柱1 |
| MFA | **管理者/特権は必須（TOTP＋Passkey）**。一般は段階的必須化（QA-109） | ISMAP AC-3 / DS-310 C-6 |
| セッション | Permission SetのセッションTTLを最小化（管理者1h、開発者4h、監査ReadOnly8h）。STS TTLで一時化 | ISMAP AC-14 |
| 緊急アクセス | break-glass 管理者（Security OU側、自動適用層）。SSO障害時手順を文書化、利用はCloudTrailで監査 | ISMAP AC-5 |
| 共有アカウント | **禁止**。Identity-based Policy のみ使用 | ISMAP AC-6 |

### 4.2 認可設計（Permission Set 骨子）

GC-002 §4.5 のグループ⇔Permission Set骨子を継承し、**最小権限・テナント条件付き**に具体化する。Permission Set数は5（過度でない範囲、品質基準 5〜20/Project に適合）。

| グループ | Permission Set | 主な権限範囲（Action例） | テナント条件 | Permission Boundary |
|---------|----------------|------------------------|------------|---------------------|
| GC-Admin | OrgAdmin | Org/SCP参照、Shared/Tenant管理。**自動適用層リソースは不可** | 全テナント | PB-Admin（IAM/Org破壊系・ガードレール改変をDeny） |
| GC-Network | NetworkAdmin | TGW/DX/VPC/Route53/SG（NW-001範囲） | 全テナント（NW共通） | PB-Network（データ削除・IAM変更をDeny） |
| GC-Security | SecurityAdmin | SecurityHub/GuardDuty/Config/Access Analyzer（読取＋是正）、KMS管理 | 全テナント（横断統制） | PB-Security（CloudTrail/Config停止をDeny） |
| GC-AppDev | TenantDeveloper | Fargate/Lambda/Batch/SQS/ECR/S3/Logs（最小権限） | **テナント条件付き**（タグ/ARN） | PB-Developer（IAM/KMS/Org/破壊系をDeny） |
| GC-Auditor | ReadOnlyAuditor | Org/Billing/ログ/構成の参照のみ | 全テナント（参照） | PB-ReadOnly（全Write系をDeny） |

### 4.3 Permission Boundary（権限の上限画定）

開発者ロール（TenantDeveloper）のPermission Boundary例。**危険なAction（IAM/KMS管理/Org/ガードレール改変）を恒久的にDeny**し、付与ポリシーが過大でも上限を超えられない構造とする（gc-zero-trust / ISMAP AC-2）。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowWorkloadServices",
      "Effect": "Allow",
      "Action": [
        "ecs:*", "lambda:*", "batch:*", "sqs:*",
        "ecr:*", "s3:*", "logs:*", "cloudwatch:*",
        "application-autoscaling:*", "events:*"
      ],
      "Resource": "*"
    },
    {
      "Sid": "DenyDangerousActions",
      "Effect": "Deny",
      "Action": [
        "iam:*", "organizations:*", "account:*",
        "kms:ScheduleKeyDeletion", "kms:DisableKey", "kms:PutKeyPolicy",
        "cloudtrail:StopLogging", "cloudtrail:DeleteTrail",
        "config:StopConfigurationRecorder", "config:DeleteConfigurationRecorder",
        "guardduty:DeleteDetector", "securityhub:DisableSecurityHub",
        "ec2:DeleteFlowLogs"
      ],
      "Resource": "*"
    },
    {
      "Sid": "DenyOutsideAllowedRegions",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["ap-northeast-1", "ap-northeast-3"] }
      }
    }
  ]
}
```

> SCP（GC-002 §4.3）が組織レベルのガードレール、Permission Boundaryがロールレベルの上限。両者は重畳して最小権限を担保する（責務分界: SCP=組織、PB=ロール、付与ポリシー=実権限）。

### 4.4 テナント境界のIAM分離（QA-003 VPC/タグ分離を反映）

VPC/タグ分離方式（GC-002 §4.2）では、IAM条件によってテナント横断アクセスを禁止する。TenantDeveloperは自テナントのリソースのみ操作可能とする。

```json
{
  "Sid": "TenantScopedAccess",
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject", "sqs:SendMessage", "sqs:ReceiveMessage"],
  "Resource": [
    "arn:aws:s3:::helloworld-tenant-${aws:PrincipalTag/tenant}-*/*",
    "arn:aws:sqs:ap-northeast-1:*:helloworld-tenant-${aws:PrincipalTag/tenant}-*"
  ],
  "Condition": {
    "StringEquals": { "aws:ResourceTag/tenant": "${aws:PrincipalTag/tenant}" }
  }
}
```

| 分離軸 | IAM実装 | 補完層 |
|-------|---------|-------|
| リソース帰属 | `aws:ResourceTag/tenant == aws:PrincipalTag/tenant` 条件、ARN命名（`*-tenant-A-*`） | タグ統制（GC-002 §4.6） |
| データ | テナント別S3バケットポリシー（他テナントPrincipalをDeny） | テナント別CMKキーポリシー（§5.4） |
| 暗号鍵 | テナント別CMKのキーポリシーで自テナントロールのみ kms:Decrypt 許可 | NW分離（NW-001 §5.2 テナント間遮断） |
| ネットワーク | （NW-001 §5.2）テナント間通信デフォルト遮断 | SG/NACL（NW-001 §10） |

> **三層防御**: IAM条件（タグ/ARN）× KMSキーポリシー × NW分離。いずれか単独でなく重畳でクロステナント参照を防止（DS-310 C-2 / ISMAP AC-2）。

### 4.5 サービスロール設計（最小権限・3パターン対応）

オンライン共通＋3パターン固有のサービスロールを定義する。**実行ロールとサービスロールを分離**（ISMAP AC-12 サービスアカウント管理）し、それぞれ必要最小のAction/Resourceに限定。全ロールにPermission Boundary（PB-ServiceRole）を付与。

| ロール | 区分 | 主な許可Action | リソース範囲 | 利用パターン |
|-------|------|--------------|------------|------------|
| ecsTaskExecutionRole | オンライン共通 | ecr:GetDownloadUrlForLayer/BatchGetImage、logs:CreateLogStream/PutLogEvents、kms:Decrypt（ECR/Logs CMK） | テナントECR/Logsグループ | 全（オンライン） |
| ecsTaskRole-online | オンライン共通 | s3:Get/PutObject、kms:Decrypt/GenerateDataKey（データCMK）、sqs:SendMessage（C向け起動） | テナントS3/SQS | 全（オンライン） |

### 5.2 CMK方針（QA-104: テナント別キー採用 ＋ 共通鍵との比較）

**採用: テナント別CMK**。判断根拠を共通鍵と比較して記載する。

| 観点 | テナント別CMK（**採用**） | 共通CMK（不採用） |
|------|------------------------|------------------|
| テナント分離強度 | ◎ キーポリシーで自テナントロールのみ復号許可。クロステナント復号を構造的に遮断 | △ 全テナントが同一鍵を参照。IAM条件のみで分離（単層） |
| ブラスト半径 | 小（1テナントの鍵漏洩が他に波及しない） | 大（共通鍵漏洩で全テナント影響） |
| 監査トレーサビリティ | ◎ CloudTrailの kms:Decrypt がテナント単位で識別可能 | △ 鍵単位では識別不可、暗号化コンテキスト依存 |
| コスト | 鍵数増（テナント数×用途）。CMK $1/月/鍵＋API課金 | 最少（鍵数少） |
| 運用負荷 | 中（鍵ローテーション・ポリシー管理がテナント数分） | 低 |
| ISMAP/DS-310適合 | ◎ テナント分離・最小権限・監査の各要件に最も整合 | △ |
| 本案件適合 | **◎**（共同利用・複数自治体テナント・ISMAP高要件） | × |

**判断**: 共同利用方式で複数自治体テナントを扱い、ISMAP高要件・DS-310テナント分離が必須であるため、分離強度・ブラスト半径・監査性で優位なテナント別CMKを採用する。コスト増（鍵数）は Hello World 規模では軽微であり、分離価値が上回る（GC-002 §4.2テナント分離方針・§10と整合）。

### 5.3 KMSキー設計（用途×テナント）

| キー種別 | 用途 | 範囲 | 自動ローテーション | マルチRegion | 管理主体 |
|---------|------|------|------------------|------------|---------|
| 基盤キー（参照） | CloudTrail/Configログ暗号化 | Org/Security OU | 年1回（自動適用） | 自動適用層判断 | **Security OU（参照のみ）** |
| **テナント別データCMK** | S3/SQS/EBS/DynamoDB（テナントA/B/N各々） | テナント単位 | **有効（年1回）** | 単一Region（QA-107、DR時にレプリカ化） | Security Team（本設計） |
| アプリ共通CMK | ECR/Logs/Lambda環境変数/Secrets | テナント横断のアプリ層 | 有効（年1回） | 単一Region | Security Team（本設計） |

**マルチRegion要否（QA-107）**: 本案件はDR（ap-northeast-3）がスコープ外のため、**単一Region CMKを基本**とする。理由: マルチRegionキーは複数Regionで同一鍵マテリアルを共有する設計であり、DRレプリケーション（S3 CRR等）でクロスRegion復号が必要になった時に有効。本案件ではクロスRegionデータ移動がなく、単一Regionで十分。DR採用時にマルチRegionキー（Primary=tokyo / Replica=osaka）へ移行できるよう、キー作成時に `MultiRegion` 化可能な設計余地を確保する（ローテーション周期・キーポリシーは共通化）。

### 5.4 テナント別CMKキーポリシー（クロステナント復号の遮断）

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnableIAMRootPermissions",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::<account-id>:root" },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "AllowTenantAServiceRolesDecrypt",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::<account-id>:role/ecsTaskRole-online-tenant-A",
          "arn:aws:iam::<account-id>:role/lambdaExecRole-A-tenant-A",
          "arn:aws:iam::<account-id>:role/batchJobRole-B-tenant-A",
          "arn:aws:iam::<account-id>:role/ecsTaskRole-worker-C-tenant-A"
        ]
      },
      "Action": ["kms:Decrypt", "kms:GenerateDataKey", "kms:DescribeKey"],
      "Resource": "*",
      "Condition": {
        "StringEquals": { "kms:EncryptionContext:tenant": "A" }
      }
    },
    {
      "Sid": "DenyCrossTenant",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "kms:Decrypt",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "kms:EncryptionContext:tenant": "A" }
      }
    }
  ]
}
```

> **暗号化コンテキスト**（`kms:EncryptionContext:tenant`）でテナントを束縛。テナントAのCMKはコンテキスト `tenant=A` のみ復号可能とし、他テナントロール・他コンテキストからの復号をDeny。IAM条件（§4.4）と二重化（DS-310 C-2/C-5 / ISMAP CR-2/CR-3）。

## 9. 3パターンのセキュリティ差分（A/B/C）

見積の構築要素として、A/B/Cそれぞれの**アタックサーフェス・必要IAMロール・暗号化ポイント**の差分を整理する（NW-001 §8のNW差分と対をなす）。

### 9.1 セキュリティ差分マトリクス

| 観点 | A: Lambda | B: AWS Batch | C: SQS+ECS Fargate |
|------|----------|--------------|-------------------|
| **アタックサーフェス** | 最小。マネージドランタイム、サーバ/OSなし、ENI（VPC）のみ。コードレベル（依存関係）が主 | 最大。EC2 CE採用時はOS/AMI/EBSが攻撃面に追加。コンテナイメージ＋ジョブ実行環境 | 中。Fargate（OSマネージド）だがコンテナイメージ＋SQSキュー（メッセージ injection）が攻撃面 |
| **OS/パッチ責務** | AWS（マネージド）。VN-1対応不要 | EC2 CE時は**利用者責務**（SSM Patch Manager＋CIS Hardened AMI、VN-1/VN-6）。Fargate CE時はAWS | AWS（Fargateマネージド） |
| **必要IAMロール** | lambdaExecRole-A（実行ロール1、**1ロール**） | batchServiceRole-B＋batchJobRole-B＋batchTaskExecutionRole-B（サービス/ジョブ/実行の3分離、**3ロール**） | ecsTaskRole-worker-C＋autoScalingRole-C（**2ロール**。ExecutionRoleはオンライン共通ecsTaskExecutionRoleを共用） |
| **ロール最小権限の肝** | Logs/S3/SQS(DLQ)/KMS。VPC Lambda ENI作成権限 | サービスロール（CE/Queue管理）とジョブロール（S3/ECR/KMS）の**分離**が肝（過大権限回避） | ワーカー（SQS受信/削除/S3/KMS）＋スケール（CloudWatch読取）の分離 |
| **暗号化ポイント** | Lambda環境変数（CMK）、S3成果物（テナント別CMK）、DLQ（CMK）、Logs（CMK） | EBS（EC2 CE時、CMK）、ECRイメージ（CMK）、S3成果物（CMK）、Logs（CMK） | **SQSメイン＋DLQ（CMK必須）**、ECRイメージ（CMK）、S3成果物（CMK）、Logs（CMK） |
| **暗号化コンテキスト** | tenant束縛（§5.4） | tenant束縛 | tenant束縛。SQSメッセージのCMK暗号化が処理経路の中核 |
| **イメージスキャン（VN-7）** | zip前提なら対象外（コンテナ採用時はECRスキャン） | **必須**（ECRイメージpull） | **必須**（ワーカーイメージ） |
| **GuardDuty保護** | Lambda Protection重要 | EC2/Malware Protection（EC2 CE時） | ECS/Runtime Monitoring |
| **WAF/境界** | （バッチは非公開、WAF対象外。オンライン共通のみ） | 同左 | 同左＋SQS Producer側のアクセス制御（IAM） |
| **主なリスク** | コールドスタート中の権限・依存関係脆弱性 | OS/AMI管理漏れ（EC2 CE）、ジョブロール過大権限 | キューへの不正メッセージinjection、DLQ未監視 |
| **ISMAP差分** | AC-12/CR-2/CR-5、VN-1不要 | **AC-12（ロール分離）/VN-1/VN-6（EC2 CE）/VN-7** 追加 | **AC-12/CR-2（SQS CMK）/VN-7**、DLQ必須 |

### 9.2 差分の見積・設計上の含意

- **IAMロール数**: A=1 < C=2 < B=3（Bはサービス/ジョブ/実行ロールの3分離で最多、かつロール分離の設計難度も B>C>A）。**設計・レビュー工数は B > C > A**（GC-002 §6.4・NW-001 §8.2の構築工数相対と整合）。
- **暗号化ポイント数**: C（SQS CMKが中核で必須）とB（EBS追加）が多い。Aは最少（zip前提でECR/EBSなし）。
- **脆弱性管理負荷**: B（EC2 CE採用時）が突出（OS/AMI/EBSパッチ責務＝VN-1/VN-6）。Fargate/Lambda（A/C）はマネージドでパッチ責務が小さい。**Bは Fargate CE を選べばVN負荷を低減できる**（設計選択肢として明記）。
- **アタックサーフェス**: A（最小）< C（中）< B（最大、EC2 CE時）。セキュリティ運用負荷も同順。
- **見積按分**: pattern タグ（GC-002 §4.6）で按分。セキュリティ固有工数（ロール設計・CMK・スキャン・パッチ）をパターン別に独立計上。

## 10. インシデント対応設計

検出→調査→対応→復旧のフローを定義する（ISMAP IR系 / DS-310 C-3）。

### 10.1 インシデント対応フロー

```
[検出] GuardDuty/SecurityHub/Config/CloudWatch Alarms/WAF
   ↓ EventBridge（Severity判定）
[通知] SNS → セキュリティチーム / SOAR(Slack)
   ↓
[調査] CloudTrail（API追跡）/ VPC Flow Logs（通信追跡）/ Logs Insights
   ↓ 影響範囲特定（テナント/リソース/データ）
[対応] 検証環境: 手動是正（SG隔離・ロール無効化・鍵Disable）
       本番移行時: 承認の上で自動是正（QA-110）＋フォレンジック保全（スナップショット）
   ↓
[復旧] 是正確認 → Config Rules再評価 → 正常化確認 → 報告（IR-4）
   ↓
[事後] 根本原因分析（RCA）→ Runbook更新（OPS連携）→ 再発防止
```

|-----------|-----------|---------|-------|
| GuardDuty | 不正アクセス/マイニング | リソース隔離（SG）、認証情報失効 | IR-1/IR-2 |
| SecurityHub | コンプライアンス逸脱 | Config自動修復/手動是正 | IR-2 |

## 12. リスク・制限事項

| # | リスク／制限 | 対応方針 |
|---|------------|---------|
| 1 | **自動適用層（Security Base）をCDKが上書き** | CDKは委任範囲（任意CMK/サービスロール/SG）のみ。基盤キー/CloudTrail/Config/GuardDuty/SecurityHubはImport/SSM参照。Phase4設計レビューで確認（TAIL-001 §7.2） |
| 2 | テナント別CMKの鍵数増による運用・コスト | Hello World規模では軽微。鍵ローテーション/ポリシー管理をCDK＋Config Ruleで標準化。本番拡大時は鍵集約方針を再評価（§13） |
| 3 | GuardDuty/SecurityHub Findingsのノイズ | Suppression Rule＋Severity別トリアージ＋Countモード初期運用で誤検知抑制（§6.1/§7.4） |
| 4 | 自動応答（自動隔離）の誤作動リスク | 検証環境は通知＋手動是正。自動隔離は本番移行時に承認の上で限定有効化（QA-110） |
| 5 | VN-3（侵入テスト）が検証スコープ外 | 本番移行時に年2回外部テストを計画（§8.7・§13）。ISMAP100%は本番時達成 |
| 6 | パターンB（EC2 CE）のOS/AMIパッチ責務 | Fargate CE選択でVN負荷低減を推奨。EC2 CE採用時はSSM Patch＋CIS AMI必須（§9） |
| 7 | KMSマルチRegion要否未確定（QA-107） | 単一Regionを基本。DR採用時にマルチRegionキーへ移行可能な構造を確保（§5.3） |
| 8 | MFA一般ユーザー必須化時期（QA-109） | 特権は即必須。一般は段階的必須化（運用設計で時期確定） |
| 9 | SCP実適用は運営主体/GCAS側 | 本設計はテナントOU追加制約の提示に留める。実適用を運営主体と調整（GC-002 §4.3） |

## 13. 今後の検討事項

1. **Shield Advanced採用判断**: 住民向け公開サービスの可用性要件（REQ-002）確定後に再評価（コスト vs DDoS耐性）。
2. **侵入テスト（VN-3）**: 本番移行時に年2回の外部ペネトレーションテストを計画化（ISMAP100%達成の最終要件）。
3. **KMSマルチRegion / 鍵集約方針**: DR（ap-northeast-3）採用時のマルチRegionキー移行、テナント数拡大時の鍵集約 vs 分離トレードオフ再評価（GC-002 §10と整合）。
4. **SIEM連携（LG-12/LG-16）**: 本番運用でSplunk等への外部送信・自動分析を追加（本案件は Logs Insights で代替）。
5. **自動応答（SOAR）の本番有効化**: 自動隔離・フォレンジック保全の承認フロー・実装を運用設計（@infra-operations）と連携して確定（QA-110）。
6. **デバイス検疫（ゼロトラスト柱2）**: エンドポイント検疫（Intune/Jamf等）はコーポレートIdP/Identity側の責務。本案件範囲外だが本番運用で要検討。
7. **MFA一般ユーザー必須化（QA-109）** の時期・例外プロセスを運用設計で確定。
8. **アカウント分離移行時**のIAM/KMS再設計（GC-002 §10段階移行パスと整合。テナント毎アカウント＋SCP個別適用への移行）。
