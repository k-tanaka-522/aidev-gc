# 共同利用ガバメントクラウド Hello World アーキ比較検証 — テーラリングレポート

## 1. テーラリング概要

本レポートは、IPA共通フレーム2013に基づく「修整根拠書」として、本サンプル案件に対して、エージェント・成果物・プロセスを選択・調整する根拠を記録するドキュメントです。

本案件は **「同一のHello Worldワークロードを3アーキテクチャパターンで構築し、工数を見積比較する」** ことを主目的とする比較検証案件であり、通常のGC移行案件とはテーラリングの力点が異なります。

| 通常案件との差分 | 本案件の方針 |
|----------------|------------|
| 業務要件詳細化が中心 | アプリはHello Worldスケルトン → 業務要件は最小、**アーキ比較評価軸の定義**に重点 |
| 単一アーキを設計・構築 | **共通部1系統 ＋ バッチ/非同期3パターン**を並行設計・構築・見積 |
| 移行・運用まで実施 | 主スコープは **Phase 0〜5＋見積比較**。Phase 6以降は簡易 |
| IaCは設計の一部 | **CDK(TypeScript)が成果物の中核**。3パターン分のスタック設計が比較の本体 |

## 4. 成果物テーラリング

### 4.1 比較見積構造（本案件の核）

```
総工数 = [共通部] + [パターンA: Lambda 固有] + [パターンB: AWS Batch 固有] + [パターンC: SQS+ECS Fargate 固有]
```

- 共通部（オンラインFargate public/private、VPC、セキュリティ、GCAS環境、監視）は **1回のみ計上**
- バッチ・非同期の設計/構築/見積は **パターンごとに独立計上** し、差分を見える化

## 5. プロセステーラリング

### 5.1 PM手法の選択

**採用: IPA標準 ＋ ハイブリッド（共通部ウォーターフォール＋パターン並行）**

| プロセス | 型 | 理由 |
|---------|-----|------|
| **Phase 0-3: 立ち上げ・要件・見積** | ウォーターフォール | 評価軸・スコープ確定、フェーズゲート |
| **Phase 4 共通部設計** | ウォーターフォール | 全パターンの土台のため先行・確定優先 |
| **Phase 4 パターンA/B/C設計** | 並行（パラレル） | 共通部確定後、3パターンを並行設計し比較を効率化 |
| **Phase 5 構築** | 反復（パターン単位スプリント） | CDKスタック単位で構築・検証を反復 |
| **Phase 6: テスト** | 簡易（疎通確認） | 比較検証目的のため動作確認レベル |

### 5.2 フェーズゲート

| ゲート | 実施フェーズ | 項目 | 承認権 |
|--------|-----------|------|--------|
| **Phase 0 Gate** | Phase 0末 | GCAS構成方針、テンプレート3層適用方針確定 | 運営主体PM |
| **Phase 2 Gate** | Phase 2末 | **アーキ比較評価軸の承認**、想定ワークロード確定 | 運営主体 技術責任者 |
| **Phase 3 Gate** | Phase 3末 | アーキ比較見積（A/B/C）の妥当性確認 | 運営主体 |
| **Phase 4 Gate** | Phase 4末 | 共通部設計＋3パターン設計レビュー（ISMAP整合、自動適用層非上書き確認） | セキュリティ責任者 |
| **Phase 5 Gate** | Phase 5末 | 3パターンCDK構築・疎通確認、最終比較結論 | 運営主体 技術責任者 |

### 5.3 ガバクラ標準IaC制約の設計反映（必須）

本案件のテーラリングで特に徹底する設計原則。

| 制約 | 設計への反映 |
|------|------------|
| テンプレート3層体系（自動適用/必須適用/サンプル） | **CDKは必須適用＋任意層を表現。自動適用層は上書きしない** |
| Organizations メンバーアカウント・SCP制約 | SCPで許可されたサービス/リージョン内でCDKリソースを定義 |
| GCAS-SSO(CEP)連携 | IAMはSSO前提。IAMユーザー直接発行を避ける |
| ConMon/CSPM | Config Rules/SecurityHub/GuardDutyを常時監視として全パターンに適用 |
| KMS CMK暗号化、DS-310準拠 | 全データストア（S3/ECR/Logs/SQS等）をCMK暗号化 |
| タグ統制 | 全リソースに environment/owner/cost_center/project/compliance=ismap を付与 |

## 7. リスク・対策（テーラリング視点）

### 7.1 テーラリング自体のリスク

| リスク | 影響 | 対策 |
|--------|------|------|
| **比較見積の共通部/固有部の切り分けミス** | パターン間比較が不公正になる | 共通部を先に確定し、固有部のみを各パターンに計上するルールを徹底 |
| **移行・運用エージェント無効化による論点漏れ** | 検証スコープ外の論点が後で必要になる | 無効化は「本案件スコープ外」と明記。必要時に再有効化 |
| **3パターン設計の粒度不揃い** | 工数比較の精度低下 | 各パターンで同一の設計テンプレート（構成/IAM/監視/タグ）を用いる |

### 7.2 テーラリング後のプロジェクト高リスク項目

| リスク | 優先度 | 対策 | 責任者 |
|--------|--------|------|--------|
| アーキ比較評価軸の未定義 | **高** | Phase 2で評価マトリクス定義（QA積み） | @infra-requirements |
| バッチ想定ワークロード未確定 | **高** | Phase 2で想定負荷を仮定義 | @infra-requirements |
| 自動適用層をCDKが上書き | **高** | 必須適用＋任意層のみCDK表現 | @infra-iac, @infra-gc-environment |
| 3パターン並行による設計工数膨張 | **中** | 共通部先行確定＋パターン固有部のみ並行 | @pm-planning |
| SCP制約によるCDKデプロイ失敗 | **中** | Phase 4で許可サービス/リージョンを事前確認 | @infra-iac |
