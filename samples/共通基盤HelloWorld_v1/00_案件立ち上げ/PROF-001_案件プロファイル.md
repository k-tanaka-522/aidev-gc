# 共同利用ガバメントクラウド Hello World アーキ比較検証 — 案件プロファイル

## 1. 基本情報

| 項目 | 内容 |
|------|------|
| **案件名** | 共同利用ガバメントクラウド Hello World アーキ比較検証 |
| **顧客（想定）** | 共同利用グループ運営主体（省庁級・複数自治体テナント） |
| **案件区分** | サンプル案件（アーキテクチャ比較・工数見積を目的とする検証案件） |
| **目的** | Spring Boot製のHello Worldワークロードを題材に、設計要素・構築要素を洗い出し、バッチ/非同期処理の**3アーキテクチャパターン**の工数を見積比較する |
| **出力先ルート** | `samples/共通基盤HelloWorld_v1/` |
| **IaCツール** | AWS CDK (TypeScript)、ガバクラ標準IaC準拠 |
| **アプリ実装スコープ** | インフラ(CDK)中心、Spring BootアプリはHello Worldスケルトンのみ |
| **作成日** | 2026年6月1日 |

### 1.1 本案件の特殊性（比較検証案件）

本案件は通常のGC移行案件とは異なり、**「同一ワークロードを3つのアーキテクチャパターンで構築し、工数を見積比較する」** ことを主目的とする。したがって：

- オンライン処理（ECS Fargate：パブリック/プライベート）は**全パターン共通**の土台として1回設計・構築する
- バッチ・非同期処理は**3パターン（A: Lambda / B: AWS Batch / C: SQS+ECS Fargate）**を並行して設計・構築・見積する
- 見積は「共通部 ＋ パターン固有部」の構造とし、パターン間で差分が明確になる形で算出する

## 4. 移行方式判定

### 4.1 判定根拠

**結論: 新規構築（工数係数 2.5）**

**理由:**
1. 既存システムの移行はなく、Hello Worldワークロードをゼロから構築する
2. クラウドネイティブ設計（ECS Fargate / Lambda / AWS Batch / SQS）を前提とした新規アーキテクチャ
3. ガバクラ標準IaC（CDK）でゼロからリソースをコード化

→ **新規構築判定**。ただしアプリはHello Worldスケルトンのため、Phase 2（要件定義）の業務要件詳細化工数は新規構築標準より圧縮可能。一方でPhase 4（設計）は3パターン分が並行するため設計工数が増加する。

### 4.2 工数係数への影響

| 係数 | 値 | 根拠 |
|------|-----|------|
| 移行方式係数 | 2.5 | 新規構築 |
| ※アプリスコープ縮小補正 | ×0.6（Phase 2要件のみ） | Hello Worldスケルトンのため業務要件詳細化を圧縮 |
| ※3パターン並行補正 | バッチ・非同期の設計/構築/見積に適用（後述） | パターン共通部1.0＋パターン固有部×3 |

## 9. アーキ比較対象（本案件の核）

### 9.1 共通部（全パターン共通）

| 領域 | 内容 |
|------|------|
| **オンライン処理（パブリック）** | ECS Fargate（パブリックサービス）＋ ALB ＋ WAF |
| **オンライン処理（プライベート）** | ECS Fargate（プライベートサービス）＋ 内部ALB ＋ VPC Endpoint |
| **共通基盤** | VPC/サブネット/SG、ECR、KMS CMK、CloudWatch、CloudTrail、Config/SecurityHub/GuardDuty、GCAS-SSO(CEP)、SCP対応、タグ統制 |
| **アプリ** | Spring Boot Hello World スケルトン（コンテナ化、最小ロジック） |

### 9.2 比較対象（バッチ・非同期処理 3パターン）

| パターン | 構成 | 主な設計・構築要素 | 想定される特徴 |
|---------|------|----------------|------------|
| **パターンA: Lambda** | Lambda（バッチ/非同期）＋ EventBridge トリガ | Lambda関数、IAMロール、EventBridgeルール、CloudWatch Logs、（VPC Lambda時）ENI設計 | 構築軽量・運用負荷低。実行時間/メモリ制約あり。CDK構築工数が最小 |
| **パターンB: AWS Batch** | AWS Batch（Fargate or EC2コンピュート環境）＋ ジョブキュー＋ ジョブ定義 | コンピュート環境、ジョブキュー、ジョブ定義、ECRイメージ、IAMロール、EventBridge起動 | 大規模/長時間バッチ向け。構築要素が多く設計工数が最大級 |
| **パターンC: SQS + ECS Fargate** | SQSキュー＋ ECS Fargate（ワーカー）＋ Auto Scaling（キュー深度連動） | SQSキュー、DLQ、ECSサービス/タスク定義、Application Auto Scaling、IAMロール、CloudWatchアラーム | 非同期メッセージング向け。スケーリング設計が肝。中程度の構築工数 |

### 9.3 比較見積の構造

```
総工数 = 共通部工数 + パターンA固有工数 + パターンB固有工数 + パターンC固有工数
```

- 共通部は1回のみ計上
- 各パターン固有部を独立計上し、パターン間の工数差が見える化される
- 見積比較表（パターンA/B/Cの設計・構築・運用工数の対比）をPhase 3成果物とする

## 10. 案件リスク・前提条件

### 10.1 高リスク項目

| リスク | 影響 | 対策 |
|--------|------|------|
| **アーキ比較評価軸の未定義** | パターン比較が定性的になり結論が曖昧化 | Phase 2で評価マトリクス（性能/コスト/運用/拡張性）を定義（QA積み） |
| **バッチ想定ワークロード未確定** | パターン適性判断のサイジング根拠不足 | Phase 2でHello Worldバッチの想定負荷を仮定義 |
| **3パターン並行による設計工数増** | Phase 4工数膨張 | 共通部を先に確定し、パターン固有部のみ並行設計 |
| **GCAS構成/テナント分離方針未確定** | Phase 4設計手戻り | Phase 2-4でGCAS構成方針（アカウント or VPC/タグ分離）を早期確定 |
| **ガバクラ標準IaC自動適用層との衝突** | CDKが自動適用層を上書きするリスク | 自動適用層は上書きしない設計原則を徹底（必須適用＋任意層のみCDK表現） |

### 10.2 前提条件

1. **環境前提**
   - ベンダー払い出しのGC環境（Organizations メンバーアカウント、SCP適用済）
   - GCAS-SSO(CEP)連携が利用可能
   - テンプレート3層体系（自動適用/必須適用/サンプル）が前提として存在

2. **スコープ前提**
   - Spring BootアプリはHello Worldスケルトンのみ（業務ロジックなし）
   - IaCツールはAWS CDK (TypeScript) に固定
   - 主スコープはPhase 0〜5（立ち上げ〜構築）＋見積比較。Phase 6以降は簡易

3. **比較前提**
   - オンライン（Fargate public/private）は全パターン共通の土台
   - バッチ・非同期はA/B/Cの3パターンを全て設計・構築・見積する
