# IPA テーラリング実装ガイド

## 概要
IPA共通フレーム2013（以下「IPA標準」）に基づいて、GC案件固有の特性に合わせてプロセス・成果物をテーラリングする手順。修整根拠を体系的に記録し、後続のリスク管理・品質管理に活用する。

---

## IPA共通フレーム2013 基礎

### 9フェーズ構成
IPA標準は、以下の9つのフェーズ（ステージ）で構成：

1. **企画フェーズ** — ビジネス要件、経営的意思決定
2. **要件定義フェーズ** — システム要件の詳細化
3. **設計フェーズ** — システム設計、アーキテクチャ決定
4. **構築フェーズ** — 実装、開発
5. **テストフェーズ** — 品質確保、リリース判断
6. **導入フェーズ** — 本番環境への移行、ユーザー教育
7. **保守フェーズ** — 運用、サポート

GC案件向けにはこれを9フェーズに拡張：
- Phase 0: 案件入口（企画前の準備）
- Phase 1: 提案見積（営業・提案フェーズ）
- Phase 2: 要件定義
- Phase 3: 詳細見積計画
- Phase 4: 設計
- Phase 5: 構築
- Phase 6: テスト
- Phase 7: 導入・移行
- Phase 8: 保守・運用

### 標準プロセス要素
各フェーズは、以下のプロセス要素から構成：

| 要素 | 説明 |
|------|------|
| **計画・実施** | 具体的な活動（何をするか） |
| **確認・評価** | レビュー・チェック |
| **成果物** | 出力ドキュメント |
| **役割・責任** | メンバー配置 |
| **リスク** | 留意点 |

## テーラリングの基本原則

### 原則1: 削除は最小限に
成果物・プロセスの削除は、明確な根拠がある場合のみ。「簡略化」「統合」を優先。

例：
```
削除 (NG): 「小規模案件だから要件定義書は不要」
統合 (OK): 「要件定義書と基本設計書を1冊に統合（ボリューム削減、タイムアップ）」
簡略化 (OK): 「ユーザー承認の厳格性を中程度に（監査ログ, 会議記録は全て記録）」
```

### 原則2: 追加根拠を明示
GC案件特有の要件（GCAS, ISMAP, 複数自治体対応など）で必要な追加タスク・成果物は、明確に根拠付けする。

例：
```
追加タスク: 「GCAS申請対応」
根拠: 「ガバメントクラウド利用のため、GCAS承認が必須（GC調達仕様書p.X参照）」
成果物: 「CEP（契約企業プロフィール）」
工数: 「40人日（申請書作成＋監査対応）」
期間: 「2-4週間（GC承認待機含む）」
```

### 原則3: 影響範囲を記録
あるプロセスを変更すると、他のフェーズ・成果物にどう影響するかを記録。

例：
```
修整内容: 「Phase 1 (提案見積) を1週間短縮」
影響:
- Phase 2 (要件定義) の開始が1週間前倒し → ユーザー側ヒアリング体制確保必須
- Phase 3-8 のスケジュール全体が1週間前倒し → リソース確保確認必須
- リスク: 要件漏れ、品質低下の可能性 +20%
対策: 「設計レビュー回数 +1回」「セキュリティテスト期間 +1週間」
```

## テーラリング実施手順

### ステップ1: テーラリング対象の特定

プロジェクト10軸プロファイルに基づいて、テーラリング対象を特定：

```
テーラリング対象の例：
□ 自治体規模が大規模 → Phase 1-3 の調整タスク追加必要
□ 移行方式が新規構築 → Phase 4 (設計) 大幅追加必要
□ GC共同利用 → Phase 2 のIF要件整理タスク追加必要
□ セキュリティレベル高 → Phase 6 (テスト) 工数大幅増必要
□ 期限6ヶ月以内 → Phase並行化, EVM導入必要
□ スコープ未確定 → Phase 0-2 を段階的実施必要
```

### ステップ2: フェーズ別テーラリング

各フェーズについて、以下の項目を検討：

| 項目 | 実施項目 | 判断 |
|------|--------|------|
| **プロセス** | 実施するか、簡略化するか、削除するか | Y/簡/N |
| **成果物** | 生成するか、統合するか、簡略版にするか | Y/統合/簡 |
| **期間** | 短縮できるか、並行化できるか | -X週間 / 並行化 |
| **人数** | 追加配置が必要か、兼任でOKか | +1名 / 兼任OK |
| **レビュー** | 承認レベル（厳格/標準/簡略）を変更するか | 変更/変更なし |
| **リスク** | テーラリングに伴う新たなリスクは何か | - |
| **対策** | リスク対策は何か | - |

#### Phase 0: 案件入口

```
【大規模自治体 + GC共同利用 + セキュリティ高】

修整内容:
□ ステアリングコミッティ設置タスク +1タスク（月1回の定期会議）
□ GCAS申請準備タスク +1タスク（40人日、2-4週間）
□ セキュリティポリシー確認タスク +1タスク（20人日、2週間）

影響:
- Phase 0 期間: 4週間 → 6週間 (+2週間)
- Phase 0 工数: 40人日 → 100人日 (+60人日)
- 人数: 2名 → 3名 (PM + SE1 + セキュリティSE1)

根拠:
- 「大規模自治体の複雑な意思決定」IPA標準 p.X参照
- 「GC共同利用時のガバナンス」GC調達仕様書 p.Y参照
- 「ISMAP対応時のセキュリティ要件確認」ISMAP認定基準 参照
```

#### Phase 1: 提案見積

```
【中規模自治体 + R1移行 + ASP 5個連携】

修整内容:
□ RFP分析タスク（IF要件抽出含む） +10人日
□ 参考案件調査タスク（同規模・同移行方式） +5人日
□ ステークホルダー分析タスク +8人日

簡略化:
□ コスト見積 → 概算見積のみ（詳細見積はPhase 3で実施）

期間: 2週間 → 3週間
工数: 60人日 → 83人日
人数: 2名 → 3名

根拠:
- 「ASP連携がある場合はIF仕様書の事前ヒアリング」gc-project-profiling参照
- 「中規模自治体の調整工数」tailoring-decision-matrix 軸2参照
```

#### Phase 2: 要件定義

```
【複数システム移行 + 複雑NW (LGWAN+DX) + セキュリティ高】

修整内容:
□ 現行NW詳細調査タスク +30人日（複雑性対応）
□ セキュリティ要件詳細化ワークショップ +20人日
□ 複数システムのIF要件整理ワークショップ +25人日
□ 非機能要件詳細表作成タスク +15人日

強化:
□ ユーザーレビュー → 2回 → 4回（複雑性とリスク対応）
□ 品質ゲート（要件定義書承認）→ 厳格レベル

期間: 6週間 → 10週間
工数: 160人日 → 250人日
人数: 4名 → 5名 (+1 NW/SYS, またはSE1名を現行調査に専任)

リスク: 要件の再質問増加、承認遅延 +20%
対策: ステアリングコミッティで課題エスカレーション、意思決定ルール明確化
```

#### Phase 3: 詳細見積計画

```
【6ヶ月超短納期 + スコープ段階的確定】

修整内容:
□ スコープ凍結プロセス（段階的承認）+10人日
□ スケジュール短縮検証タスク +10人日
□ リスク管理強化（日次ステアリング） +20人日

簡略化:
□ 詳細見積を「概略+詳細」の2段階に分割
  - 段階1: Phase 1-3 の見積（4週間目の判断時点）
  - 段階2: Phase 4 以降の詳細見積（Phase 3 終了時）

期間: 2週間 → 4週間 (2週間は概略, 次の2週間で詳細確認)
工数: 60人日 → 90人日

根拠: 「超短納期案件のスコープ段階的確定」ipa-pm-process p.XX参照
```

#### Phase 4: 設計

```
【新規構築（工数係数 2.5倍）+ セキュリティ高 + ネットワーク複雑】

修整内容:
□ セキュリティ設計レビュー → 専門家による外部レビュー +20人日, 外部費用 +500万円
□ ネットワーク設計 → 外部セキュリティ診断後の設計変更対応を見込む +30人日
□ クラウド最適化設計（IaC化） +40人日
□ アーキテクチャレビューボード（ARB）設置 → 月1回の公式レビュー会

期間: 8週間 → 12週間
工数: 350人日 × 2.5 (新規構築係数) × 1.5 (セキュリティ係数) = 1,312人日 → さらに +90人日
人数: 6名 → 7名 (+1 セキュリティSE)

リスク: 外部診断による設計修正期間の延長
対策: Phase 6 セキュリティテストを2回に分割（早期診断 + 最終診断）
```

```
【IaC化 (Terraform) + マルチAZ + RDS移行】

修整内容:
□ IaC開発（Terraform） +40人日
□ IaC品質保証（linting, static analysis） +15人日
□ GitOps パイプライン構築 +30人日
□ データベース移行計画 +20人日

強化:
□ コード品質ゲート導入（CI/CD pipeline に quality check）

期間: 8週間 → 10週間
工数: 200人日 → 305人日
人数: 5名 → 6名

根拠: 「クラウドネイティブ開発のIaC化」gc-iac-structure-terraform参照
```

#### Phase 6: テスト

```
【セキュリティレベル高 (ISMAP) + 複数ASP連携 (5個)】

修整内容:
□ セキュリティテスト（ペネトレーション、脆弱性診断） +60人日, 外部費用 +800万円
□ ASP連携テスト計画（各ASP4つのテストシナリオ） +40人日
□ 本番同等環境での結合テスト +30人日
□ セキュリティ監査対応（ISMAP） +20人日

強化:
□ テスト品質ゲート → 「セキュリティテスト合格」を本稼働の必須条件に

期間: 8週間 → 12週間
工数: 144人日 × 1.5 (セキュリティ係数) + 外部診断 = 216人日 → さらに +134人日 = 350人日
人数: 5名 → 6名

リスク: セキュリティ診断の指摘対応が長期化 +30%
対策: 「診断指摘→設計修正→再テスト」の短期ループ、外部診断から2週間での対応体制
```

#### Phase 7: 導入・移行

```
【段階的移行 (複数システム) + 本番データ移行 (大量) + 並行運用】
```

### ステップ3: 修整根拠書の作成

すべてのテーラリング修整を、以下の形式で「修整根拠書」として記録：

```markdown
# テーラリング修整根拠書

## プロジェクト概要
- プロジェクト名: XXX
- 10軸プロファイル: [記載]
- テーラリング実施日: 20XX年Y月Z日

## フェーズ別修整内容

### Phase X: [フェーズ名]

#### 修整1: [修整内容タイトル]
**対象プロセス:** [IPA標準のどのプロセス要素に該当するか]
**修整区分:** □削除 □統合 □簡略化 □追加 □強化
**修整内容:** [具体的にどう変えるのか（プロセス/成果物/期間/人数等）]
**根拠:** [なぜそうするのか。10軸プロファイルのどの軸に基づくのか、何を参照したか]
**影響範囲:**
- 期間: [X週間短縮/X週間延長/なし]
- 工数: [+X人日/-X人日]
- 人数: [+1名/-1名/なし]
- 後続フェーズへの影響: [具体的に]
**リスク:** [この修整に伴うリスク]
**対策:** [リスク対応方法]

#### 修整2: [次の修整]
[同じフォーマット]

...

## テーラリング完了後の成果物リスト

| フェーズ | 成果物名 | 追加/削除/統合 | 備考 |
|---------|--------|-----------|------|
| Phase 1 | 提案見積書 | 統合 | 概算見積のみ、詳細は Phase 3 で実施 |
| Phase 2 | 要件定義書 + IF要件書 | 統合 | 1冊に統合 |
| Phase 4 | セキュリティ設計書 | 追加 | 外部セキュリティ診断対応 |
| Phase 6 | セキュリティテスト計画書 | 強化 | ペネトレーション追加 |
...

## 最終確認

**実施者:** [PM名]
**確認者:** [上長/ステアリング委員会名]
**確認日:** XXXX年Y月Z日
**有効期限:** [契約期間終了日 / または定期レビュー日]
```

### ステップ4: CLAUDE.md への反映

CLAUDE.md の「プロジェクト固有情報」セクションを以下のように入力：

```markdown
## プロジェクト固有情報

### 案件概要
- プロジェクト名: XXX システム GC移行
- 顧客: X自治体
- 対象システム: システムA, システムB, ...
- GC利用方式: [単独利用 / 共同利用]
- 移行方式: [リフト / R1 / R2 / 新規構築]

### テーラリング結果
- 有効エージェント: @tailoring, @infra-requirements, @infra-network, @infra-security, @infra-estimation, @infra-proposal
- 無効エージェント: [なし / 該当なし]
- PM手法: IPA標準 + セキュリティ強化（外部診断対応）
- テーラリング根拠書: TAILORING_REPORT.md (添付)

### IaC規約
- ツール: Terraform
- リソース命名: snake_case（例: vpc_main, sg_app）
- タグ必須: environment (dev/stg/prod), owner (팀명), cost_center (部門コード), project (プロジェクトコード)
- Variable型: 全て明示（anyは禁止）
- for_each推奨（countは使用禁止）

### 追加テーラリング事項
[個別にあればここに記載]
```

## テーラリング実施時の注意点

### 注意1: スコープクリープ防止
テーラリングで追加タスク・成果物を加えるときは、必ず根拠と期間・工数を明示。曖昧な「念のため追加」は避ける。

### 注意2: リスク評価
テーラリング修整に伴うリスク（品質低下、遅延、コスト増など）を明示的に評価。「短納期のため要件定義を簡略化」なら、「要件漏れリスク +30%」と定量化。

### 注意3: 定期レビュー
テーラリング根拠書は案件中に定期的（月1回）にレビュー。新たなリスク・制約が出現した場合は、修整根拠書を更新。

### 注意4: 後続プロジェクトへの教訓化
案件完了後、テーラリング根拠書を振り返り、「予想と実績」の差を記録。次の同様案件の根拠データに活用。
