# IPA共通フレーム2013 支援プロセス

## 概要

支援プロセスは、プロジェクト全体を通じて品質と整合性を保証するためのプロセスです。5つの主要プロセスで構成されます。

---

## 1. 品質保証プロセス (SP.1)

### 目的
開発活動が定義されたプロセスと計画に従って実施されているかを確認し、製品品質を保証する。

### 主要活動

#### 1.1 品質方針の策定
- 組織の品質目標（可用性 99.9%, セキュリティ等級 等）
- 品質要件（ビジネス + 技術）
- 品質基準（テストカバレッジ >= 80% 等）

#### 1.2 プロセス監査
- 計画通りにプロセスが実行されているか
- 成果物が基準に従って作成されているか
- 非準拠事項の報告と改善勧告

#### 1.3 品質メトリクス測定
- バグ密度
- テストカバレッジ
- レビュー指摘密度
- FP生産性

---

## 2. 検証プロセス (SP.2)

### 目的
成果物が明記された要件を満たしているかを確認する。

### 主要活動

#### 2.1 検証計画
- 何を検証するか（成果物）
- どのように検証するか（方法）
- 誰が検証するか（関係者）
- いつ検証するか（タイミング）

#### 2.2 検証の実施
- コードレビュー
- 単体テスト
- 結合テスト
- パフォーマンステスト

**テスト階層:**
```
┌──────────────────┐
│ UAT (ユーザテスト)│ ← 要件充足確認
├──────────────────┤
│ システムテスト    │ ← 要件充足確認
├──────────────────┤
│ 結合テスト        │ ← 要件充足確認 (一部)
├──────────────────┤
│ 単体テスト        │ ← 詳細設計充足
├──────────────────┤
│ コードレビュー    │ ← コード品質確認
└──────────────────┘
```

#### 2.3 テストカバレッジ
```
カバレッジ >= 80%: 合格
カバレッジ 70-80%: 要改善
カバレッジ < 70%: 不合格
```

#### 2.4 バグ管理
- バグ重要度分類（Level 1-4）
- リリース判定基準（Level 1, 2 ゼロ等）
- バグ追跡と対応

---

## 3. 妥当性確認プロセス (SP.3)

### 目的
完成した製品がビジネス目標を達成するか（顧客ニーズを満たすか）を確認する。

### 主要活動

#### 3.1 妥当性確認計画
- ビジネス目標の定義
- ユーザ受け入れ判定基準
- UAT スケジュール

#### 3.2 UAT（ユーザ受け入れテスト）実施
- ビジネスユーザが実際に製品を使用
- ビジネス要件を満たしているか確認
- 本番稼働前の最終判定

#### 3.3 ユーザ承認
- UAT 完了報告書署名
- 本番リリース承認

---

## 4. 文書化プロセス (SP.4)

### 目的
プロジェクトの成果物と経験を記録し、プロジェクト終了後の運用や次プロジェクトの参考資料とする。

### 主要活動

#### 4.1 文書化計画
- 作成すべき成果物リスト
- 各成果物の責任者
- 提出期限

#### 4.2 成果物の作成と管理
**必須成果物:**
```
要件定義フェーズ:
  - 要件定義書
  - ユースケース図
  - 業務フロー図

設計フェーズ:
  - NW設計書
  - セキュリティ設計書
  - システム設計書
  - DB設計書

実装フェーズ:
  - テスト計画書
  - テストケース仕様
  - ソースコード（コメント付き）

テスト/リリースフェーズ:
  - テスト実績報告書
  - リリースノート
  - 運用手順書
  - トラブル対応手順書
```

#### 4.3 ドキュメント品質
- 正確性（誤字脱字なし）
- 完全性（全項目記載）
- 一貫性（図表と説明の整合）
- 可読性（構成・フォント統一）

---

## 5. 構成管理プロセス (SP.5)

### 目的
成果物のバージョンと変更を一元的に管理し、整合性を保証する。

### 主要活動

#### 5.1 構成管理計画
- 管理対象の成果物（コード、設計書、テストケース等）
- バージョン規約
- 変更フロー

#### 5.2 構成ベースラインの確立
- 各フェーズの確定版を指定
- バージョンタグ付け

```yaml
ベースライン例:
要件定義ベースライン:
  - 要件定義書 v1.0
  - 日付: 2026-03-15
  - ステータス: 顧客承認済み

設計ベースライン:
  - NW設計書 v2.1
  - セキュリティ設計書 v1.5
  - 日付: 2026-04-05
  - ステータス: レビュー承認済み

本番ベースライン:
  - Terraform code v1.0.0
  - CloudFormation templates v1.0.0
  - 日付: 2026-05-20
  - ステータス: 本番適用済み
```

#### 5.3 変更管理
- 変更要求の受付
- 影響分析
- 承認
- 実装
- トレーサビリティ確保

#### 5.4 構成管理台帳
```yaml
成果物: NW設計書
現行版: v2.1
最終更新日: 2026-04-05
ステータス: 確定
変更履歴:
  v2.1: VPC フローログ追加 (2026-04-05)
  v2.0: VPC 設計見直し (2026-03-20)
  v1.0: 初版 (2026-03-01)
Git Tag: network-design-v2.1
```

```
           │
     ┌─────┴─────┬──────────┬──────────┬──────────┐
     │             │           │          │          │
┌────▼────┐ ┌────▼────┐ ┌──▼──────┐ ┌─▼───────┐ ┌──▼──────┐
│品質保証  │ │検証     │ │妥当性確認│ │文書化   │ │構成管理  │
├────────┤ ├────────┤ ├────────┤ ├────────┤ ├────────┤
│プロセス │ │製品品質│ │ビジネス│ │記録保存│ │変更管理│

```

## フェーズ別の支援活動

### 要件定義フェーズ
```
品質保証 — プロセス準拠確認
検証    — レビュー観点チェック（要件の完全性）
文書化  — 要件定義書の品質基準チェック
構成管理 — 要件定義ベースライン確立
```

### 設計フェーズ
```
品質保証 — 設計が要件に適合しているか
検証    — 設計レビュー実施
         — テストケース設計（要件トレーサビリティ）
妥当性確認 — 本番での動作可能性確認
文書化  — 設計書完成度確認
構成管理 — 設計ベースライン確立
```

### 実装フェーズ
```
品質保証 — コードが設計に準拠しているか
検証    — コードレビュー → 単体テスト → 結合テスト
妥当性確認 — テスト計画が要件をカバーしているか
文書化  — テストケース、運用手順書の品質
構成管理 — コードバージョン管理、タグ付け
```

### テスト/リリースフェーズ
```
品質保証 — テスト戦略が計画通りか
検証    — テスト実施状況（進捗率、カバレッジ）
妥当性確認 — UAT 実施、ユーザ承認取得
文書化  — テスト実績報告、リリースノート
構成管理 — 本番ベースライン確立、タグ作成
```

---

## 支援プロセスの品質基準

| プロセス | 品質基準 | 判定 |
|---------|--------|------|
| 品質保証 | 全フェーズでプロセス監査を実施した | ✓ 合格 |
| 検証 | テストカバレッジ >= 80% | ✓ 合格 |
| 検証 | 本番バグ密度 <= 0.5/KLOC | ✓ 合格 |
| 妥当性確認 | ユーザ承認を取得した | ✓ 合格 |
| 文書化 | 必須成果物が全て作成された | ✓ 合格 |
| 構成管理 | ベースラインが確立された | ✓ 合格 |
| 構成管理 | 変更が全て追跡されている | ✓ 合格 |
