# GC 移行パターン集

## 1. 移行方式別テンプレート

### 1.1 リフト & シフト（Lift & Shift）

**特徴**: 既存システムをほぼそのままクラウドに移行

**対象リソース**:
- EC2 インスタンス（オンプレミスVM→EC2）
- ストレージ（NAS/SAN → EBS / S3）
- ネットワーク（オンプレLAN → VPC）
- RDS（オンプレミスDB → Amazon RDS / DynamoDB）

**移行手順**:

```
Phase 1: 事前準備（T-30日）
  - ネットワーク接続準備（DirectConnect / VPN）
  - IAMロール/ポリシー定義
  - セキュリティグループ/NACLテンプレート準備
  - バックアップ戦略確認

Phase 2: リソース作成（T-20日）
  - VPC / Subnet 作成
  - セキュリティグループ / NACLデプロイ
  - EC2テンプレート作成（AMI化）
  - RDS作成 / リード レプリカ構築

Phase 3: データ複製（T-10日）
  - オンプレDB → RDS DMS 実行
  - ストレージ → S3 データ転送（AWS DataSync / Snowball）
  - アプリケーション設定ファイル更新

Phase 4: アプリケーション検証（T-5日）
  - ステージング環境で本番同様テスト
  - DB接続テスト
  - キャッシュ / セッション管理確認

Phase 5: カットオーバー（Day 0）
  - DNS切替（オンプレ → GC）
  - オンプレアプリケーション停止
  - 最終同期実行
  - GC側アプリケーション起動
  - トラフィック確認（ヘルスチェック）

Phase 6: 本番安定（Day +1〜7）
  - 日次監視（エラーログ / パフォーマンス確認）
  - オンプレ環境は切戻し待機（7日間）
  - パフォーマンス / コスト分析
```

**推定工数**: 120 - 160 人日（システム規模に応じて）

### 1.2 リホスト (Rehost: R1)

**特徴**: リフト & シフトにOSパッチ / ミドルウェア最適化を追加

**差異点**:
- OS パッチレベル統一
- ミドルウェア（Apache, Tomcat, PostgreSQL 等）をGC向けに最適化
- EBS最適化、ネットワーク最適化設定
- CloudWatch エージェント導入

**追加工程**:

```
Phase 3.5: ミドルウェア最適化（T-7日）
  - OS パッチ適用（セキュリティアップデート）
  - ミドルウェア設定ファイル（httpd.conf, postgresql.conf等）見直し
  - パフォーマンスチューニング（キャッシュサイズ等）
  - CloudWatch エージェント導入
  - システムログ集約設定（CloudWatch Logs）
```

**推定工数**: 160 - 200 人日

---

### 1.3 リプラットフォーム (Replatform: R2)

**特徴**: OSSコンポーネントをマネージドサービスに移行

**例**:
- PostgreSQL on EC2 → Amazon RDS for PostgreSQL
- Apache Kafka on EC2 → Amazon MSK (Managed Streaming for Kafka)
- Redis on EC2 → Amazon ElastiCache
- Elasticsearch on EC2 → Amazon OpenSearch
- MySQL → Aurora

**追加工程**:

```
Phase 2.5: マネージドサービス検証（T-15日）
  - RDS パラメータグループ定義（文字セット、接続数等）
  - バックアップ保持期間設定
  - Multi-AZ 設定検証
  - 読取レプリカ構築テスト

Phase 3.5: DMS 全量 / 増分同期（T-7日）
  - スキーマ検証（テーブル定義、インデックス）
  - データ型マッピング確認（TINYINT → SMALLINT等）
  - シーケンス / トリガー確認
  - 増分同期の実行（CDC: Change Data Capture）
```

**推定工数**: 200 - 280 人日（マネージドサービス複数の場合）

---

### 1.4 新規構築 (Refactor/Re-architect)

**特徴**: クラウドネイティブ設計に完全リセット

**対象変更**:
- モノリシック → マイクロサービス / コンテナ化
- オンプレミスDB → DynamoDB / DocumentDB / S3 等
- キューシステム → SQS / SNS
- ファイル共有 → S3

**工程構成**:

```
Phase 0: 新システム設計（T-45日）
  - マイクロサービス設計
  - API 定義 (OpenAPI)
  - Database スキーマ再設計（DynamoDB / RDS 検討）
  - コンテナイメージ定義（ECR）

Phase 1: コンテナ化 & IaC（T-30日）
  - Dockerfile 作成
  - ECS Fargate タスク定義
  - CloudFormation / Terraform 記述
  - マネージドサービス統合

Phase 2: マイクロサービス開発（T-20日）
  - 既存ロジック → 新マイクロサービス変換
  - API インテグレーション
  - 認証（Cognito / API Gateway オーサライザ）

Phase 3: データ移行（T-10日）
  - バッチ処理による既存DB → 新DB 変換
  - データ検証・正規化スクリプト

Phase 4: 結合テスト（T-5日）
  - マイクロサービス間の連携確認
  - 性能テスト
  - セキュリティテスト

Phase 5: カットオーバー（Day 0）
  - 新システム本番化
  - オンプレ システム切戻し待機

Phase 6: 本番運用（Day +1〜30）
  - バグ修正
  - パフォーマンス最適化
  - コスト最適化
```

**推定工数**: 400 - 600 人日（完全リセットのため）

## 2. データ移行方式の選択基準

### 2.1 データ転送方式の比較

| 方式 | 転送速度 | コスト | 用途 | RTO |
|------|---------|--------|------|-----|
| **AWS DataSync** | 1 - 10 Gbps | 中程度 | ネットワーク経由転送（< 100TB） | 数時間 |
| **AWS Snowball** | 物理搬送 | 低（大容量） | 大規模転送（> 100TB）、低速網向け | 数日 |
| **AWS Snowmobile** | 物理搬送 | 低（超大容量） | エクサバイト級転送 | 1-2週間 |
| **AWS DMS** | ネットワーク | 低 | DB 全量 / 増分同期 | 数時間 |
| **AWS S3 Transfer Acceleration** | 500Mbps - 1Gbps | 中程度 | インターネット経由（高速） | 数分 - 数時間 |
| **Direct Connect** | 1 - 100 Gbps | 高 | 専用線経由（大容量、継続的） | 数時間 |

### 2.2 データ移行フロー

```
既存ストレージ（NAS / SAN）
  ↓
[DataSync / Snowball で AWS へ転送]
  ↓
S3 バケット
  ↓
[必要に応じて EBS / EFS / RDS へ変換]
  ↓
GC リソース（EBS / EFS / RDS）
```

### 2.3 DB 移行フロー

```
既存 DB（PostgreSQL / MySQL / Oracle on オンプレ）
  ↓
[AWS DMS で複製開始 - フル + 増分モード]
  ↓
Amazon RDS（Multi-AZ レプリカ）
  ↓
[アプリケーション接続先を既存 → RDS に切替]
  ↓
[一定期間並行運用（検証用）]
  ↓
[既存 DB は読取専用 → オフライン]
```

## 3. 切替（カットオーバー）手順

### 3.1 DNS 切替パターン

**パターン A: Route53 無停止切替（推奨）**

```
事前準備:
  1. Route53 レコード作成（オンプレ IP → GC ELB IP）
  2. TTL を 300秒 に短縮（切替3日前）
  3. GC 側リソース ヘルスチェック有効化

切替当日（Day 0）:
  1. T-30分: 最終的なDB同期実行（DMS 増分）
  2. T-15分: GC アプリケーション起動確認（ヘルスチェック OK）
  3. T-5分: オンプレアプリケーション停止
  4. T-0分: Route53 Weighted Policy で 100% → GC に変更
  5. T+5分: ヘルスチェック + ログ監視（エラー無いか確認）

切替後:
  1. T+30分: 監視強化（ラウンドロビン / スティッキーセッション確認）
  2. T+1時間: データベース検証クエリ実行
  3. T+1日: パフォーマンス / エラーレート集計
```

**パターン B: 段階的トラフィック転換（カナリアリリース）**

```
Day 0:
  - Route53 weighted policy: オンプレ 95%, GC 5%

Day 1:
  - Route53 weighted policy: オンプレ 80%, GC 20%
  - エラー / パフォーマンス問題 → 即座に 5% に戻す

Day 3:
  - Route53 weighted policy: オンプレ 50%, GC 50%

Day 5:
  - Route53 weighted policy: オンプレ 0%, GC 100%
  - オンプレアプリケーション停止
```

**パターン C: Blue-Green 切替（完全冗長）**

```
事前:
  Blue 環境: オンプレ（本番）
  Green 環境: GC（検証済み）

切替前:
  - Green 環境を本番トラフィック流量で負荷テスト
  - データベース同期が完了
  - ロードバランサー（ELB / ALB）に両方登録

切替当日:
  - ELB / ALB ターゲット グループ: Blue → Green に変更
  - トラフィック 100% → Green へ
  - Blue は 7日間待機（問題発生時の復帰用）

問題発生時:
  - ELB / ALB ターゲット グループ: Green → Blue に戻す
```

## 4. 切戻し（ロールバック）手順

### 4.1 即座切戻し（T0 - T+6時間以内）

**前提条件**: 既存オンプレ環境がオンライン状態

```
Step 1: アラート検知（T+0分）
  - CloudWatch アラーム / ログが異常を検知
  - インシデント判定: 重大度 SEV1 / SEV2

Step 2: 切戻し判定（T+5分）
  - オンコール対応者が 3 人以上の判定で「Go」
  - Go/No-Go チェックリスト実施

Step 3: 切戻し実行（T+10分）
  - Route53 Weighted Policy: GC 100% → オンプレ 100%
  - または ELB ターゲット グループから GC 削除
  - Alt) 緊急 DNS キャッシュクリア（ブラウザキャッシュ対応）

Step 4: 検証（T+15分）
  - オンプレアプリケーション 応答確認
  - エラーレート 0% 確認
  - ユーザ報告 / 問い合わせ監視

Step 5: 原因調査（T+30分 以降）
  - CloudWatch / CloudTrail ログ確認
  - GC側リソース メトリクス確認
  - 根本原因分析（RCA）開始
```

### 4.2 延長切戻し（T+6時間 - T+7日）

```
前提: GC環境でデータロスが発生した場合

Step 1: GC側リソース停止
  - ECS タスク停止 / RDS デタッチ
  - CloudWatch アラーム無効化（誤検知防止）

Step 2: データリストア
  - 最新バックアップから RDS リストア
  - S3 からデータ復旧
  - 一貫性チェック実行

Step 3: オンプレ と GC のデータ同期
  - DMS で GC → オンプレ へ逆同期（ローカル DB → GC DB）
  - または手動でオンプレ データベース をリセット

Step 4: GC 再カットオーバー
  - 原因対応後、GC側再度本番化
  - カナリアリリース（5% → 20% → 50% → 100%）
```

## 5. Go / No-Go チェックリスト

#### インフラストラクチャチェック

- [ ] VPC / Subnet / セキュリティグループ設定確認

- [ ] IAM ロール / ポリシー適用確認

### 5.4 Approval Gate（オンコール判定基準）

| チェック項目 | NG判定条件 | 対応 |
|-----------|---------|------|
| ヘルスチェック成功率 | < 95% | 原因特定、修復後に再判定 |
| エラーログ（1分単位） | > 10件 | 原因特定、修復後に再判定 |
| DB同期遅延 | > 60秒 | DMS 再設定、遅延回復まで待機 |
| TLS/SSL証明書有効期限 | < 30日 | 証明書更新後に進行 |
| インフラリソース準備 | 不完全（チェックリスト < 100%） | 不足項目対応後に再判定 |

**Go 判定の必須条件**:
- インフラ / アプリケーション チェックリスト **100%** クリア
- セキュリティチェック **100%** クリア
- パフォーマンスチェック **100%** クリア
- オンコール team **全員** 承認（3 人以上のコンセンサス）
