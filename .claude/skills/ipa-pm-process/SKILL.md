# IPA共通フレーム2013 プロジェクト管理プロセス

## 概要

IPA（情報推進機構）共通フレーム2013は、日本の標準的なシステム開発プロセスモデルです。プロジェクト管理は以下の3つのプロセスで構成されます：

1. **計画（Planning）** — プロジェクト方針設定、WBS作成、スケジュール策定、リスク計画
2. **アセスメント（Assessment）** — 進捗状況把握、リスク評価、品質測定
3. **制御（Control）** — 是正措置、スコープ変更管理、文書管理

---

## 1. 計画プロセス (PM.1)

### 目的
プロジェクトの目標を達成するための枠組みを構築し、実行計画を策定する。

### 主要活動

#### 1.1 プロジェクト方針の設定
- 達成目標（ビジネス目標 + 技術目標）
- スコープ境界の定義（含む/除外する機能）
- 成功基準（メトリクス）
- ステークホルダー特定と関係者分析（RACI）

#### 1.2 WBS（仕事分解構造）の策定
**基本原則:** 成果物ベース（工程ベースではない）

```
プロジェクト
├─ フェーズ（例：要件定義）
│  ├─ 成果物（例：要件定義書）
│  │  ├─ タスク1
│  │  ├─ タスク2
│  │  └─ タスク3
│  └─ 成果物2
└─ フェーズ2
```

**チェックリスト:**
- [ ] WBS の葉（最下位）がすべて実行可能なタスクか
- [ ] 100% ルール（親の工数 = 子の工数合計）に従っているか
- [ ] タスク単位の工数が 10-80h の範囲か（1-10h は細かすぎる）
- [ ] すべてのタスクに担当者と期間を割り当てたか

#### 1.3 スケジュール計画
- 工数から日程への変換（リソース配置、稼働率考慮）
- マイルストーン設定（フェーズ完了、レビュー実施日等）
- クリティカルパス分析
- バッファ配置（10-20%）

```
工数変換の公式：
期間 (日) = (タスク工数 / 8h) / (割り当て人数 × 稼働率)

例：
- タスク工数: 40h
- 割り当て人数: 1 人
- 稼働率: 70% (MTG 等の間接業務を考慮)
- 期間: (40 / 8) / (1 × 0.70) = 5 / 0.70 = 約 7 日
```

#### 1.4 リソース計画
- 必要スキル（言語、ツール、経験年数）
- 人員確保計画
- 外注範囲の定義

#### 1.5 コミュニケーション計画
- ステークホルダー分析（影響度/関心度の2×2)
- 報告体制（誰に、何を、どのくらいの頻度で）
- エスカレーションパス定義

#### 1.6 リスク管理計画
- リスク識別カテゴリ：技術 / 体制 / スケジュール / 要件 / 外部
- 対応戦略：回避 / 軽減 / 受容 / 転嫁
- 監視指標（SPI, CPI, バグ密度等）

#### 1.7 品質管理計画
- 品質目標（可用性 99.9%, セキュリティ等級 等）
- テスト戦略（単体/結合/UAT）
- レビュー計画（設計/コードレビュー）
- 検査判定基準（テストカバレッジ 80% 等）

### 成果物
- プロジェクト計画書（WBS + スケジュール + リソース計画）
- リスク登録簿（初期状態）
- 品質管理計画
- コミュニケーション計画

## 2. アセスメントプロセス (PM.2)

### 目的
プロジェクトの進捗状況を測定・分析し、意思決定に必要な情報を提供する。

### 主要活動

#### 2.1 進捗状況の把握
- 実績データ収集（完了タスク、実績工数、実績コスト）
- EVM（Earned Value Management）計算
  - PV（計画価値）
  - EV（獲得価値）
  - AC（実績コスト）
  - SPI = EV / PV （スケジュール効率性指数）
  - CPI = EV / AC （コスト効率性指数）

**判定基準:**
```
┌─────────────┬────────────┬───────────────┐
│ メトリクス   │ 基準値      │ 判定          │
├─────────────┼────────────┼───────────────┤
│ SPI         │ >= 1.0     │ ✓ 進度OK      │
│             │ 0.9-1.0    │ △ 警告        │
│             │ < 0.9      │ ✗ 大幅遅延    │
├─────────────┼────────────┼───────────────┤
│ CPI         │ >= 1.0     │ ✓ 予算OK      │
│             │ 0.95-1.0   │ △ 警告        │
│             │ < 0.95     │ ✗ 超過        │
└─────────────┴────────────┴───────────────┘
```

#### 2.2 リスク評価
- リスク確率 × 影響度 の再評価
- 新規リスク検出
- 顕在化予兆の検出

```
リスク度マトリクス:
           確率
影響   低  中  高
度 低  1  2  3
   中  2  4  6
   高  3  6  9

対応優先度:
- 度数 9, 8: 即座の対応、承認者報告
- 度数 4, 6: 対応計画立案
- 度数 1, 2, 3: 監視継続
```

#### 2.3 品質測定
- テストカバレッジ測定
- バグ密度（摘出バグ数 / ソースコード規模）
- レビュー指摘密度
- FP生産性

#### 2.4 傾向分析
- SPI / CPI の推移から完了予測（EAC）を算出
- 是正措置の効果測定
- 予測完了日（Estimated At Completion）

```
EAC（完了時総見積コスト）:
EAC = AC + (BAC - EV) / CPI

例：
AC (実績コスト) = ¥5,000,000
BAC (計画総工数) = 1000h
EV (獲得価値) = 400h
CPI = EV / AC = 0.8

EAC = 5M + (1000h - 400h) / 0.8
    = 5M + 750h （計画超過 250h）

→ 報告「現状の効率が続くと、完了コストは当初計画から +250h となる見通し」
```

### 成果物
- 月次進捗報告書（メトリクス + 分析）
- リスク管理表（更新版）
- EVM データシート（PV/EV/AC 時系列）

## 3. 制御プロセス (PM.3)

### 目的
プロジェクトを計画通りに実行し、逸脱を検出して是正する。

### 主要活動

#### 3.1 是正措置の実施
**是正措置の種類:**
1. **スコープ調整** — 機能削減や段階的なリリース
2. **リソース追加** — チーム人数増員
3. **スケジュール調整** — 納期延期（顧客合意必須）
4. **プロセス改善** — レビュー強化、テスト自動化等

**是正措置の流れ:**
```
SPI < 0.9 検出
   ↓
原因分析（なぜ遅れたのか）
   ↓
対応案検討（3-5案を提案）
   ↓
実行可能性検証（工数、コスト、スケジュール影響）
   ↓
ステアリングコミッティ承認
   ↓
実行 + 効果測定
```

#### 3.2 スコープ変更管理
**変更フロー:**
```
1. 変更要求受付 （CHG-YYYYMMDD-001）
2. 影響分析 （@infra-impact-analysis）
3. 見積もり （工数 + コスト）
4. 承認判定 （軽微: PM / 中程度: 技術リード+PM / 大規模: ステアリングコミッティ）
5. 実装 （GitHub PR ベース）
6. 統合検証
```

**影響度判定:**
```
軽微：テストケース < 5件追加 / ドキュメント修正のみ
中程度：テストケース 5-20件追加 / 既存アーキテクチャへの小規模拡張
大規模：アーキテクチャ変更 / 新コンポーネント導入 / 納期への影響 > 1週間
```

#### 3.3 文書管理
- バージョン管理（設計書 v1.0 → v1.1 等）
- 構成管理台帳（どの版が本番か）
- 変更履歴追跡
- ベースライン（確定版）の管理

#### 3.4 ステークホルダー報告
- 進捗状況報告（週次 / 月次）
- 問題報告（リスク、課題、変更）
- エスカレーション（承認者判断が必要な事項）

### 成果物
- 是正措置報告書（原因 + 対応策 + 効果）
- 変更管理台帳
- 構成管理台帳（更新版）

## 4. 一般的なフェーズゲート（判定基準）

### 要件定義完了時
```
✓ 合格要件:
- [ ] 機能要件数 >= 50件
- [ ] 非機能要件が 6カテゴリ×各 5件以上
- [ ] 未決事項 <= 5件
- [ ] ステークホルダー承認取得
```

### 設計完了時
```
✓ 合格要件:
- [ ] 全設計書のレビュー実施済み（指摘密度 > 0.5件/ページ）
- [ ] セキュリティレビュー で Level 1, 2 指摘ゼロ
- [ ] 設計と要件の整合性確認済み
```

### 実装（単体テスト）完了時
```
✓ 合格要件:
- [ ] テストカバレッジ >= 80%
- [ ] バグ密度 <= 0.5/KLOC
- [ ] Level 1, 2 バグ ゼロ
```

### リリース判定
```
✓ 合格要件:
- [ ] Level 1, 2 バグ ゼロ
- [ ] Level 3 バグ <= 2件
- [ ] テスト実行率 >= 95%
- [ ] ユーザー承認取得
```

---

## 5. よくある失敗パターンと対策

| パターン | 原因 | 対策 |
|---------|------|------|
| スケジュール遅延 | WBS が工程ベース / バッファなし | 成果物ベース + 10-20% バッファ必須 |
| コスト超過 | 見積もり不足 / スコープ増加 | 変更管理ルール厳格化 |
| リスク顕在化 | 初期リスク識別不足 | リスクワークショップ実施 |
| 品質問題 | 品質基準が曖昧 | 定量的基準（テストカバレッジ等）を設定 |
| ステークホルダー不満 | コミュニケーション不足 | 定期報告 + 課題の早期報告 |
