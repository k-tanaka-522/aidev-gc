# 技術提案書 構成パターン

## 概要
GCインフラ案件向けの技術提案書（営業資料）の構成パターンと、各セクション毎の記載ポイント。

---

## 提案書の3 つのレベル

### Level 1: 営業提案書（初期営業向け）
**ページ数:** 8-12頁
**対象読者:** 予算編成者、情報システム部門のマネージャー、購買部門
**目的:** 受注獲得、ビジネス条件の初期合意

### Level 2: 技術提案書（詳細設計後）
**ページ数:** 15-25頁
**対象読者:** 技術責任者、部門長、情報セキュリティ責任者
**目的:** 技術的信頼度向上、技術方針の承認

### Level 3: 統合提案書（大型案件向け）
**ページ数:** 30頁以上
**対象読者:** 経営層、全ステークホルダー
**目的:** 経営的・技術的な総合判断、最終受注決定

---

## Level 1: 営業提案書（8-12頁）の構成

### P1. 表紙
```
[企業ロゴ]

技術提案書

案件名: A市 基幹システムGC移行プロジェクト

提案企業: [企業名]
提案日: 20XX年Y月Z日
有効期限: 20XX年Y月（+30日）
```

### P2. 案件理解・現状分析
```
## 1. 案件理解

### 1.1 現在の課題
- 既存システムの老朽化（COBOL, 汎用機）
- セキュリティリスク、保守難
- スケーラビリティ制約

### 1.2 期待される効果
- クラウドによるコスト削減（保守負荷削減）
- セキュリティ強化（ISMAP対応）
- スケーラビリティの向上

### 1.3 重要な制約
- 本稼働期限: XX年XX月（XX ヶ月）
- セキュリティ: ISMAP対応必須
- ネットワーク: LGWAN接続要件あり
- 予算: 概算 XX万円
```

### P3. 提案概要・技術方針
```
## 2. 提案概要

### 2.1 提案システムアーキテクチャ
- **クラウド**: AWS ガバメントクラウド（GC）を採用
- **利用方式**: [単独利用 / 共同利用]
- **移行方式**: R1（IaaS + 一部PaaS化）
  - 既存ロジックはEC2で継続実行
  - 重い処理（DB）はRDSに移行
  - 将来的にはコンテナ化を検討

### 2.2 技術的なメリット
| メリット | 説明 |
|---------|------|
| セキュリティ | ISMAP認定クラウドを活用、監査対応も容易 |
| スケーラビリティ | Auto Scalingで需要に応じた自動スケーリング |
| コスト効率化 | オンプレミスの固定費から変動費へ |
| 運用効率化 | AWS のマネージドサービス活用 |

### 2.3 ネットワーク設計方針
- 既存LGWAN接続を継続（セキュリティ維持）
- AWS側もLGWAN専用VPCを構築
- DirectConnect（専線）による接続確保（オプション）
```

[テーブル: PM 1名, Architect 1名, Infra-SE 2-3名, NW-SE 1名, Sec-SE 1名, QA 2名など]

### 3.2 スケジュール概要

|---------|------|--------|
| Phase 0-2 | 3ヶ月 | 要件定義書承認 |
| Phase 3-4 | 2ヶ月 | 詳細設計完了 |

[Gantt図]
```

### P5. セキュリティ・コンプライアンス対応
```
## 4. セキュリティ・コンプライアンス

### 4.1 ISMAP対応
- AWS GC は既に ISMAP 認定済み
- 当社のセキュリティ設計は ISMAP基準に準拠
- 外部監査対応：年2回の脆弱性診断を実施

### 4.2 個人情報保護対応
- 個人情報保護条例対応
- データ暗号化（保存時: AES-256, 転送時: TLS 1.2）
- アクセス制御: IAM ロールベース

### 4.3 監査証跡
- CloudTrail による全APIログの記録
- VPC Flow Logs によるネットワークログ
- 1年間の監査ログ保持
```

```

### 5.3 支払条件（案）
- 契約時: 50%
- Phase 4完了時: 25%
- Phase 8完了時: 25%

### 5.4 納期
- 開始予定: XX年XX月
- 本稼働予定: XX年XX月（XX ヶ月後）

### P7. リスク・前提条件
```
## 6. リスク・前提条件

### 6.1 主要リスク と対応
| リスク | 影響 | 対応方針 |
|--------|------|---------|
| ユーザー側リソース不足 | 要件定義遅延 | 事前のコミットメント確保 |
| 既存NW複雑性 | 設計工数増 | Phase 2 で詳細調査 |
| セキュリティ診断指摘 | 設計修正 | 外部診断を早期実施 |

### 6.2 前提条件
1. ユーザー側PM配置（専任推奨）
2. 既存システムドキュメント完備
3. GCAS申請は提案企業が主体（GC登録企業）
4. ヒアリング協力体制（週1回以上）

### 6.3 除外事項
- AWS利用料の見積（AWS パートナー見積別途）
- セキュリティ診断費用（別途 +800万円程度）

## Level 2: 技術提案書（15-25頁）の構成

Level 1のすべて + 以下を追加：

### 追加P: ネットワーク設計の詳細
```
## 8. ネットワーク設計

### 8.1 ネットワークトポロジー
[図: VPC（3段階構造）、LGWAN接続、DirectConnect、オンプレNW]

### 8.2 VPC構成
| VPC名 | 用途 | CIDRブロック | サブネット数 |
|------|------|-----------|----------|
| VPC-LG | LGWAN用 | 10.0.0.0/16 | 6 |
| VPC-WEB | Web層 | 10.1.0.0/16 | 4 |
| VPC-DB | DB層 | 10.2.0.0/16 | 4 |
| VPC-OPS | 管理 | 10.3.0.0/16 | 2 |

### 8.3 ルーティング・NAT戦略
- NAT Gateway: 複数AZに配置（冗長化）
- VPC Peering: VPC間通信
- Transit Gateway: 複数VPC管理
```

### 追加P: セキュリティ設計の詳細
```
## 9. セキュリティ設計

### 9.1 セキュリティレイヤー
[図: WAF → ALB → SG → EC2 → RDS]

### 9.2 IAM設計
- ロールベースアクセス制御（RBAC）
- 各部門の職務に応じたロール定義
- MFA（多要素認証）の強制

### 9.3 暗号化戦略
- 保存時: AWS KMS（AES-256）
- 転送時: TLS 1.2以上
- データベース: RDS暗号化

### 9.4 監査・コンプライアンス
- CloudTrail: 全APIログ
- VPC Flow Logs: ネットワークトラフィック
- Config: リソース構成の監視
- ログ保持期間: 1年（カスタマイズ可）
```

### 追加P: IaC (Terraform) 設計
```
## 10. IaC (Infrastructure as Code) 戦略

### 10.1 Terraformの利用方針
- VPC、EC2、RDS、セキュリティグループの自動化
- 環境別（dev/stg/prod）のコード分離
- バージョン管理（Git）と CI/CD 連携

### 10.2 ディレクトリ構造
```
terraform/
├── environments/
│   ├── dev/
│   ├── stg/
│   └── prod/
├── modules/
│   ├── vpc/
│   ├── ec2/
│   ├── rds/
│   └── security/
├── main.tf
├── variables.tf
└── outputs.tf
```

### 10.3 CI/CD パイプライン
- GitHub → AWS CodePipeline
- terraform plan/apply の自動実行
- 承認ゲート（本番環境）
```

### 11.1 監視対象と KPI

|---------|-----|-------|------|

```
## 12. 災害対応 (DR) ・事業継続計画 (BCP)

### 12.1 RTO/RPO目標値
- RTO (復旧時間目標): 15分
- RPO (復旧ポイント目標): 1時間

### 12.3 バックアップ戦略

## 提案書作成時のチェックリスト

```
□ 表紙: 企業ロゴ、案件名、提案日、有効期限を記載
□ 案件理解: 現状課題と期待効果を明確に記述
□ 技術方針: なぜこの設計か、メリット・デメリットを説明
□ ネットワーク図: VPC、LGWAN接続、DirectConnectを可視化
□ セキュリティ: ISMAP、個人情報保護への対応を明記
□ 体制: PM、Architect、SEなど、経験年数・実績を記載
□ スケジュール: Gantt図で全フェーズの期間を可視化
□ 見積: 人日×単価の計算根拠を明示
□ リスク: 主要リスク と対応方針を記載
□ 参考実績: 同規模・同種の過去案件を3件以上紹介
□ 企業紹介: 認定資格（ISMAP, ISO27001など）を記載
□ ページ番号・目次: 15頁以上の場合は目次を付ける
□ 色使い・図表: 白黒でも読みやすく、カラーで区別を図る
□ 言語: 「AWSの活用により」「クラウドネイティブ化」など技術用語を平易に説明
□ 審査: 内部レビュー（PM、上長）を経て最終版を作成
```
