# 抜け漏れ検知パターン集

## 1. Phase 2（要件定義完了時）フェーズゲートチェック

### 1.1 要件の網羅性チェック

#### ビジネス要件

- [ ] システムの目的・ゴールが明確に記載されている
- [ ] 対象ユーザ・ステークホルダーが列挙されている
- [ ] ユーザストーリーが最低 20 件以上記載されている（詳細度: As a [role], I want to [action], so that [benefit]）
- [ ] 各ユーザストーリーに受け入れ条件（AC）が記載されている
- [ ] マイグレーション対象システムの現状（AS-IS）を文書化している
- [ ] AS-IS から GC への改善ポイントが列挙されている
- [ ] スコープの明確化（対象外システムも明記）

#### 非機能要件

- [ ] パフォーマンス要件
  - [ ] API レスポンスタイム（p99）の目標値
  - [ ] スループット（req/sec）の目標値
  - [ ] 同時接続ユーザ数予測
  - [ ] ピーク時トラフィック予測

- [ ] 可用性・信頼性要件
  - [ ] SLA（可用性 99.5% / 99.9% / 99.99%）
  - [ ] RTO（目標復旧時間）
  - [ ] RPO（目標復旧ポイント）
  - [ ] バックアップ頻度
  - [ ] 冗長化方式（Active-Active / Active-Standby）

- [ ] セキュリティ要件
  - [ ] 情報セキュリティレベル（L1 / L2 / L3）
  - [ ] 個人情報保護法 / GDPR 対応の必要性
  - [ ] 暗号化要件（TLS 1.2 以上、AES-256 等）
  - [ ] 監査ログ要件（CloudTrail / VPC Flow Logs）
  - [ ] アクセス制御（IAM / MFA 要件）
  - [ ] ISMAP 対応の必要性
  - [ ] ペネトレーションテスト実施予定

- [ ] スケーラビリティ要件
  - [ ] 3 年後のユーザ数 / データ量予測
  - [ ] 自動スケーリングの要件
  - [ ] オートスケーリング上限

- [ ] 保守性・運用要件
  - [ ] 自動デプロイメント要件（CI/CD）
  - [ ] ログ保持期間（7 年等）
  - [ ] パッチ管理方針
  - [ ] バージョンアップ頻度
  - [ ] ホットスタンバイ / グレースフルシャットダウン要件

#### コスト要件

- [ ] 月額 / 年額のコスト予算
- [ ] コスト削減目標（オンプレミス比較）
- [ ] リザーブドインスタンス（RI）/ Savings Plans 活用方針
- [ ] コスト監視・アラート要件（月額 XX 万円超過時）

### 1.2 トレーサビリティ確認

- [ ] 全ユーザストーリーが設計要素にマッピングされている
- [ ] 各要件に対応する設計項目が決まっている
- [ ] 各設計項目に対応するテストケースが計画されている

**トレーサビリティマトリックス例**:

| ユーザストーリー ID | 説明 | 対応する設計 | テストケース |
|------------------|------|-----------|-----------|
| US-001 | ユーザはログインできる | SEC-DESIGN-001（認証設計） | TC-AUTH-001 |
| US-002 | ユーザはファイルをアップロードできる | STORAGE-DESIGN-001 | TC-UPLOAD-001 |

### 1.3 要件間の矛盾チェック

- [ ] 高いパフォーマンス要件と低コスト要件が両立可能か検証
- [ ] 可用性要件と災害復旧要件が一致しているか確認
- [ ] セキュリティ要件とユーザ利便性要件が矛盾していないか確認

### 1.4 現行システム調査の完成度

- [ ] 現行システムのハードウェア構成図が記載されている
- [ ] 現行システムのネットワーク図が記載されている
- [ ] 現行ユーザ数 / データ量が把握されている
- [ ] 現行システムの問題点 / ボトルネックが列挙されている
- [ ] 現行インフラのコスト見積（年額）が記載されている

### 1.5 Phase 2 フェーズゲート判定基準

**Pass 条件**:
- 要件定義書: 合計ページ数 ≥ 50 ページ（エクセキューティブサマリー含む）
- ユーザストーリー数: ≥ 20 件
- 非機能要件: 全カテゴリで最低 1 項目は定義済み
- 現行調査: 完成度 ≥ 80%
- トレーサビリティ: ≥ 95% の要件がマッピング済み
- ステークホルダーレビュー: 全員サイン済み

#### バックアップ・DR 設計書

- [ ] EBS スナップショット戦略（取得頻度、保持期間）
- [ ] RDS バックアップ戦略（自動バックアップ保持期間、手動バックアップ）
- [ ] S3 バージョニング / ライフサイクル設計（長期保存、削除ポリシー）
- [ ] Backup（AWS Backup）戦略（全リソース統合バックアップの場合）
- [ ] RPO / RTO 要件への適合性確認表
- [ ] リストア手順書（ステップバイステップ、テスト方法含む）
- [ ] フェイルオーバー設計書（DNS 切替、Route53 ヘルスチェック）
- [ ] クロスリージョンレプリケーション設計書（必要な場合）

#### コスト最適化設計書

- [ ] EC2 インスタンスタイプ / 数の根拠（ユーザ数、データ量より）
- [ ] EBS ストレージタイプ選定根拠（gp3 / io1 等）
- [ ] RDS インスタンスクラス選定根拠
- [ ] リザーブドインスタンス（RI）/ Savings Plans 活用計画
- [ ] スポットインスタンス活用計画（開発環境等）
- [ ] ネットワーク転送料金見積（クロスリージョン、データ転送出力）
- [ ] 運用自動化による効率化ポイント（コスト削減額）
- [ ] 月額コスト見積表（初期構築、運用フェーズ別）

### 2.2 設計書の品質チェック

#### 完成度

- [ ] 全設計書のページ数 ≥ 200 ページ（図表含む）
- [ ] 設計図のレジェンド（凡例）が記載されている
- [ ] リソース命名規則が明確に定義されている（snake_case、タグ戦略など）
- [ ] 設計書のバージョン、作成日、承認欄が記載されている

#### 正確性

- [ ] 要件 → 設計の対応関係が全て説明されている
- [ ] 各設計要素に対応する IaC リソース / ファイルが明記されている
- [ ] セキュリティグループ / NACL ルールが矛盾していない（許可 / 拒否）
- [ ] IAM ポリシーが最小権限に基づいている（ワイルドカード * の使用最小化）
- [ ] KMS 鍵のポリシーが設計通りに記載されている
- [ ] ルーティング設計に矛盾がない（ルート優先度、デフォルトルート）

#### 実装可能性

- [ ] 各設計が AWS GC の制限値を超えていないか確認
  - [ ] セキュリティグループあたりのルール数（≤ 600）
  - [ ] 1 つのセキュリティグループからの参照数（≤ 1000）
  - [ ] VPC あたりの subnet 数（≤ 200）
  - [ ] Route Table あたりのルート数（≤ 1000）
- [ ] EBS ボリュームサイズが GC 制限内（≤ 16 TiB）
- [ ] RDS ストレージサイズが制限内（MySQL: ≤ 65 TiB など）

### 2.3 要件 → 設計の対応確認

- [ ] 全ユーザストーリー（US-xxx）が設計要素に対応している

### 2.4 設計間の矛盾確認

## 3. Phase 5（実装（IaC）完了時）フェーズゲートチェック

### 3.1 IaC コード品質チェック

#### 構文 / フォーマット

- [ ] terraform validate: エラーなし

- [ ] linter（tflint 等）: 警告 ≤ 10 件

#### リソース定義の完全性

- [ ] ハードコード化された機密情報（パスワード、API キー）がない
- [ ] 機密情報は Secrets Manager / Parameter Store を使用している
- [ ] IAM ポリシーが最小権限に基づいている（* 使用最小化）

#### IaC モジュール化

- [ ] モジュール化されたコンポーネント（ネットワーク、セキュリティ、コンピュート等）
- [ ] 各モジュールに説明コメント（日本語）が記載されている

#### バージョン管理

- [ ] Terraform version: pinned（≥ 1.0）

- [ ] backend 設定: S3 + DynamoDB（state lock）
