# SRE 実践ガイド

## 1. SLI / SLO 定義

### 1.1 SLI（Service Level Indicator）とは

信頼性を測定する指標。システムがどれだけ正常に動作しているかを数値化する。

**例**:
- API 応答時間が 500ms 以下の割合
- ネットワークパケットロス率が 0.1% 以下
- ディスク I/O エラーなしの稼働時間割合

### 1.2 SLO（Service Level Objective）とは

SLI の目標値。チーム間でのコミットメント。

**例**:
- API 応答時間が 500ms 以下の割合: **99.5%**
- ディスク I/O エラーなしの稼働時間: **99.9%**
- ネットワークパケット損失: **0.01% 未満**

### 1.3 SLI / SLO 定義テンプレート

```
【SLI / SLO 定義書】

サービス名: [例: Web API Service]
対象環境: 本番
定義日: YYYY-MM-DD

【SLI / SLO リスト】

| No. | 指標名 | SLI 測定方法 | 目標値 (SLO) | 集計期間 | オーナー |
|-----|--------|-----------|-----------|---------|---------|
| 1 | API 応答時間（p99） | CloudWatch Metric / ApplicationELB Target Response Time | 99.5% が 500ms 以下 | 30日 | AppChamp |
| 2 | API エラー率（5xx） | (5xx レスポンス数 / 全リクエスト) × 100 | < 0.1% | 30日 | AppChamp |
| 3 | DB クエリ応答時間 | CloudWatch RDS Performance Insights | 99% が 100ms 以下 | 30日 | DBChamp |
| 4 | DB トランザクション完了率 | (成功commit数 / 全トランザクション) × 100 | > 99.9% | 30日 | DBChamp |
| 5 | インフラ稼働率 | EC2/RDS/ELB が Healthy 状態の時間割合 | 99.9% | 30日 | InfraChamp |
| 6 | DNS 応答時間 | Route53 クエリ応答時間（CloudWatch） | p99 < 50ms | 30日 | InfraChamp |
| 7 | ログ出力遅延 | CloudWatch Logs 取得完了までの時間 | p99 < 5秒 | 30日 | OpsChamp |

【SLI の詳細定義】

No. 1: API 応答時間（p99）
  - 測定対象: ALB を通過する全 HTTP リクエスト
  - 計算式: CloudWatch Metric "TargetResponseTime" の 99パーセンタイル値
  - 除外条件: キャッシュヒット（3xx応答）は含まない
  - 報告時期: 毎日 09:00 に前日集計値をSlackに通知

No. 2: API エラー率（5xx）
  - 測定対象: ALB を通過する全 HTTP リクエスト
  - 計算式: (5xx レスポンス数 / 全リクエスト数) × 100
  - 除外条件: オーバーロード時（429応答）は除外
  - 報告時期: リアルタイムアラート（1件以上で Slack 通知）+ 日次集計

No. 3: DB クエリ応答時間
  - 測定対象: Amazon RDS への SQL クエリ
  - 計算式: CloudWatch RDS Performance Insights の Database Load の p99値
  - 除外条件: バックアップ中のロック時間は除外
  - 報告時期: 毎日 09:00 に前日集計値をSlack通知

No. 4: DB トランザクション完了率
  - 測定対象: 全 SQL トランザクション
  - 計算式: (commit成功数 / (commit成功数 + rollback数 + timeout数)) × 100
  - 除外条件: ロール・バック（意図的なabort）は含める
  - 報告時期: 日次 + 月次集計

No. 5: インフラ稼働率
  - 測定対象: EC2, RDS, ELB, VPN, DirectConnect
  - 計算式: (Health = Healthy な時間) / (測定期間) × 100
  - 除外条件: 計画メンテナンス（事前告知 7日）は除外
  - 報告時期: 毎日 09:00 に前日稼働率を報告

No. 6: DNS 応答時間
  - 測定対象: Route53 への DNS クエリ
  - 計算式: Route53 CloudWatch Metric "QueryCount" の平均応答遅延
  - 除外条件: キャッシュされたレコード（ALIAS）は含める
  - 報告時期: 日次 + 月次集計

No. 7: ログ出力遅延
  - 測定対象: CloudWatch Logs へのログ送信 → ログ取得までの遅延
  - 計算式: timestamp (ログ生成) → timestamp (Logs取得可能) の時間差
  - 除外条件: バッチログ（kinesis firehose）は含める
  - 報告時期: リアルタイム（異常値）+ 日次集計
```

## 2. エラーバジェット（Error Budget）計算

### 2.1 エラーバジェットの概念

SLO が 99.5% の場合、残り **0.5% が許容される落下時間**。

### 2.2 計算式

```
エラーバジェット = (100% - SLO) × 測定期間

例1: 月単位（30日）
  SLO = 99.5%
  許容ダウンタイム = 0.5% × 30 日 × 24 時間 = 3.6 時間 / 月

例2: 四半期（90日）
  SLO = 99.9%
  許容ダウンタイム = 0.1% × 90 日 × 24 時間 = 2.16 時間 / 四半期

例3: 年単位（365日）
  SLO = 99.99%
  許容ダウンタイム = 0.01% × 365 日 × 24 時間 = 52.6 分 / 年
```

### 2.3 エラーバジェット計画表

```
【エラーバジェット月次レポート】

サービス: Web API Service
対象期間: 2024-04-01 〜 2024-04-30
報告日: 2024-05-01

【SLO vs 実績】

| 指標 | SLO | 実績達成率 | ステータス | 備考 |
|------|-----|----------|----------|------|
| API 応答時間 p99 | 99.5% | 99.78% | PASS | エラーバジェット余裕あり |
| API エラー率 | < 0.1% | 0.08% | PASS | 良好 |
| DB 応答時間 | 99% | 99.12% | PASS | 良好 |
| インフラ稼働率 | 99.9% | 99.85% | NEAR-MISS | 監視強化が必要 |

【エラーバジェット消費状況】

API 応答時間（99.5% SLO）:
  - 月次許容ダウンタイム: 3.6 時間
  - 実績達成率: 99.78%（許容値 99.5%を超過）
  - 消費額: -0.28%（マイナス = 余裕あり）
  - 評価: 順調

インフラ稼働率（99.9% SLO）:
  - 月次許容ダウンタイム: 43.2 分
  - 実績達成率: 99.85%（許容値 99.9%を下回る）
  - 消費額: +0.05%（正の値 = 消費）
  - 評価: やや注意（傾向を継続監視）

【消費原因分析】

インフラ稼働率 消費原因:
  - 2024-04-15 14:30-15:20 (50分): VPN ルーター不具合（自動フェイルオーバー発動）
  - 原因: BGP ルート更新遅延
  - 改善アクション: BGP タイムアウト値見直し（進行中）

【翌月方針】

- VPN ルーターの BGP パラメータ最適化（5月中完了目指す）
- DB クエリ監視をさらに強化（新しいスローログアラート追加）
- API レスポンスタイム測定精度向上（CloudFront キャッシュ影響排除）
```

## 3. ポストモーテム（事後分析）テンプレート

### 3.1 実施タイミング

- **インシデント発生直後**: 初期対応完了後、48 時間以内に開催
- **参加者**: インシデント対応チーム全員 + 管理層 + 関連チーム

### 3.2 ポストモーテムテンプレート

```
【ポストモーテム報告書】

案件: [インシデントコード] INC-2024-0501-001
タイトル: API サーバメモリリークによる応答時間増加
発生日時: 2024-04-30 14:23 JST
検出日時: 2024-04-30 14:35 JST（12分後）
復旧日時: 2024-04-30 15:10 JST（47分後）
実施者: Infrastructure Team
報告者: On-call Engineer (A)
報告日: 2024-05-01

【インシデント概要】

概要:
  API サーバメモリリーク により、メモリ使用率が 92% に達し、
  アプリケーションの GC（Garbage Collection）ポーズ時間が
  増加し、API レスポンスタイム が SLO（500ms）を超過。

影響範囲:
  - 影響サービス: Web API Service
  - 影響ユーザ: 約 50,000 名（全ユーザの 15%）
  - 実影響時間: 47 分
  - 推定損失: 約 100 万円（トラフィック低下 × 売上）

【タイムライン】

| 時刻 | 発生者 | 対応内容 | 詳細 |
|------|--------|---------|------|
| 14:23 | Monitoring | CloudWatch アラーム発火 | CPU 使用率 75%, メモリ 88% |
| 14:30 | AppChamp | EC2 インスタンス確認 | メモリ使用率増加傾向を確認 |
| 14:35 | InfraChamp | オンコール呼び出し | インシデント判定 SEV1 |
| 14:38 | AppChamp | ヒープダンプ取得 | メモリリーク候補箇所を特定 |
| 14:45 | InfraChamp | インスタンス自動再起動 | クイックフィックス実行 |
| 14:50 | AppChamp | メモリ確認 | 正常に回復（使用率 45%） |
| 15:10 | InfraChamp | 復旧完了判定 | 全サーバ正常、トラフィック復帰 |
| 15:15 | DBChamp | DB 一貫性確認 | ロールバック不要、データ正常 |

【根本原因分析】

直接的原因:
  - アプリケーションコード内にメモリリークが存在
  - 特定の API エンドポイント呼び出し時に、
    キャッシュオブジェクトがメモリから解放されない
  - コード行番号: app/api/handlers.py line 234-248

根本原因の根源:
  1. 開発時にヒープダンプテストが実施されなかった
  2. コードレビュー時に リソース解放漏れを見落とした
  3. ステージング環境でのメモリ負荷テストが不十分

Contributing Factors（加糖因子）:
  - 本番環境での自動メモリ監視が 5 分ごとのポーリング
    → より細かい監視間隔なら 5 分以上早期検知可能
  - インスタンス自動再起動設定がなかった
    → 自動フェイルオーバーで回復時間短縮可能

【改善アクション】

| アクション | 優先度 | 責任者 | 期日 | ステータス |
|-----------|--------|--------|------|----------|
| メモリリーク バグ修正 | P0 | AppChamp | 2024-05-02 | 着手 |
| コード中の全リソース管理を監査 | P0 | AppChamp | 2024-05-08 | 予定 |
| ステージング環境で 1 時間メモリ負荷テスト追加 | P1 | QAChamp | 2024-05-07 | 予定 |
| CloudWatch メモリ監視インターバルを 1 分に短縮 | P1 | InfraChamp | 2024-05-03 | 完了 |
| EC2 インスタンス自動再起動設定（アプリ異常時） | P1 | InfraChamp | 2024-05-06 | 予定 |
| コードレビュー チェックリストに「リソース解放」項目追加 | P2 | TechLead | 2024-05-09 | 予定 |

【学んだ教訓（Lessons Learned）】

よかったこと（What went well）:
  - オンコール体制が機能し、12 分以内に対応チーム動員
  - DB 側は独立しており、データ整合性が保たれた
  - 自動スケーリングにより他インスタンスがトラフィック吸収

改善すべき点（What could be improved）:
  - ステージング環境での負荷テストをもっと厳密に
  - コードレビュー時の資源管理チェックリストが不足
  - メモリ監視の時間解像度がまだ粗い

アクション跨度への投資判断:
  - 短期（1-2週）: メモリリーク修正 + 監視改善
  - 中期（1-3ヶ月）: テスト自動化 + コードレビュー改善
  - 長期（3-6ヶ月）: メモリリーク検知ツール導入検討

【関連する過去インシデント】

- INC-2024-0401-003: 別アプリケーション でもメモリリーク報告
  → 同じコード部品の問題か、共通の開発ガイドライン不足か、確認予定

【確認事項・フォローアップ】

- [ ] バグ修正 PR のコードレビュー（2 名以上）
- [ ] 修正版本番デプロイ前のリグレッションテスト
- [ ] 既存本番環境での類似パターン監査
- [ ] 1 週間後: メモリリーク再発がないか確認
- [ ] 1 ヶ月後: 改善アクション 実施状況確認
```

## 4. オンコール設計

### 4.1 オンコール体制構成

```
【オンコール構成】

体制: 3 チーム × 3 ローテーション = 週 24/7 カバー

| チーム | 専門分野 | メンバー数 | 対応時間帯 |
|--------|---------|----------|----------|
| InfraChamp | インフラ（VPC/EC2/RDS/LB） | 5 名 | 24/7 |
| AppChamp | アプリケーション（API/キャッシュ） | 4 名 | 24/7 |
| DBChamp | データベース（RDS/DynamoDB） | 3 名 | 24/7 |

各チーム内ローテーション（1 週間交代）:
  週 1: Engineer-A（主）+ Engineer-B（サブ）
  週 2: Engineer-B（主）+ Engineer-C（サブ）
  週 3: Engineer-C（主）+ Engineer-D（サブ）
  ...
```

### 4.2 オンコール責務

```
主なオンコール対応:

1. アラート検知 → 確認（5 分以内）
   - CloudWatch アラーム自動通知（SMS / Slack）
   - アラート内容確認
   - 初期判定（SEV1 / SEV2 / SEV3 / False Positive）

2. インシデント評価（10 分以内）
   - 影響ユーザ数
   - 影響時間推定
   - 必要なエスカレーション判定

3. 復旧対応（開始 15 分以内）
   - 根本原因の仮説立案
   - 切戻し / リスタート / 設定変更 などの対応実施
   - セカンダリ・エスカレーション判定

4. インシデント発表（30 分ごと）
   - 進捗状況を Slack #incident-response に投稿
   - 管理層への報告（SEV1 の場合）

5. 復旧後の検証（1 時間以内）
   - 全サービスヘルスチェック実行
   - エラーログ確認
   - 復旧完了判定
```

### 4.3 エスカレーションルール

```
【エスカレーションマトリクス】

| 判定項目 | SEV1 | SEV2 | SEV3 |
|---------|------|------|------|
| インシデント検出 | 即座 | 通常対応 | 日中対応 |
| オンコール呼び出し | 主 + サブ + マネージャ | 主のみ | 主のみ |
| 初期対応期限 | 5 分 | 15 分 | 1 時間 |
| 復旧期限 | 30 分 | 2 時間 | 営業日内 |
| 経営層報告 | 即座 | 30 分以内 | 事後 |
| ポストモーテム | 当日中 | 3 営業日以内 | 1 週間以内 |

SEV1 判定条件（全て OR で評価）:
  - 本番環境 全ユーザが利用不可
  - 全ユーザの 50% 以上が影響
  - エラー率が 10% を超える
  - DB 不可用（本番データベース）
  - セキュリティ侵害の可能性

SEV2 判定条件:
  - 本番環境 一部ユーザが利用不可
  - エラー率が 1-10%
  - パフォーマンス低下（SLO 違反）
  - バックアップ / ログ不可用

SEV3 判定条件:
  - 機能制限（一部機能に支障）
  - ステージング環境問題
  - 軽微なパフォーマンス低下
```

### 4.4 オンコール手当 / インセンティブ

```
【オンコール報酬体系】

時間帯別報酬:
  - 営業時間内オンコール（9:00-18:00）: 時給 +500 円
  - 夜間オンコール（18:00-00:00）: 時給 +1,000 円
  - 深夜オンコール（00:00-09:00）: 時給 +1,500 円

インシデント対応報酬:
  - SEV1 対応: 1 回 +5,000 円 + SEV1 期間中の夜勤免除
  - SEV2 対応: 1 回 +2,000 円
  - SEV3 対応: 1 回 +1,000 円

休息日制度:
  - SEV1 復旧後 24 時間以内に 8 時間の休息時間確保
  - 夜間対応者には翌営業日の帰宅時間調整

キャリア評価:
  - オンコール期間中の迅速な対応 → 年間評価 +5%
```

## 5. 監視ダッシュボード構成

```
【運用用ダッシュボード】

リアルタイム監視画面（24/7 表示）:
  - API レスポンスタイム（p99）
  - API エラー率（5xx）
  - DB クエリ遅延（p95, p99）
  - インフラ稼働率（EC2, RDS, ELB）
  - ネットワーク帯域使用率
  - ディスク使用率（全インスタンス）
  - メモリ使用率（全インスタンス）

アラート設定:
  - API レスポンスタイム p99 > 500ms: Yellow (SLO警告)
  - API レスポンスタイム p99 > 1000ms: Red (SLO違反)
  - API エラー率 > 0.5%: Yellow
  - API エラー率 > 1%: Red
  - DB Connection Pool 使用率 > 80%: Yellow
  - インスタンス CPU > 80%: Yellow
  - インスタンス CPU > 95%: Red
  - メモリ使用率 > 85%: Yellow
  - メモリ使用率 > 95%: Red
  - ディスク使用率 > 85%: Yellow
  - ディスク使用率 > 95%: Red（拡張手続き開始）

集計・レポート:
  - 日次 SLO 達成率レポート（毎日 09:00）
  - 週次インシデント集計（毎週月曜 10:00）
  - 月次エラーバジェット消費状況（毎月初日）
```
