# インフラテスト・パターン集

## 1. テスト種別と責務

### 1.1 単体テスト（Unit Test）
- リソース個別の動作確認
- 例：VPC作成、セキュリティグループルール追加
- **責務**: IaC記述者が実施
- **検証方法**: `terraform plan` 出力、`aws cloudformation validate-template`

### 1.2 結合テスト（Integration Test）
- 複数リソース間の連携動作確認
- 例：VPC + Subnet + IGW + Route Table の通信経路確認
- **責務**: インフラエンジニア
- **主要チェック項目**:
  - ネットワーク疎通確認（ping, traceroute）
  - セキュリティグループ/NACL動作検証
  - IAMロール / ポリシーの権限確認
  - DNS解決確認
  - TGW / VPN / DirectConnect接続確認

### 1.3 性能テスト（Performance Test）
- 負荷下での動作、応答時間、スループット確認
- **責務**: QA / パフォーマンスエンジニア
- **主要メトリクス**:
  - レイテンシ (p50, p95, p99)
  - スループット (req/sec, Mbps)
  - CPU / メモリ / ディスク使用率
  - ネットワーク帯域使用率

### 1.4 セキュリティテスト（Security Test）
- 脆弱性、アクセス制御、暗号化、ログ出力の確認
- **責務**: セキュリティエンジニア / ペネトレーションテスター
- **主要項目**:
  - ネットワークセグメンテーション検証
  - IAM権限最小権限確認
  - 暗号化（転送中/保存時）確認
  - SSL/TLS設定確認（TLS 1.2以上）
  - ログ出力 / CloudTrail / VPC Flow Logs 確認
  - WAF / セキュリティグループ動作検証

### 1.5 DR テスト（リストア/フェイルオーバーテスト）
- バックアップからのリストア、フェイルオーバー、RPO/RTO検証
- **責務**: インフラ運用チーム
- **検証項目**:
  - バックアップ作成確認
  - リストア手順の有効性
  - リストア時間計測（RTO）
  - リストア直後のデータ整合性確認（RPO）
  - フェイルオーバー自動化の動作確認

## 2. テストケース設計パターン

### 2.1 パターン: ネットワーク疎通テスト

**テスト名**: VPC / Subnet / セキュリティグループ疎通確認

**前提条件**:
- VPC / Subnet が作成済み
- EC2 インスタンスがセキュリティグループに所属
- テスト用IAMロール / KMS権限が設定済み

**テストケース**:

| No. | テストケース | 検証内容 | 期待結果 |
|-----|-----------|--------|---------|
| TC-NET-001 | 同一Subnet内EC2間疎通 | ping, ssh接続 | 接続成功 |
| TC-NET-002 | 異Subnet同一VPC間疎通 | ping, ssh接続 | 接続成功（Route Table設定を確認） |
| TC-NET-003 | VPC Peering経由疎通 | 対向VPC内EC2へping | 接続成功 |
| TC-NET-004 | TGW経由オンプレ接続 | オンプレホストへping | 接続成功 |
| TC-NET-005 | インターネット出力 | curl https://example.com | 200 OK |
| TC-NET-006 | セキュリティグループ拒否 | 許可されてない宛先ポートへアクセス | タイムアウト |
| TC-NET-007 | NACL拒否 | NACL拒否ルール対象ポートへアクセス | 接続拒否 |

**合否判定**:
- TC-NET-001 〜 006: 全て期待結果と合致
- TC-NET-007: NACL のロギング確認

---

### 2.2 パターン: IAM/KMS テスト

**テスト名**: IAMロール / KMS鍵権限確認

**前提条件**:
- IAMロール / ポリシーが定義済み
- KMS鍵が作成済み
- テスト用の複数ユーザ/ロールが用意

**テストケース**:

| No. | テストケース | 検証内容 | 期待結果 |
|-----|-----------|--------|---------|
| TC-IAM-001 | 管理ユーザがS3バケット操作 | ls, put, get, delete実行 | 全て成功 |
| TC-IAM-002 | 読取専用ユーザがS3操作 | ls, get 実行 / put, delete試行 | get成功、put/delete失敗 |
| TC-IAM-003 | KMS鍵の暗号化 | データ暗号化、復号化 | 成功 |
| TC-IAM-004 | KMS権限拒否 | 権限なしユーザが暗号化データ復号試行 | 失敗 |
| TC-IAM-005 | AssumeRole | 別ロールへのAssumeRole | 成功 |
| TC-IAM-006 | 外部ロールAssumeRole | クロスアカウントロール引き継ぎ | 成功 |

**合否判定**:
- TC-IAM-001 〜 006: 全て期待結果と合致
- KMS监査ログに操作記録が残っていることを確認

**テスト名**: CloudWatch / CloudTrail / VPC Flow Logs 動作確認

**テストケース**:

| No. | テストケース | 検証内容 | 期待結果 |
|-----|-----------|--------|---------|

## 3. 性能テストの合否判定基準

### 3.1 レイテンシ基準

| システム部分 | 項目 | 基準 | 備考 |
|-----------|------|------|------|
| ネットワーク | ping RTT（同リージョン） | p95 < 5ms | AZ内は 1ms 未満を想定 |
| ネットワーク | ping RTT（クロスリージョン） | p95 < 100ms | 東京-シンガポール想定 |
| アプリケーション | API応答時間 | p95 < 500ms | アプリ仕様に応じて調整 |
| アプリケーション | データベースクエリ | p95 < 100ms | インデックス最適化前提 |

### 3.2 スループット基準

| システム部分 | 項目 | 基準 | 備考 |
|-----------|------|------|------|
| ネットワーク | VPC内NIC帯域 | 99%利用可能 | ネットワーク帯幅の最大値 |
| アプリケーション | リクエストスループット | 設計値の 80% 以上 | 負荷分散効果 |

### 3.3 リソース使用率基準

| リソース | 項目 | 基準 | 備考 |
|---------|------|------|------|
| CPU | ピーク使用率 | 80% 未満 | 余裕度を確保 |
| メモリ | 使用率 | 85% 未満 | スワップ使用なし |
| ディスク | 使用率 | 80% 未満 | inode 使用率も確認 |

## 4. セキュリティテストの合否判定基準

### 4.1 ネットワークセキュリティ

| 項目 | 合否基準 |
|------|---------|
| インターネット向けリソース | セキュリティグループで最小権限のみ許可 |
| VPC内リソース | プライベートサブネット内に配置、必要に応じてNAT経由 |
| DirectConnect / VPN | 暗号化され、認証機能を有効 |
| ログ | VPC Flow Logs が有効で、S3 / CloudWatch Logs に出力 |

### 4.2 IAM / 認可

| 項目 | 合否基準 |
|------|---------|
| 最小権限 | 全IAMロール / ポリシーが必要最小限の権限のみを付与 |
| リソースベースポリシー | S3, KMS, SNS等に明示的なリソースベースポリシー設定 |
| アカウント間権限 | AssumeRole 使用、外部ロール ARN を明示 |

### 4.3 暗号化

| 項目 | 合否基準 |
|------|---------|
| 転送中 | TLS 1.2 以上、TLS 1.3 推奨 |
| 保存時 | S3, RDS 等で KMS 暗号化 有効 |
| 鍵管理 | マスターキーが AWS KMS で管理、ローテーション設定有り |

### 4.4 ログ / 監査

| 項目 | 合否基準 |
|------|---------|
| CloudTrail | 有効、全リージョン、管理イベント + データイベント |
| VPC Flow Logs | 有効、ACCEPT/REJECT 両方記録 |
| CloudWatch Logs | セキュリティグループ、IAM 変更がログ出力される |
| アクセスログ | ALB, S3, RDS 等でアクセスログが有効 |

## 5. DR テストの合否判定基準

### 5.1 バックアップ確認

| 項目 | 合否基準 |
|------|---------|
| 作成頻度 | SLA に定義された頻度で作成（日次 / 時間ごと） |
| バックアップ保持期間 | RPO 基準を満たす期間 |
| 整合性チェック | バックアップ直後に整合性検証スクリプト実行 |

### 5.2 リストア手順テスト

| 項目 | 合否基準 | 検証方法 |
|------|---------|---------|
| リストア時間（RTO） | SLA 定義値以内 | テスト環境でリストア実行、時間計測 |
| リストア後データ（RPO） | SLA 定義値以内のデータロス | バックアップ取得時刻と最新レコード確認 |
| リストア正確性 | 元データと完全一致 | チェックサム / レコード数確認 |

### 5.3 フェイルオーバーテスト

| 項目 | 合否基準 | 検証方法 |
|------|---------|---------|
| フェイルオーバー時間 | SLA 定義値以内 | Route53 健全性チェック + 切替時間計測 |
| フェイルオーバー後の機能 | 全機能が正常動作 | 本番相当のテストケース実行 |
| ロールバック | 元環境への戻し成功 | 切替前状態への復帰を確認 |

## 6. 移行リハーサル計画

### 6.1 リハーサル段階

#### Stage 1: 机上リハーサル（フェーズ4完了後）
- **実施者**: インフラ設計者 + QA
- **成果物**: 移行手順書レビュー
- **時間**: 4h 以上
- **合否判定**: 抜け漏れ / 危険箇所の指摘ゼロ

#### Stage 2: 環境構築テスト（フェーズ5開始時）
- **実施者**: インフラエンジニア
- **対象**: テスト環境 / ステージング環境
- **成果物**: 環境構築手順の実行ログ
- **合否判定**: 手順書通りに100%完成

#### Stage 3: 本番同様リハーサル（フェーズ6完了後）
- **実施者**: 本番チーム + QA
- **対象**: ステージング環境（本番構成と同等）
- **成果物**: リハーサル実行ログ、改善指摘
- **合否判定**: RTO / RPO 目標達成、改善指摘対応完了
