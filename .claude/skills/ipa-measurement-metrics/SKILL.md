# 品質メトリクス定義と基準値

## 概要

プロジェクトの品質を定量的に管理するため、標準的なメトリクスと基準値をまとめました。各メトリクスは、業界標準やGC案件での実績に基づいています。

---

## 1. バグ密度（Bug Density）

### 定義
```
バグ密度 = 摘出バグ数 / ソースコード規模

単位:
- /KLOC （千行数）: 手続き型言語（Python, bash）向け
- /関数   : オブジェクト指向言語向け
- /FP    : アーキテクチャ独立、言語中立
```

### 基準値テーブル

#### 通常のシステム開発
```
┌────────────────────────────────────────┐
│ バグ密度             │ 判定        │
├────────────────────────────────────────┤
│ < 0.3/KLOC          │ ✓✓ 優秀    │
│ 0.3-0.5/KLOC        │ ✓ 合格     │
│ 0.5-1.0/KLOC        │ △ 警告     │
│ > 1.0/KLOC          │ ✗ 不合格   │
└────────────────────────────────────────┘
```

#### インフラ IaC（Terraform/CloudFormation）
```
高い信頼性が要求される:
┌────────────────────────────────────────┐
│ バグ密度             │ 判定        │
├────────────────────────────────────────┤
│ < 0.2/KLOC          │ ✓✓ 優秀    │
│ 0.2-0.4/KLOC        │ ✓ 合格     │
│ 0.4-0.7/KLOC        │ △ 警告     │
│ > 0.7/KLOC          │ ✗ 不合格   │
└────────────────────────────────────────┘

理由：インフラコードは可用性への影響が大きい
```

#### 金融系・医療系システム
```
極めて高い信頼性が要求される:
┌────────────────────────────────────────┐
│ バグ密度             │ 判定        │
├────────────────────────────────────────┤
│ < 0.1/KLOC          │ ✓ 合格     │
│ 0.1-0.2/KLOC        │ △ 警告     │
│ > 0.2/KLOC          │ ✗ 不合格   │
└────────────────────────────────────────┘
```

### 計算例

```
Terraform モジュール 設定ファイルのテスト:
- ソースコード: 1200 行
- 摘出バグ: 5 件

バグ密度 = 5 / 1.2 KLOC = 4.17 / KLOC
判定: ✗ 不合格（インフラIaCの基準に対して）

→ テスト強化、セキュリティレビュー追加が必要
```

## 2. テストカバレッジ（Test Coverage）

### 定義
```
カバレッジ = テスト対象コード行数 / 全体コード行数 × 100%

測定方法:
1. ステートメント（行）カバレッジ — 最も基本的
2. ブランチ（分岐）カバレッジ  — より厳密
3. 条件カバレッジ               — 最も厳密（条件式の全組み合わせ）
```

### 基準値テーブル

```
┌────────────────────────────────────────┐
│ カバレッジ           │ 判定        │
├────────────────────────────────────────┤
│ > 85%               │ ✓✓ 優秀    │
│ 80-85%              │ ✓ 合格     │
│ 70-80%              │ △ 要改善   │
│ < 70%               │ ✗ 不合格   │
└────────────────────────────────────────┘

推奨:
- アプリケーション: 80% 以上
- インフラIaC: 70% 以上 （人的テストを補完）
- ビジネスロジック重要部分: 90% 以上
```

### 計算例

```
Lambda 関数テスト（Python):
- 全体コード: 500 行
- テスト対象: 420 行
- テストケースで実行: 410 行

カバレッジ = 410 / 500 × 100% = 82%
判定: ✓ 合格
```

## 3. バグ重要度分布（Bug Severity Distribution）

### 定義

| Level | 説明 | 本番リリース基準 |
|-------|------|----------------|
| Level 1 (致命) | システム停止、データ喪失、セキュリティ大洞 | 許容: 0 件 |
| Level 2 (重大) | 機能が使用不可、重要な計算誤り、セキュリティ脆弱性 | 許容: 0 件 |
| Level 3 (重要) | 機能が一部制限、ワークアラウンド有、パフォーマンス低下 | 許容: 0-2 件 |
| Level 4 (軽微) | UI/UXの問題、軽微な動作異常、ドキュメント誤り | 許容: 制限なし |

### リリース判定基準

```
リリース判定フロー:

Level 1, 2 あり → ✗ リリース不可
         ↓
Level 3 > 5 件 → ✗ リリース不可（対応後の再判定）
         ↓
Level 3 <= 2 件 → △ 条件付きリリース
       (ワークアラウンド確認、本番後追跡)
         ↓
Level 4 任意    → ✓ リリース可
```

## 4. テスト効率性（Test Efficiency）

### 定義
```
テスト効率 = 単体テストで検出したバグ数 / 単体テストで実行したテストケース数

例:
100 個のテストケース実行で 5 個のバグ検出
= 5 / 100 = 5%
```

### 基準値テーブル

```
┌──────────────────────────────────────┐
│ テスト効率       │ 判定         │
├──────────────────────────────────────┤
│ > 5%            │ ✓ 良好      │
│ 2-5%            │ △ 通常      │
│ < 2%            │ ✗ 低い      │
└──────────────────────────────────────┘

解釈:
- 効率が高い = テスト設計が良い（バグ検出率が高い）
- 効率が低い = テストが十分でない or コード品質が良好
```

## 5. レビュー指摘密度（Review Defect Density）

### 定義
```
指摘密度 = 指摘件数 / 作成ドキュメント量

単位:
- 設計書: 件数 / ページ
- コード: 件数 / 100 行
```

### 基準値テーブル

#### 設計書レビュー
```
┌──────────────────────────────────────┐
│ 指摘密度（設計書）  │ 判定     │
├──────────────────────────────────────┤
│ > 1.5 件/ページ    │ ✓ 有効   │
│ 0.5-1.5 件/ページ  │ △ 標準   │
│ < 0.5 件/ページ    │ ✗ 形式的 │
└──────────────────────────────────────┘

解釈:
- 高密度 = レビューで多くの問題が検出される（品質向上）
- 低密度 = レビューが形式的（見落としリスク）
```

#### コードレビュー
```
┌──────────────────────────────────────┐
│ 指摘密度（コード）   │ 判定     │
├──────────────────────────────────────┤
│ > 1.0 件/100行     │ ✓ 有効   │
│ 0.5-1.0 件/100行   │ △ 標準   │
│ < 0.5 件/100行     │ ✗ 形式的 │
└──────────────────────────────────────┘
```

## 6. ファンクションポイント（FP）生産性

### 定義
```
生産性 = ファンクションポイント / 開発工数（人月）

FP: ビジネス機能を定量化した単位
人月: 1人が1ヶ月間フルタイムで作業した工数
```

### 基準値テーブル

```
┌────────────────────────────────────────┐
│ プロジェクト規模   │ 生産性(FP/人月)  │
├────────────────────────────────────────┤
│ 小規模(<100FP)     │ 10-15 FP/人月   │
│ 中規模(100-1000FP) │ 5-10 FP/人月    │
│ 大規模(>1000FP)    │ 2-5 FP/人月     │
└────────────────────────────────────────┘

GC 案件での参考値:
┌────────────────────────────────────────┐
│ 作業種別            │ 生産性(FP/人月)  │
├────────────────────────────────────────┤
│ 要件定義            │ 2-4 FP/人月     │
│ NW/セキュリティ設計 │ 3-6 FP/人月     │
│ Terraform/CFn 実装  │ 15-25 FP/人月   │
│ テスト計画・実施    │ 5-8 FP/人月     │
│ ドキュメント作成    │ 2-3 FP/人月     │
└────────────────────────────────────────┘

理由: インフラコード化により自動化率が高い
```

## 7. 運用性メトリクス

### 稼働率（Availability）
```
稼働率 = (計画期間 - 停止時間) / 計画期間 × 100%

基準値:
┌─────────────────────────────────┐
│ 稼働率          │ 許容停止時間  │
├─────────────────────────────────┤
│ 99.99% (4ナイン) │ 年 52分       │
│ 99.9%  (3ナイン) │ 年 8.7時間   │
│ 99.0%  (2ナイン) │ 年 87.6時間  │
│ 95.0%           │ 年 18.25日   │
└─────────────────────────────────┘

GC案件での目標値:
- シングルテナント本番: 99.9% (3ナイン）
- 重要なサービス: 99.95% (4.5ナイン)
```

### 平均復旧時間（MTTR: Mean Time To Repair）
```
MTTR = 総復旧時間 / 障害件数

基準値:
┌──────────────────────────────────┐
│ 障害レベル │ MTTR目標 │ リスク │
├──────────────────────────────────┤
│ Critical   │ 1時間以内│ 高     │
│ Major      │ 4時間以内│ 中     │
│ Minor      │ 1日以内 │ 低     │
└──────────────────────────────────┘
```

### 平均故障間隔（MTTF: Mean Time To Failure）
```
MTTF = 総稼働時間 / 障害件数

目標値:
- インフラ: MTTF > 3ヶ月（年4回以下の障害）
- アプリケーション: MTTF > 1ヶ月（月1回以下の障害）
```

## 8. セキュリティメトリクス

### 脆弱性検出率（Vulnerability Detection Rate）
```
検出率 = テストで検出した脆弱性 / 本番で検出した脆弱性

基準値:
┌──────────────────────────┐
│ 検出率      │ 判定      │
├──────────────────────────┤
│ > 90%       │ ✓ 優秀   │
│ 70-90%      │ ✓ 合格   │
│ < 70%       │ ✗ 不足   │
└──────────────────────────┘
```

### 脆弱性応答時間（Vulnerability Response Time）
```
基準値:
┌──────────────────────────────────┐
│ 重要度     │ 対応期限  │ リスク │
├──────────────────────────────────┤
│ Critical   │ 24時間以内│ 極高   │
│ High       │ 7日以内  │ 高     │
│ Medium     │ 30日以内 │ 中     │
│ Low        │ 90日以内 │ 低     │
└──────────────────────────────────┘
```

## 9. コスト効率メトリクス

### コスト対効果（Cost per Function Point）
```
コスト効率 = プロジェクト総コスト / FP

基準値:
┌───────────────────────────────────────┐
│ 規模        │ コスト/FP   │ 判定     │
├───────────────────────────────────────┤
│ 小規模      │ ¥800-1200   │ 標準    │
│ 中規模      │ ¥1200-2000  │ 標準    │
│ 大規模      │ ¥2000-3500  │ 標準    │
├───────────────────────────────────────┤
│ コスト削減達成 │ < 上記 × 0.8 │ ✓    │
│ コスト超過   │ > 上記 × 1.2 │ ✗    │
└───────────────────────────────────────┘
```

## メトリクス測定計画テンプレート

```yaml
プロジェクト: GC 例案件
測定期間: 2026-03-01 ~ 2026-05-31
責任者: @pm

測定対象メトリクス:
  - バグ密度 (KLOC単位)
  - テストカバレッジ (ステートメント)
  - レビュー指摘密度 (ページ単位)
  - テスト効率性
  - FP生産性
  - 稼働率 (本番環境)

測定方法:
  バグ密度:
    - 計測対象: 全開発環境での摘出バグ
    - 集計単位: KLOC (千行数)
    - 集計タイミング: 月末
    - ツール: Jira

  テストカバレッジ:
    - ツール: Jacoco / Coverage.py
    - 測定タイミング: CI/CD パイプライン内で自動計測
    - 集計: マージ時点での値

報告:
  - 月次レポート: 全メトリクスの推移
  - 四半期ごとの傾向分析
  - 年度末の総括 (目標値との対比)
```
