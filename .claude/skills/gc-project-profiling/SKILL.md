# GC案件 プロファイリング知識ベース

## 概要
ガバメントクラウド（GC）案件特有の特性・工数係数・追加タスク・リスク要因をまとめたナレッジベース。テーラリング、見積、リスク管理の基盤データ。

---

## 自治体規模別特性

### 小規模自治体（人口 <50万）

#### 典型例
- 市町村（一般市、町、村）
- 職員数 500-1,500 名
- 情報システム部門 2-5 名
- 予算規模 数千万～1億円程度

#### 特性
| 項目 | 特徴 |
|------|------|
| 意思決定 | 迅速、稟議ルート短い |
| ステークホルダー | 市民部門、税務部門など5-10部門 |
| 既存システム | レガシー（汎用機+ Windows Server） が多い |
| セキュリティ | 個人情報保護条例対応必須だが、ISMAP申請レベルまでは不要なことが多い |
| ネットワーク | LGWAN のみ、シンプル構成 |
| 運用体制 | 専任者 1-2 名、外部サポートに依存 |
| 契約体系 | 一括購入、単価重視 |

#### 工数・スケジュール
- 提案見積 Phase: 2-3週間, 40-60人日
- 要件定義 Phase: 4-6週間, 100-150人日
- 全体プロジェクト: 6-9ヶ月, 600-900人日

#### 留意点
- ユーザー側リソース確保が難しい（兼任が多い）→ 意思決定遅延リスク
- 既存システムドキュメント不足 → 現行調査に時間かかる
- 「クラウドって何？」という基礎教育から開始必要

---

### 中規模自治体（人口 50-200万）

#### 典型例
- 政令指定都市未満の中核市
- 職員数 2,000-5,000 名
- 情報システム部門 20-50 名
- 予算規模 数億円程度

#### 特性
| 項目 | 特徴 |
|------|------|
| 意思決定 | 標準的、稟議ルート2-3段階 |
| ステークホルダー | 15-25 部門、関係者 50-100 名 |
| 既存システム | レガシー + クラウド混在（既に SaaS/IaaS 導入事例あり） |
| セキュリティ | 個人情報保護条例 + ISMAP対応を検討中のことが多い |
| ネットワーク | LGWAN + インターネット分離, 支所VPN接続 |
| 運用体制 | 専任者 5-10 名、内製と外部委託のハイブリッド |
| 契約体系 | 複数年契約、TCO重視 |

#### 工数・スケジュール
- 提案見積 Phase: 2-3週間, 60-100人日
- 要件定義 Phase: 6-8週間, 150-220人日
- 全体プロジェクト: 9-15ヶ月, 900-1,500人日

#### 留意点
- ステアリングコミッティ設置必須（月1回）
- 複数部門の利害対立 → リスク高い
- ISMAP 対応は必須と考えるべき

### 大規模自治体（人口 200-500万）

#### 典型例
- 政令指定都市、人口 150 万人以上の都市
- 職員数 8,000-15,000 名
- 情報システム部門 100-200 名
- 予算規模 数十億円規模

#### 特性
| 項目 | 特徴 |
|------|------|
| 意思決定 | 複雑、稟議ルート4-5段階、経営層の決定待機 |
| ステークホルダー | 30-50 部門、関係者 200-300 名 |
| 既存システム | 複雑（メインフレーム+オンプレサーバー+クラウド混在） |
| セキュリティ | ISMAP 対応必須、外部監査あり |
| ネットワーク | LGWAN + DirectConnect, 複数拠点 VPN |
| 運用体制 | 内製化志向、 24 時間監視体制 |
| 契約体系 | 長期契約（3-5年）、総合評価方式（価格+技術） |

#### 工数・スケジュール
- 提案見積 Phase: 3-4週間, 100-160人日
- 要件定義 Phase: 8-12週間, 220-350人日
- 全体プロジェクト: 12-18ヶ月, 1,500-2,500人日

#### 留意点
- ステアリングコミッティ + 各部門調整会議（週1回以上）
- セキュリティ監査対応（外部監査、監査法人）
- 既存システム廃棄・レガシー脱却が大きなテーマ
- マルチシステム管理（システムA/B/Cの段階的移行）

---

### 省庁級（国庫補助あり、全国展開）

#### 典型例
- 都道府県、指定都市、複数市町村の共同事業
- 対象 5-100 自治体
- 職員数 数千～数万
- 予算規模 数十～数百億円

#### 特性
| 項目 | 特徴 |
|------|------|
| 意思決定 | 極めて複雑、複数の上位機関（国庫補助関係者）の承認必須 |
| ステークホルダー | 自治体 5-100 個、部門 100 個以上 |
| 既存システム | 多様（ベンダーも異なる） |
| セキュリティ | ISMAP 対応 + 国庫補助要件対応（NISC など） |
| ネットワーク | LGWAN + DirectConnect + クロスボーダーNW |
| 運用体制 | 統一運用センター構想、全国展開対応 |
| 契約体系 | 国庫補助契約 + 地方譲与税、複数契約体系 |

#### 工数・スケジュール
- 提案見積 Phase: 4-6週間, 160-250人日
- 要件定義 Phase: 12-16週間, 350-600人日
- 全体プロジェクト: 18-36ヶ月, 3,000-6,000人日

#### 留意点
- 国庫補助関係者との多段階承認 → 意思決定遅延リスク最高
- 「共通化」「標準化」のテーマが重要
- セキュリティ・監査対応が必須、かつ非常に複雑
- 統一ガバナンス構築が重要（各自治体の独立性とのバランス）

## 移行方式別工数係数

### リフト（Lift and Shift）
**工数係数: 1.0**

#### 特性
- 既存システム構成をそのまま AWS に移行
- 最小限の機能修正
- オンプレミスの設定・アーキテクチャをクラウドに転写

#### 工数の配分
| フェーズ | 係数 | 理由 |
|--------|------|------|
| Phase 2（要件定義） | 0.8 | 機能変更なし、現行調査に集中 |
| Phase 4（設計） | 0.6 | 既存構成をそのまま移行設計 |
| Phase 5（構築） | 1.0 | リホストのため実装量は標準 |
| Phase 6（テスト） | 0.7 | 機能テストは既存仕様で十分 |
| Phase 7（移行） | 1.3 | データ移行・検証に時間かかる |

**典型的な見積: 800-1,200 人日, 9-12ヶ月**

#### リスク
- 既存システムの制約がクラウドに持ち込まれる（パフォーマンス劣化など）
- レガシー問題が温存される
- 将来のクラウドネイティブ化が困難

#### 適用シーン
- 既存システムが安定稼働中で、変更を最小限にしたい
- 短納期・低予算のプロジェクト
- 既存資産（ライセンス）を最大限活用したい

---

### R1（リホスティング）
**工数係数: 1.3**

#### 特性
- IaaS（EC2） でオンプレシステムをホスト
- 一部の重いコンポーネントを AWS ネイティブサービス（RDS, S3）に置き換え
- 段階的なクラウド化のステップ 1

#### 工数の配分
| フェーズ | 係数 | 理由 |
|--------|------|------|
| Phase 2（要件定義） | 1.0 | DB選定、スケーラビリティ要件の追加 |
| Phase 4（設計） | 1.0 | AWS ネイティブサービス（RDS など）の設計 |
| Phase 5（構築） | 1.3 | DB マイグレーション、アプリ修正 |
| Phase 6（テスト） | 1.2 | パフォーマンステスト、互換性テスト追加 |
| Phase 7（移行） | 1.4 | DB 移行、並行検証に時間かかる |

**典型的な見積: 1,040-1,560 人日, 10-14ヶ月**

#### リスク
- アプリケーション修正必要（既存ベンダーコントロール外）
- DB スキーマ変更に伴うテスト工数増
- 既存ライセンス（DB など）の問題

#### 適用シーン
- オンプレDB（Oracle など）を RDS に置き換えたい
- ある程度のアプリ修正は許容できる
- 中期的にクラウドネイティブ化を目指したい

---

### R2（リプラットフォーミング）
**工数係数: 1.8**

#### 特性
- ビジネスロジックは維持、技術スタックを大幅刷新
- レガシー言語（COBOL など）をモダン言語（Java など）に移行
- レガシー DB を新型 DB に移行
- アーキテクチャの全面見直し

#### 工数の配分
| フェーズ | 係数 | 理由 |
|--------|------|------|
| Phase 2（要件定義） | 1.5 | 新技術スタックの検討、互換性確認 |
| Phase 4（設計） | 1.8 | 新アーキテクチャ設計、スキーマ設計 |
| Phase 5（構築） | 2.0 | 言語変換、新フレームワーク習熟 |
| Phase 6（テスト） | 1.8 | 全面的な機能テスト、パフォーマンステスト |
| Phase 7（移行） | 1.5 | リスク高い、複数リハーサル必須 |

**典型的な見積: 1,440-2,160 人日, 12-18ヶ月**

#### リスク
- 高リスク（言語変換、新技術導入）
- ベンダー側の COBOL スキル人員が必要
- テストボリュームが大幅増
- バグ・不具合の可能性高い（全機能再実装）

#### 適用シーン
- COBOL などレガシー言語からの脱却必須
- 既存ベンダーに追加の開発能力がない場合
- 中長期的なシステム保守性を重視したい

---

### 新規構築
**工数係数: 2.5**

#### 特性
- 既存システムなし、またはスクラッチから新規開発
- クラウドネイティブ設計を前提
- ビジネス要件をゼロから定義

#### 工数の配分
| フェーズ | 係数 | 理由 |
|--------|------|------|
| Phase 2（要件定義） | 2.0 | ビジネス要件をゼロから詳細化 |
| Phase 4（設計） | 2.5 | クラウドネイティブアーキテクチャ設計 |
| Phase 5（構築） | 2.5 | 新規開発、フレームワーク習熟 |
| Phase 6（テスト） | 2.0 | 全面的な機能テスト |
| Phase 7（移行） | 1.5 | 既存システムなし、並行運用不要 |

**典型的な見積: 2,000-3,000 人日, 12-20ヶ月**

#### リスク
- 要件定義フェーズの遅延 → プロジェクト全体遅延
- 仕様変更・追加要件の可能性高い
- 運用・保守体制の構築が重要

#### 適用シーン
- まったく新しいサービス・システムを立ち上げる
- 既存システムを廃棄、クラウドで再構築
- デジタル化を推進する新規事業

## GC 固有追加タスク 10 件

GC 利用の際に、通常の SaaS/IaaS 案件に加えて必須となるタスク：

### タスク1: GCAS（ガバメントクラウド・アカウント・サービス）申請対応
**必須度: 最高**
- **対象フェーズ:** Phase 0
- **工数:** 40 人日
- **期間:** 2-4 週間（GC 側の審査待機）
- **担当:** PM, セキュリティ SE
- **概要:**
  - CEP（契約企業プロフィール）の申請書類作成
  - セキュリティチェックシート作成・提出
  - GC 承認待機、GC からの質問対応
- **成果物:**
  - CEP 登録完了
  - GCA S アカウント発行通知書

### タスク2: 自治体 IT 調達仕様ポイント確認
**必須度: 高**
- **対象フェーズ:** Phase 1
- **工数:** 10 人日
- **担当:** PM,営業
- **概要:**
  - GC 調達仕様書（内閣府）の要件確認
  - ASP 要件の確認（必要な場合）
  - 自治体ローカル要件の確認
- **成果物:**
  - 調達要件チェックシート

### タスク3: ISMAP（情報セキュリティマネジメント適格性認定）対応準備
**必須度: 高（ISMAP対応案件）**
- **対象フェーズ:** Phase 1-2
- **工数:** 20 人日
- **担当:** セキュリティ SE
- **概要:**
  - ISMAP 認定基準の確認（自治体の対応レベル決定）
  - AWS GC の ISMAP 認定状況確認
  - セキュリティ要件の詳細化
- **成果物:**
  - ISMAP 対応要件リスト

### タスク4: 多自治体ガバナンス体制設計（共同利用の場合）
**必須度: 高（共同利用のみ）**
- **対象フェーズ:** Phase 2
- **工数:** 60 人日
- **期間:** 6-8 週間
- **担当:** PM, ビジネスアナリスト
- **概要:**
  - 各自治体の役割・責任の定義
  - インターフェース仕様書作成（自治体間データ授受）
  - 運用ガバナンス（月1回以上の調整会議）の運営方法定義
- **成果物:**
  - 共同利用ガバナンスマニュアル
  - インターフェース仕様書（各IF, 5-10 個）

### タスク5: 自治体既存ネットワークとの接続設計（LGWAN対応）
**必須度: 最高**
- **対象フェーズ:** Phase 2-4
- **工数:** 30 人日
- **担当:** ネットワークエンジニア
- **概要:**
  - 自治体の LGWAN 接続方式の確認（VPN か DirectConnect か）
  - 既存ゲートウェイの確認
  - GC 上のネットワーク設計と既存 NW の接続設計
- **成果物:**
  - LGWAN 接続設計書
  - ネットワークトポロジー図

### タスク6: セキュリティ設計・監査対応（ISMAP / 個人情報保護）
**必須度: 最高**
- **対象フェーズ:** Phase 4-6
- **工数:** 60 人日（セキュリティレベルに応じて 20-80人日）
- **担当:** セキュリティ SE, 外部診断機関
- **概要:**
  - IAM (Identity and Access Management) 設計（多要素認証、ロールベース制御）
  - 暗号化ポリシー（保存時・転送時）
  - 監査ログ・ログ保全体制
  - 脆弱性診断（Phase 6）
  - セキュリティ監査対応（外部監査機関）
- **成果物:**
  - セキュリティ設計書
  - 脆弱性診断報告書（2 回以上）
  - ISMAP 監査チェックシート完了

### タスク7: 運用・保守体制の設計（クラウド特有の 24 時間監視対応）
**必須度: 高**
- **対象フェーズ:** Phase 5-8
- **工数:** 40 人日
- **期間:** 4 週間
- **担当:** オペレーション SE, PM
- **概要:**
  - CloudWatch, AWS Config などの監視設定
  - インシデント対応手順書（Runbook）作成
  - 24 時間シフト体制の計画（大規模案件）
  - AWS Well-Architected Framework に基づく定期レビュー
- **成果物:**
  - 運用マニュアル / Runbook
  - 監視・アラート設定書
  - インシデント対応体制図

### タスク8: DR（ディザスタリカバリー）・BC（ビジネスコンティニュイティ）計画
**必須度: 高**
- **対象フェーズ:** Phase 4-5
- **工数:** 30 人日
- **担当:** インフラ SE
- **概要:**
  - RTO（復旧時間目標）/ RPO（復旧ポイント目標）の設定
  - バックアップ戦略（スケジュール、保持期間）
  - フェイルオーバー手順（自動化か手動か）
  - 定期 DR テスト計画（年 4 回）
- **成果物:**
  - DR 計画書
  - バックアップ・リストア手順書

### タスク9: クラウド利用料の見積・最適化
**必須度: 高**
- **対象フェーズ:** Phase 3-4
- **工数:** 15 人日
- **担当:** コストエンジニア / PM
- **概要:**
  - AWS リソース見積（EC2, RDS, S3 など）
  - RI（リザーブドインスタンス）/ Savings Plans の活用
  - 定期的なコスト最適化レビュー（月1回）
- **成果物:**
  - AWS 利用料見積書
  - コスト最適化提案書

### タスク10: ユーザー教育・クラウドリテラシー向上
**必須度: 中**
- **対象フェーズ:** Phase 5-8
- **工数:** 20 人日
- **期間:** 2 ヶ月
- **担当:** トレーニング SE
- **概要:**
  - クラウド基礎知識（自治体職員向け）
  - システム運用者向けの CloudWatch, ログ分析トレーニング
  - 定期ウェビナー（月 1 回）
- **成果物:**
  - トレーニング教材
  - トレーニング実施ログ

## GC 案件リスク要因マトリクス

| リスク要因 | リスク度 | 自治体規模別 | 移行方式別 | 対策 |
|----------|--------|-----------|----------|------|
| 意思決定遅延（ステアリング承認） | 高 | 大規模 | 全て | ステアリング月1回以上、エスカレーションルール明確化 |
| 要件定義不足 | 高 | 全て | 新規構築 / R2 | Phase 2 強化、非機能要件詳細化ワークショップ |
| GCAS 申請却下 | 中 | 全て | 全て | 事前の CEP 要件確認、GC 登録企業での実施 |
| ISMAP 監査指摘 | 中 | 大規模 | 全て | Phase 4 設計時セキュリティレビュー、外部診断早期実施 |
| 既存 NW との接続問題 | 中 | 全て | リフト / R1 | Phase 2 で現行 NW 詳細調査、自治体 NW 部門との定期会議 |
| ASP / 外部 IF 多数 | 高 | 全て | 全て | Phase 2 で IF 優先度つけ、早期統合テスト |
| 期限短縮による品質低下 | 中 | 全て | 全て | EVM 導入、定期リスク評価（月1回） |
| セキュリティテスト期間不足 | 中 | 大規模 | 新規 | Phase 6 テスト期間 +4 週間確保、並行実施計画 |
| 既存ドキュメント不完備 | 高 | 小 / 中規模 | リフト / R1 | Phase 2 で現行調査タスク +20% |
| マルチシステム並行管理 | 高 | 大規模 | 全て | @infra-impact-analysis で影響分析、フェーズシフト |

## GC 案件向け用語集

| 用語 | 意味 | 備考 |
|------|------|------|
| **GC** | ガバメントクラウド | 政府・自治体向けのクラウドサービス |
| **GCAS** | ガバメントクラウド・アカウント・サービス | GC を利用するための申請・承認プロセス |
| **CEP** | 契約企業プロフィール | GC の申請時に提出する企業情報・セキュリティ情報 |
| **ASP** | アプリケーション・サービス・プロバイダ | GC 上で動作する外部システム、SaaS 等 |
| **LGWAN** | 地域行政ネットワーク | 自治体と国を結ぶ行政専用 NW |
| **DX** | DirectConnect | AWS と自治体をダイレクトに接続する専線 |
| **ISMAP** | 情報セキュリティマネジメント適格性認定 | 自治体が導入するクラウド・ソフトウェアのセキュリティ認定 |
| **VPN** | Virtual Private Network | 暗号化されたプライベートネットワーク |
| **RTO** | Recovery Time Objective | 目標復旧時間（災害発生からシステム復旧までの時間） |
| **RPO** | Recovery Point Objective | 目標復旧ポイント（許容データロス量） |
| **HA / DR** | High Availability / Disaster Recovery | 高可用性・災害復旧設計 |
| **IaC** | Infrastructure as Code | インフラをコード化（Terraform など） |
